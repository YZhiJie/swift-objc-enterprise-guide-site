第 11 章 iOS 架构模式与 SwiftUI 深度工程 ​

第 5 章教「框架怎么用」，本章解决「企业级 UI 层怎么组织才能扛住 50 人团队、五年演进、百万行代码」。架构模式没有标准答案，只有约束下的取舍：本章给出 MVC/MVVM/TCA 的工程化对比与选型决策树，Observation 时代的 MVVM 正确写法，TCA 的核心闭环，类型安全导航与深链收口，动效治理，以及老 UIKit 工程的双轨改造路线——每一种选择都落到「团队规模、上手成本、可测性」三根标尺上。

说明：本章的「订单列表」需求在 examples/ 的 ArchitecturePatterns target 中以三种模式各实现一遍（swift run ArchitecturePatterns），并配 4 组单元测试验证「架构带来的可测性」。

11.0 学习目标 ​

完成本章后，你将能够：

  1. 用「适用团队规模 / 上手成本 / 可测性」三轴对比为具体团队与业务选择架构模式，并说明取舍依据；
  2. 在 Observation 时代写出职责边界清晰的 MVVM：状态机 ViewModel、协议注入、脱离 UI 的单元测试；
  3. 理解 TCA 的 State/Action/Reducer/Effect 四件套，判断何种业务值得引入、何时不值得；
  4. 用可枚举路由构建类型安全导航体系，把 Universal Links / 推送 / 快捷指令等深链入口收敛为单一路由器；
  5. 建立动画与手势的团队级治理规则，避免动效引发的性能回归；
  6. 为遗留 UIKit 工程制定「双轨并行」的渐进改造方案与评审门禁。

11.2 架构模式演进与选型决策树 ​

11.2.1 从双向纠缠到单向数据流 ​

Apple 官方的 MVC 常被戏称为 "Massive View Controller"——问题不在模式本身，而在于 Controller 同时承担了「布局协调、业务决策、数据加工、状态管理」四种职责，任何一职责膨胀都会污染其余三者。现代架构的共同演化方向是单向数据流：

11.2.3 模式混用的治理规则 ​

大型工程几乎必然多种模式并存（遗留 MVC + 新 MVVM + 局部 TCA），混用不可怕，失控才可怕。三条治理规则：

  1. 模块边界即模式边界：一个 feature 模块内只允许一种主模式（呼应第 10 章 10.4.1 的分层模块化），跨模块不互相检查内部模式；
  2. 模式之间必须过协议：UIKit 页面与 SwiftUI 页面消费同一 ViewModel 协议（见 11.7），禁止两边各存一份状态；
  3. 新页面默认新规范：新增页面一律 SwiftUI + @Observable，存量页面只做维护性修改——用评审门禁（第 9 章 9.6）而非口头约定执行。

❌ 反例：同一个页面里一半视图走 MVC delegate、一半走 @Observable 绑定，状态两处存放——「页面显示与真实数据不一致」这类最难排查的线上问题大多源于此。

11.3 MVVM：Observation 时代的正确写法 ​

11.3.1 ViewModel 的职责边界 ​

MVVM 失败的项目大多不是「框架选错」，而是 ViewModel 变成了垃圾抽屉。判断标准只有一条：这是不是一段可以脱离 UI 测试的业务决策？

该进 ViewModel不该进 ViewModel
加载/提交状态机（idle→loading→loaded/failed）UIView/UIColor/字体等视图引用
输入校验与业务规则（金额上限、表单联动）布局与展示格式之外的外观决策
派生数据（合计、分组、排序后的展示模型）import SwiftUI / import UIKit
用户意图的路由回调（「去详情」用闭包/事件表达）导航的具体实现（push/pop 写在 VM 里）

⚠️ 坑点：评审时重点检查 ViewModel 的 import 列表——出现 SwiftUI/UIKit 即打回。一旦 import 了 UI 框架，这个类就绑死在主线程与界面上，7.6 的协议注入测试体系全部失效。

11.3.2 状态机驱动的 ViewModel ​

用枚举状态机取代「isLoading + data + error 三变量散放」：非法组合（既 loading 又 loaded）在类型上不可能出现，UI 层每个分支都能穷举处理。

swift
// File: MVVM.swift —— 状态机 ViewModel（完整可运行版见 examples）

import Foundation
import Observation

@MainActor
@Observable
final class OrderListViewModel {

    private(set) var phase: LoadPhase = .idle

    /// 每次加载新建 Task 并保存引用——取消句柄；不保存就无法取消（常见遗漏）
    private var loadTask: Task<Void, Never>?

    /// 依赖注入：依赖协议而非具体实现，Stub 才能注进来（第 7 章 7.6）
    let repository: any OrderRepositoryProtocol

    func load() {
        loadTask?.cancel()                      // ✅ 重复触发先取消旧的：防迟到回调竞态
        phase = .loading
        loadTask = Task { [weak self] in
            guard let self else { return }
            do {
                let orders = try await repository.fetchOrders()
                guard !Task.isCancelled else { return }   // 已被取消：不回写状态
                phase = .loaded(orders)
            } catch is CancellationError {
                return                              // 主动取消不算失败，静默退出
            } catch {
                guard !Task.isCancelled else { return }
                phase = .failed("加载失败，请重试")
            }
        }
    }

    /// 视图生命周期钩子：SwiftUI 的 onDisappear / UIKit 的 viewWillDisappear 调用
    func cancelLoading() {
        loadTask?.cancel()
    }
}

三个工程要点：

  1. 取消是生命周期义务：页面销毁时在途请求若不取消，迟到回调会把已退出页面的状态改脏——这是企业级 App 高频线上竞态（与第 2 章 2.8 协作取消同一思想）；
  2. 派生数据用计算属性：totalAmountText 从 phase 现算，而不是请求回来时手动再存一份「合计」——两份状态必然在某次改码后失同步；
  3. @MainActor 隔离：与第 5 章 5.3 一致，UI 状态只在主线程变更，Swift 6 严格并发下编译器直接把关。

11.4 TCA：可预测状态的工程化 ​

11.4.1 四件套：State / Action / Reducer / Effect ​

TCA（The Composable Architecture）把「单向数据流」变成强约束的框架：状态只能被 Reducer 修改，外部世界只能通过 Effect 触达。

    R -->|返回| E[Effect 副作用]

11.4.2 最小实现：60 行看懂核心闭环 ​

生产请直接用官方 swift-composable-architecture（依赖治理见第 8 章 8.3）；下面用 60 行还原其骨架，帮助理解「为什么这套约束换来可预测性」：

swift
// File: MiniTCA.swift —— 教学用最小实现（完整可运行版见 examples）

/// 副作用：唯一被允许触达外部世界的通道
/// 设计决策：Effect 只返回 Action，绝不直接改 State——
/// 所有状态变更必须回流 reducer 这一「独木桥」，可回放、可预测由此而来
struct Effect<Action>: Sendable {
    private let operation: (@Sendable () async -> Action?)?
    static func none() -> Effect<Action> { Effect(operation: nil) }
    static func task(_ body: @escaping @Sendable () async -> Action?) -> Effect<Action> {
        Effect(operation: body)
    }
    var run: (@Sendable () async -> Action?)? { operation }
}

struct OrderListFeature {
    struct State: Equatable { var phase: LoadPhase = .idle }

    enum Action: Equatable {
        case onAppear, refreshTapped
        case ordersLoaded([Order])      // 副作用回流
        case ordersFailed(String)
    }

    let repository: any OrderRepositoryProtocol

    /// Reducer：纯函数。可测性红利——不需要 UI、不需要异步等待，
    /// 直接 inout 断言状态转移（见下方「同步转移」演示）
    func reduce(_ state: inout State, action: Action) -> Effect<Action> {
        switch action {
        case .onAppear, .refreshTapped:
            state.phase = .loading
            let repository = self.repository
            return .task {
                do { return .ordersLoaded(try await repository.fetchOrders()) }
                catch { return .ordersFailed("加载失败，请重试") }
            }
        case .ordersLoaded(let orders):
            state.phase = .loaded(orders)
            return .none()
        case .ordersFailed(let message):
            state.phase = .failed(message)
            return .none()
        }
    }
}

注意两个纪律点：

  • Store 是唯一入口：View 只 send(action)，永不直接改 state；副作用结果回流后再次走 reducer；
  • Effect 禁止偷改 State：-effect 里拿到的是不可变捕获，改状态必须回流 Action——这是「任何历史状态都能用 Action 序列回放」的前提，也是金融审计场景（11.4.3）看重的性质。

11.4.3 何时引入 TCA（以及何时不引入） ​

适合 TCA 的信号不适合的信号
状态联动复杂：多输入源交叉影响（表单跨步校验、工单状态机）页面以展示为主，状态简单（详情页、内容流）
需要状态回放取证：交易/审批流程要求「每步操作可追溯」团队没有 2~4 周学习预算
测试 ROI 要求高：逻辑路径多到人肉回归不可行项目周期短，框架收益来不及兑现
模块需要严格组合：父 feature 组合子 feature已有成熟 VM 体系且运转良好

⚠️ 坑点：TCA 与 Swift 6 严格并发协作良好（Effect 闭包 @Sendable、Store @MainActor），但官方库版本升级较快——锁定版本（Package.resolved，第 9 章 9.7）并在升级说明中做 breaking change 评审，避免「顺手升级」引发全量编译错误。

11.5 导航体系：类型安全路由与深链收口 ​

11.5.1 路由是状态，不是动作 ​

用字符串路径或 storyboard segue 管理导航的问题是：跳转逻辑散落各处、无法测试、无法持久化恢复。现代做法是把「当前导航位置」建模为可枚举状态，push 由数据驱动：

swift
// File: AppRouter.swift —— 类型安全路由（Xcode 工程内验证）

import SwiftUI

/// 全 App 的导航目的地：一个枚举穷举（新增页面 = 新增 case + 一个 destination 分支）
enum AppRoute: Hashable {
    case orderList
    case orderDetail(id: String)
    case settings
}

struct RootView: View {
    @State private var path: [AppRoute] = []     // ✅ 导航栈就是数组：可测试、可序列化恢复

    var body: some View {
        NavigationStack(path: $path) {
            OrderListScreen(onNavigate: { path.append(.orderDetail(id: $0)) })
                .navigationDestination(for: AppRoute.self) { route in
                    switch route {
                    case .orderList:            OrderListScreen(onNavigate: { _ in })
                    case .orderDetail(let id):  OrderDetailScreen(orderID: id)
                    case .settings:             SettingsScreen()
                    }
                }
        }
    }
}

11.5.2 深链收口：所有入口归一到单一路由器 ​

企业 App 的跳转入口至少五个：Universal Links、推送点击、快捷指令（App Intents）、Widget、App 内交叉跳转。每个入口各写一套跳转逻辑必然失控——正确姿势是单一解析器：

// File: DeepLinkRouter.swift —— 解析是纯函数：可全量单测

/// Universal Links 三步前置（Xcode 工程配置）：Associated Domains 能力 +
/// 苹果官方 CDN 校验的 apple-app-site-association 文件 + URL 构建规范。
/// 本路由器只关心「URL 进来之后」的解析与归一。
enum DeepLinkRouter {
    /// 把任意入口的 URL 归一为路由数组（可能一次 append 多级）
    static func resolve(_ url: URL) -> [AppRoute]? {
        guard url.host == "www.example.com" else { return nil }   // 域名白名单：防伪造
        switch url.pathComponents.dropFirst().joined(separator: "/") {
        case "orders":              return [.orderList]
        case let detail where detail.hasPrefix("orders/"):
            let id = String(detail.dropFirst("orders/".count))
            return id.isEmpty ? nil : [.orderList, .orderDetail(id: id)]  // ✅ 带上级页面
        case "settings":            return [.settings]
        default:                    return nil
        }
    }
}

11.6 动画与手势的系统化治理 ​

动画在消费级 App 里是「手感」，在企业级 App 里是预算内资源：动效曲线不统一会让产品显得拼凑，动效滥用会直接打穿 10.5.1 的性能预算（低端机掉帧）。

11.6.1 统一动效令牌 ​

与颜色/字体一样，时长与曲线应收敛为设计令牌，由组件库（第 10 章 10.4.1 的 C1 层）统一托管：

swift
// File: Motion.swift —— 动效令牌：全 App 只允许从这取值

enum Motion {
    /// 时长档位：禁止随手 .animation(duration: 0.37) 这类「手感值」
    enum Duration {
        static let instant: TimeInterval = 0.15   // 反馈类：按压、勾选
        static let standard: TimeInterval = 0.25  // 常规转场：卡片展开、页面元素
        static let emphasis: TimeInterval = 0.4   // 强调类：成功动效、引导
    }
    /// 曲线档位：入场上浮、离场下沉，方向语义统一
    static let enter = Animation.spring(duration: Duration.standard, bounce: 0.15)
    static let exit  = Animation.easeOut(duration: Duration.instant)
}

11.7.2 关键技术：一个 ViewModel 消费两套 UI ​

双轨期「状态不分裂」的关键：UIKit 页面与 SwiftUI 区块消费同一个 ViewModel 实例——SwiftUI 靠 @Observable 自动追踪，UIKit 靠注册回调手动同步：

swift
// File: DualTrackBinding.swift —— 双轨绑定（Xcode 工程内验证）

import UIKit
import SwiftUI
import Observation

/// UIKit 侧的桥接：订阅 @Observable 的状态变化，手动刷新 UIKit 控件
@MainActor
final class OrderListBridge: NSObject {
    private let vm: OrderListViewModel
    private var observationTask: Task<Void, Never>?

    init(vm: OrderListViewModel, onChange: @escaping () -> Void) {
        self.vm = vm
        super.init()
        // Observation 的底层 API：注册回调循环读取（与 SwiftUI 同一机制）
        observationTask = Task { [weak self] in
            withObservationTracking {
                _ = vm.phase                       // 读取即注册依赖
            } onChange: {
                Task {                             // 状态变化：回到主线程重注册 + 通知
                    await self?.reregister(onChange)
                    onChange()
                }
            }
        }
    }

    private func reregister(_ onChange: @escaping () -> Void) {
        observationTask?.cancel()
        observationTask = Task { [weak self] in
            withObservationTracking { _ = self?.vm.phase } onChange: {
                Task { await self?.reregister(onChange); onChange() }
            }
        }
    }

    deinit { observationTask?.cancel() }           // ✅ 桥接随 UIKit 视图一起销毁，防泄漏
}

企业级场景分析 ​

场景一：千万行遗留工程的 MVVM 改造战役 ​

背景：装机量数千万级的金融 App，200+ 页面 UIKit + MVC，Controller 平均 1500 行，页面级回归靠 10 人 QA 团队手点，一轮全量回归 3 周。

策略（与第 4 章「渐进迁移」、第 5 章场景一同构）：

  1. 不换模式先换依赖：第一阶段只做「Controller 瘦身」——把网络与业务规则抽成协议注入的 Service，Controller 只剩装配与展示，可测代码量从 0 升到 40%；
  2. 状态层统一：新功能一律 SwiftUI + @Observable；存量页面通过 11.7.2 的桥接消费同一 ViewModel，杜绝双份状态；
  3. 替换节奏绑定版本火车：每版本替换 1~2 个低风险页面（设置、关于、活动页先行），核心交易链路最后动且带完整 UI 测试兜底；
  4. 门禁防回潮：新增 UIViewController 文件数、ViewModel 的 UI import 检查进入 CI（第 7 章 7.9 静态扫描）。

结果指标（综合公开实践的典型量级）：页面级自动化回归占比从 0 到 70%，全量回归周期从 3 周压到 4 天；新页面交付效率提升约三分之一。关键经验：改造的对手不是 MVC，而是「没有状态纪律」——先立状态层纪律，再谈模式替换。

场景二：TCA 在金融开户表单流的落地 ​

背景：某银行远程开户流程 40+ 字段、6 步联动（证件类型影响 OCR 字段、职业影响风险测评题库），MVC 版本状态散落 8 个 ViewController + 3 个单例，跨步回改必然出现脏状态，投诉工单难以复现。

方案：整条流程一个 Reducer 树（每步一个子 Reducer 组合），Action 全量埋点上报（脱敏后），State 快照随工单存档。

结果：

指标改造前改造后
联动逻辑测试用例手工回归 120 项自动化 480 项（Reducer 纯函数，毫秒级）
脏状态类缺陷月均 9 个月均 ≤1 个
投诉复现依赖用户口述 + 服务端日志拼接按 Action 序列回放 State，分钟级复现

关键经验：TCA 的「可回放」在监管审计场景是刚需而非锦上添花——每一步状态变化都有 Action 记录可查，举证成本数量级下降。代价是团队 2~4 周学习曲线与框架版本治理，适合核心高风险流程而非全 App 铺开。

小结与自测 ​

要点回顾：

  1. 架构选型看三根标尺（团队规模/上手成本/可测性），MVVM + @Observable 是默认起点，TCA 留给复杂状态联动与审计回放场景；
  2. ViewModel 是状态机不是垃圾抽屉：禁止 import UI 框架、依赖协议注入、派生数据用计算属性；
  3. 加载必须管理取消：页面销毁取消在途 Task，迟到回调不回写状态；
  4. TCA 的可预测性来自两条纪律：状态只被 Reducer 修改、副作用只能回流 Action——可回放由此而来；
  5. 导航是可枚举状态：类型安全路由 + 深链单一解析器（纯函数 + 负向测试），冷启动竞态用路由队列化解；
  6. 双轨改造的关键是一个 ViewModel 消费两套 UI：SwiftUI 自动追踪、UIKit 桥接订阅，状态永远只有一份。

自测题（先自答再回看正文）：

1. ViewModel 里为什么不能 import SwiftUI/UIKit？

一旦引入 UI 框架，ViewModel 就绑死在界面与主线程上：无法在毫秒级单元测试中实例化、无法脱离模拟器驱动状态、并发检查也会因 UI 类型的主线程约束而复杂化。职责上它还打开了「把布局/颜色写进业务层」的口子。评审用 import 列表做硬检查即可拦截。

2. 为什么 MVVM 的单元测试能脱离 UI？协议注入在其中扮演什么角色？

因为决策逻辑（状态机）长在 ViewModel 这个普通 Swift 类型里，而它对外部世界的全部依赖都收敛到 OrderRepositoryProtocol 这类协议上。测试时注入 Stub（7.6）即可精确控制成功/失败/延迟路径，无需网络与界面。协议是「可替换性」的合同，注入是「替换」的动作。

3. TCA 的 Effect 为什么不能直接改 State？

可预测性的根基是「状态的每次变化都由一个确定的 Action 经过 Reducer 产生」。若 Effect 能绕过 Reducer 直改状态，Action 序列就不再完整描述状态历史——回放、审计、测试三个能力同时失效。Effect 只允许返回新 Action，把结果交回独木桥。

4. 深链为什么必须收敛到单一解析入口？冷启动竞态怎么处理？

多入口（链接/推送/快捷指令/Widget）各自解析必然出现规则不一致与重复实现，且黑产伪造 URL 会从最弱的那个入口打进来。单一解析器是纯函数，可全量单测（含负向用例）。冷启动时业务模块未就绪，直接跳转会落空页——路由先入队，模块就绪后再消费，解析失败兜底到首页。

5. 双轨期如何保证 UIKit 页面与 SwiftUI 区块渲染的状态不分裂？

同一个 ViewModel 实例作为唯一事实源：SwiftUI 通过 @Observable 自动追踪；UIKit 通过 withObservationTracking 桥接订阅回调刷新（注意防重入与 deinit 取消）。禁止在任何 UI 层保存业务数据的第二份拷贝——评审红线，出现即打回。
