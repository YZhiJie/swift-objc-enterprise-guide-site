9.2 Swift API Design Guidelines 要点 ​

Apple 官方准则（Swift.org 发布）的核心三原则：

  1. 在使用点清晰（Clarity at the point of use）：API 是给别人调用的，读调用代码的人不看实现也应秒懂。
  2. 简洁但不省略关键信息（Clarity over brevity）：宁可长一点，不能歧义。
  3. 术语一致（Terminology）：同一概念全工程同一个词（fetch/load/get 选一个）。
swift
// File: APIDesign.swift

// ❌ 反例 → ✅ 正例 对照

// 1. 参数标签让调用点读起来像句子
func move(from: Int, to: Int) {}                    // ❌ move(from: 0, to: 5)
func moveItem(from start: Int, to end: Int) {}      // ✅ moveItem(from: 0, to: 5)

// 2. 布尔属性/方法读作断言
var isEmpty: Bool { true }                          // ✅ if list.isEmpty
func isValid() -> Bool { true }                     // ❌ 无副作用的查询应是属性
var isValid: Bool { true }                          // ✅

// 3. 副作用方法用动词，查询用名词/形容词
mutating func sort() {}                             // 原地排序（动词）
func sorted() -> [Int] { [] }                       // 返回新数组（过去分词/非动词）

// 4. 工厂名 vs 转换名
// DateFormatter 的 date(from:)：可能失败返回 Optional —— 清晰表达转换语义

  • ✅ iOS 发布受审核制约，推荐「Trunk-Based 开发 + release 分支冻结」的混合模式：日常直合 main，发版切 release/x.y 做 RC，热修 cherry-pick 回 main。
  • ⚠️ Trunk-Based 的前提：未完成特性必须用 Feature Flag 关闭，否则 main 不可发布沦为口号。

9.6 Code Review 清单 ​

把前八章的坑点固化为评审检查表（企业模板，直接可用）：

通用项 ​

  • [ ] 无强制解包/强转/try!（除非注释说明不变量）
  • [ ] 新增 public API 符合设计准则（9.2），有 DocC 注释
  • [ ] 错误处理走领域错误枚举，无吞错误（空 catch）
  • [ ] 敏感数据无明文日志；日志级别合理

内存与并发重点 ​

  • [ ] 闭包回调 [weak self]（第 2 章）
  • [ ] delegate 属性 weak（第 1、2 章）
  • [ ] Timer/DisplayLink 有失效路径（第 6 章）
  • [ ] 跨并发域数据为 Sendable；UI 更新在 @MainActor（第 2 章）
  • [ ] 无 DispatchQueue.main.sync 死锁风险（第 7 章规则）

混编边界重点 ​

  • [ ] ObjC 头文件 nullability 注解完整（第 4 章）
  • [ ] ObjC .h 未 import -Swift.h（第 4 章）
  • [ ] 暴露 ObjC 的 Swift 成员确有必要，未滥用 @objcMembers
  • [ ] 需 KVO/swizzle 的成员有 @objc dynamic（第 4 章）

性能与工程 ​

  • [ ] 主线程无同步 IO / 大 JSON 解码（第 6 章）

  • [ ] 启动路径未新增初始化任务（第 6 章）

  • [ ] 新依赖有评审记录，SPM 版本已锁定（第 8 章）

  • [ ] 关键逻辑有单元测试，增量覆盖率达标（第 7 章）

  • ✅ 执行技巧：清单挂到 PR 模板（.github/pull_request_template.md），作者自查 + 评审者复核双签。

  • ⚠️ 清单不是越长越好：超过 25 项评审者开始跳过——保留「出过事故的」和「机器查不了的」，能自动化的全部下沉到 lint（9.3）。

9.9 ADR 模板库：把决策留在仓库里 ​

ADR（Architecture Decision Record）解决的不是「怎么设计」，而是「为什么这么设计、谁在什么时候拍的板、以后怎么翻案」。没有 ADR 的团队，同一场争论每半年重来一次。

通用骨架（docs/adr/NNNN-title.md）：

markdown
# ADR-0007：<决策标题>

- 状态：Proposed / Accepted / Superseded / Deprecated
- 日期：YYYY-MM-DD
- 决策者：<角色，不写个人英雄>
- 关联：<Issue / PR / 上级 ADR>

## 背景
<约束、数据、必须解决的问题；只写事实，不写偏好>

## 决策
<一句话结论 + 关键参数/边界>

## 备选方案
| 方案 | 优点 | 代价 | 为什么没选 |

## 后果
<正面、负面、需要配套的动作>

## 回滚条件
<什么信号出现时撤销该决策，怎么撤>

类型 1：技术选型 ​

markdown
# ADR-0012：列表刷新采用 AsyncSequence 而非 Combine

- 状态：Accepted  日期：2026-03-02  决策者：iOS 架构组
- 背景：iOS 17 起全面启用 Swift 6 严格并发；现有 Combine 管道 3 处强引用环，
  且团队 6 人中仅 2 人熟悉 Combine 操作符。
- 决策：新代码统一使用 AsyncSequence / AsyncStream；存量 Combine 按模块逐步替换，
  不设统一 deadline。
- 备选：① 继续 Combine（迁移成本 0，但并发适配成本高）；② RxSwift（引入新依赖，否决）；
  ③ 回调 + 手写状态机（可读性差）。
- 后果：正向——取消传播与 actor 隔离天然一致；负向——iOS 16 以下需保留 Combine 兼容层。
- 回滚条件：若 AsyncStream 在某模块出现可复现的背压问题，该模块回退 Combine 并记录原因。

类型 2：依赖引入 ​

markdown
# ADR-0018：引入 XXLog 作为统一日志 SDK

- 状态：Accepted（试用 2 个版本）  日期：2026-05-11  决策者：基础架构 + 安全
- 背景：现网日志分散在 4 套实现，无法统一脱敏与采样。
- 决策：引入 XXLog 2.x，封装在 LogKit 适配层后业务方可使用；禁止业务直接 import。
- 准入检查：许可证（Apache-2.0）、二进制体积（+1.2MB）、隐私清单完整性、
  最近 12 个月发版频率、是否有 CVE 记录。
- 后果：正向——统一脱敏与采样；负向——多一层适配，SDK 升级需跟随。
- 回滚条件：出现未修复的高危 CVE 或体积增幅超过 3MB，冻结升级并在一个版本内替换。

类型 3：接口变更 ​

markdown
# ADR-0021：PaymentKit 支付结果回调改为 async 接口

- 状态：Accepted  日期：2026-07-08  决策者：PaymentKit owner + 3 个消费方代表
- 背景：旧回调接口在 Swift 6 下需要 @unchecked Sendable 包装，已有 2 起竞态事故。
- 决策：`func pay(_ request: Request) async throws -> Receipt` 作为 v2 主接口；
  v1 回调接口保留 2 个版本，标注 @available(*, deprecated, message: "Use pay(_:) async")。
- 迁移：消费方按「新代码只用 v2、存量按模块排期」迁移；CI 统计 v1 调用点数量，
  每季度下降 30% 视为达标。
- 后果：正向——消除竞态与包装层；负向——调用方需要改造，短期双接口维护。
- 回滚条件：v2 在灰度期错误率高于 v1 的 1.5 倍，暂停迁移并回退默认实现。

类型 4：例外审批 ​

markdown
# ADR-0024：H5 容器模块豁免增量覆盖率门禁（限 1 个季度）

- 状态：Accepted（例外，到期自动失效）  日期：2026-09-01  决策者：技术负责人 + QA 负责人
- 背景：H5 容器依赖 WKWebView，现有测试基建无法稳定断言 JS Bridge；
  强行达标会催生大量无断言用例。
- 决策：该模块本季度增量覆盖率门禁从 80% 降至 40%，但必须满足：
  ① 每条 JS Bridge 有手工验证记录；② 季度末提交测试基建方案；③ 例外到期不自动续期。
- 后果：接受短期门禁缺口，换取测试方案质量。
- 回滚条件：例外期内出现 P1 及以上事故且归因该模块，立即恢复原阈值并冻结需求。

  • ⚠️ 例外审批必须带到期日，否则例外会变成默认值。

9.10 技术债量化：打分、配额与偿还节奏 ​

技术债最大的问题是「人人都知道有，但没人排期」。量化不是精确科学，目的是让排序可争论、可执行。

I = max(用户触达 R, 故障概率 P, 阻塞强度 B, 合规风险 L)   # 各 1–5

季度配额与看板：

  • 每季度预留 20% 工程容量给债务（按人日计），不与其他需求混排；

  • 债务登记表字段：编号、模块、分值、owner、发现日期、计划季度、状态；

  • 每月看「新增债务分」与「关闭债务分」两条曲线——只还不控增，等于白还；

  • 分值 ≥ 15 的债务：当季度必须排期，且需求方无权单方面延期；

  • 分值 ≥ 20 且涉及合规：触发「功能冻结」，直到降级到 15 以下。

  • ✅ 债务分要写「为什么是这个分」，而不是只写数字；

  • ❌ 不要用代码行数/文件数当债务量：与风险和成本都无关；

  • ⚠️ 债务也有「利息」：同一处债务每季度额外消耗的返工工时，应计入分母，否则永远排不上。

9.11 模块 ABI 治理：@frozen、library evolution 与二进制边界 ​

3.9.5 讲了 ABI 的机制；这一节讲团队怎么管。模块一旦以二进制形式交付（XCFramework、SPM binary target、企业内部分发），public API 就从「代码」变成「合同」。

层级承诺允许的变化治理动作
源码依赖（同仓编译）只承诺源码兼容可改布局、改实现语义化版本 + 变更日志
library evolution（BUILD_LIBRARY_FOR_DISTRIBUTION=YES）承诺接口兼容可增删非 @frozen 字段、改实现.swiftinterface 入包 + ABI diff
@frozen 类型承诺布局兼容不能增删字段/ case需架构组审批 + 双人评审
ObjC 兼容层（@objc）消息派发，方法可增删selector 改名 = 破坏保留旧 selector 一个版本

治理规则：

  5. 模块 owner 对 public API 有否决权；跨团队调用不得「先合并再补 ADR」。

  • ❌ 不要用 @_spi 当「内部 API」的万能出口：它仍是 public ABI 的一部分，只是需要 import 声明；
  • ✅ 二进制分发前用旧版本客户端跑集成测试，验证「接口兼容」之外的行为兼容。

9.12 安全评审清单：用渗透测试的视角写 ​

普通安全检查是「有没有开启 ATS」；渗透测试视角是「攻击者会从哪里进来、怎么验证、什么条件才放行」。评审按四步走，缺一步都不算完成。

第一步：威胁建模（STRIDE） ​

威胁在本 App 里的落点典型问题
Spoofing 伪造登录态、Universal Link、推送来源Token 可伪造、deeplink 未校验
Tampering 篡改本地缓存、UserDefaults、请求体客户端信任本地状态
Repudiation 抵赖支付/审批日志关键操作无审计日志
Information 泄露日志、剪贴板、备份、截图手机号明文进日志

Elevation 提权越狱检测、JS BridgeBridge 暴露任意原生能力

第四步：放行条件 ​

  • P0（可直接利用、影响资金/账号/隐私）：0 条，否则禁止发布；

  • P1（需要特定条件但影响大）：0 条，或已有缓解措施 + 安全 owner 书面同意；

  • P2（信息泄露/加固缺失）：允许带 owner 与截止日期放行，下个版本必须关闭；

  • 所有结论附证据（命令输出、截图、复现步骤），不接受「已确认没问题」的口头结论；

  • 评审记录进 ADR 或发布单，和版本号绑定，便于事后追溯。

  • ✅ 安全评审要与威胁建模一起做，先画攻击面再列检查项；

  • ❌ 不要把「越狱检测」当安全边界：它只是提高门槛，真正的敏感逻辑必须在服务端；

  • ⚠️ 任何「为了调试方便」的生产开关（WebView 调试、明文 HTTP、日志全量）都必须在 Release 构建中被编译期排除。

企业级场景分析 ​

场景：50 人 iOS 团队的规范体系演进 ​

某大厂 App 团队三年规范建设复盘：

  1. 第一阶段（工具先行）：SwiftLint + SwiftFormat + git hooks 全量接入，3 个月内消灭格式类评审意见——评审时间从「挑格式」转向「谈设计」。
  2. 第二阶段（清单沉淀）：把全年线上事故回溯为 18 条评审清单（其中「闭包循环引用」「主线程 IO」「nullability 缺失」三条拦截了后续 60% 同类事故苗头）。
  3. 第三阶段（契约化）：8 个业务团队拆为 25 个 SPM 模块，Interface 先行 + SemVer，跨团队阻塞（等别人改代码）下降 70%；配套「接口变更需 ADR」制度。
  4. 第四阶段（文档即代码）：DocC 覆盖率纳入模块健康度看板，新人 onboarding 从「问老员工」变为「读模块文档 + 教程」，上手周期从 3 周缩至 1 周。
  5. 教训：规范建设最大的坑是「一步到位」——第一年试图推 40 条 lint error 被团队抵制，改为「增量新代码严格 + 存量豁免注释 + 季度清理」后顺利落地。

场景：跨端评审会的有效性 ​

多团队共用基础组件时的评审实践：接口 PR 必须由至少一个消费方团队 review 通过（不只用方满意，还要防止「为单一业务设计的接口假装通用」）；组件 owner 维护「决策日志」（为什么这么设计、否决过哪些方案），避免相同争论周期性重演。

小结与自测 ​

要点回顾

  • API 设计：使用点清晰 > 简洁；术语全工程统一。
  • 规范落地：规则集分层继承，新规则走「warning 试运行 → 存量豁免 → error 转正」流程。
  • 工作流：Trunk-Based + Feature Flag 是高频发布主流；release 分支只做冻结与热修。
  • 评审清单聚焦「机器查不了 + 出过事故」；能自动化的下沉 lint。
  • 模块化 = Interface 先行 + SemVer + ADR；文档用 DocC 与代码同仓演进。

自测题

  1. 「清晰性优先于简洁性」在方法命名上如何体现？举例。
  2. 为什么新 lint 规则不能直接以 error 级上线？
  3. Trunk-Based 开发对团队基建提出了哪两个硬性前提？
  4. 为什么评审清单不宜超过约 25 条？
  5. Interface target 与实现 target 分离对编译时间有什么影响？为什么？
参考答案
  1. 命名宁可长不可歧义，且调用点要读得通：list.remove(at: 3)（清晰）优于 list.remove(3)（歧义：是删下标还是删元素 3？）；参数标签承担了语义角色。
  2. 存量代码会瞬间产生大量 error 导致无法编译，团队要么被迫大规模「豁免刷屏」要么抵制规则本身；warning 试运行给存量修复留出时间窗，也让规则误报率暴露后再收紧。
  3. 一是可靠的 CI 门禁（main 任何时刻可发布，靠自动化保障）；二是 Feature Flag 体系（未完成功能对用户隐藏，代码可先合并）。
  4. 清单过长导致评审者认知超载、执行流于打勾形式；企业实践显示 15~25 条是「会被真正执行」的上限，其余检查项必须自动化。
  5. 下游模块只 import Interface：实现变更不改接口签名时，接口模块产物不变，下游无需重编译（SPM/Xcode 基于产物指纹增量构建），大工程全量编译时间显著下降；接口变更才是「昂贵」的，这也反向约束了接口设计需审慎。

精通判据 ​

「会用」＝完成实践任务并对自测题 80%；「精通」＝在无标准答案的生产条件下仍能独立判断。四维定义见 README 教程体例说明。

能复现

  • 对一个真实 API 按 9.2 准则逐条评审并给出改法：如 func move(from: Int, to: Int) → moveItem(from:to:)、func enqueue(_ message: Message) → enqueue(message:)、func isValid() -> Bool → var isValid: Bool，写出改名前后的调用点对比，并让改名后的工程通过 swiftlint lint --strict。
  • 验证模块化接口的增量编译：SPM 本地包拆出 PaymentKitInterface 与 PaymentKit 两个 target，消费方只 import PaymentKitInterface；仅修改 PaymentKit 实现（接口签名不变）后执行 xcodebuild build，在 Build Log 中确认消费方 target 没有新的 CompileSwiftSources 记录，接口一改则下游重新编译。
  • 用 xcrun swift-api-digester -dump-sdk 导出两个版本的 API 摘要，再用 -diagnose-sdk --input-paths 对比，复现「删除一个 public 方法」被抓出；用 9.12 的 codesign -d --entitlements :-、otool -L、nm -u 对 Release 产物跑一遍安全检查清单，每条结论附命令输出。

能解释

  • 解释「使用点清晰优先于简洁」的具体落点：参数标签承担语义（remove(at:) 读得出是删下标）、布尔读作断言（if list.isEmpty）、副作用方法用动词而查询用名词（sort() 与 sorted()）；并说明为什么无副作用的 isValid() 应改为属性。
  • 解释 Interface target 分离为何改善增量编译：下游只依赖接口产物，实现变更不改签名时接口模块产物指纹不变，SPM/Xcode 跳过下游重编译；接口变更才是昂贵操作，因此接口设计需 SemVer 与 ADR 约束。
  • 解释 ADR 与 Issue/PR 的分工：PR 记录「怎么改」，ADR 记录「为什么改、还有哪些备选、什么条件下撤销」；并说明例外审批为什么必须带到期日——没有期限的例外会变成事实上的默认规范。
  • 解释技术债打分为什么用乘法而不是加法：修复成本高且影响面大的债务，优先级应显著高于「成本低但无人受影响」的债务；用 max 聚合影响面，避免多个低分维度把高风险稀释。
  • 解释 @frozen 的治理含义：它不是性能开关，而是「布局 ABI 合同」，一旦发布就不能增删字段/case；library evolution 承诺接口兼容但不承诺布局，两者必须分层管理。

能量化

  • 用 Build Log 统计「修改实现后消费方重编译 target 数 = 0、接口变更后受影响 target 数 = N」两组数字，并记录整包构建耗时（如 12min → 3min）；把该对比作为模块化收益的验收口径，而不是只谈「编译变快」。
  • 规则治理量化：新 lint 规则 warning 试运行 2 周，统计豁免数量趋势与误报率；转 error 后 swiftlint lint --strict 保持 0 warning，评审清单控制在 15~25 条（本章案例 18 条清单中 3 条拦截了 60% 同类事故）。
  • 技术债量化：用 9.10 的公式给登记表每条债务打 C/I/分，统计「本季度新增债务分 / 关闭债务分 / 逾期未修数」三个数字；配额按人日核算（团队 10 人 × 60 工作日 × 20% = 120 人日/季度），拿不出额度就说明配额没落地。
  • ABI 与安全量化：每次二进制发布记录「ABI diff 的破坏性条目数（目标 0）」与「安全评审 P0/P1/P2 数量（P0/P1 目标 0）」，作为放行单的必填字段，而不是口头结论。

能兜底

  • 新规则上线兜底：先 warning 级试运行 2 周，存量用 // swiftlint:disable:next 加理由过渡并季度清理；误报率过高时回退到 warning，避免「一天全红」导致团队抵制或大规模刷豁免。
  • Trunk-Based 落地兜底：未完成特性必须用 Feature Flag 关闭，保证 main 任意时刻可发布；发版切 release/x.y 冻结与热修，热修 cherry-pick 回 main，CI 门禁失败即阻断合并，回滚以关闭 Flag 或回退发布分支为准。
  • 治理例外兜底：ADR 例外必须写到期日并设自动复查（到期未续即失效）；ABI 破坏性变更若已发出，立即切回旧 @frozen 布局并发布补丁版本，同时用旧客户端跑集成测试确认；安全评审的 P2 项必须带 owner 与截止版本，下一版本未关闭则升级为 P1 并阻断发布。
