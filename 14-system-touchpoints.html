第 14 章 系统触点：App 扩展与 WidgetKit 等 ​

图标点开的那个 App 只是体验的一半。锁屏上的库存卡片、Siri 里的一句话盘点、通知横幅里已经解密的消息——这些都是「系统触点」：App 把能力前置到用户所在的场景，而不是等用户来找它。本章覆盖 App 扩展生态的进程模型、WidgetKit 时间线、App Intents 意图系统与通知触点，并给出把这套体系做成「可测内核 + 薄壳工程」的企业级结构。

14.0 学习目标 ​

完成本章后，你将能够：

  1. 说清扩展的进程模型与共享边界，正确使用 App Group、Keychain 共享组与共享 SPM 包；
  2. 用 TimelineProvider + 刷新策略实现 Widget 数据供给，并用刷新预算模型解释「为什么我的 Widget 不更新」；
  3. 定义 AppIntent / AppEntity / AppShortcutsProvider，把同一意图复用到快捷指令、Siri、Spotlight 与交互 Widget；
  4. 实现通知 Service Extension 的解密与富媒体决策链，做到「失败可降级、降级不泄露」；
  5. 把扩展逻辑抽进共享包建立无头可测内核，并按上线检查清单完成发布前自查。

14.1 核心知识点速览 ​

14.2 App 扩展生态全景 ​

14.2.1 扩展的本质：一个 Bundle、多个进程 ​

扩展（Extension）不是 App 里的一个模块，而是塞进 App Bundle 里的独立可执行体：用户触达时由系统拉起独立进程，跑完即回收。它与主 App 没有共享内存，唯一的合法数据通道是 App Group 容器与 Keychain 共享组。

14.2.2 共享三件套：App Group、Keychain 组、共享包 ​

三个进程要协作，先铺三条「管道」。逻辑本身放共享 SPM 包——扩展壳只做胶水：

swift
// File: Sources/SystemTouchpoints/AppGroupStore.swift —— 跨进程共享存储（共享包内，主 App 与扩展同用）

/// 可注入的键值存储协议：生产用 UserDefaults(suiteName:)，测试用内存实现
protocol KeyValueStore: AnyObject {
    func data(forKey key: String) -> Data?
    func set(_ data: Data?, forKey key: String)
}

/// 共享快照：主 App 写、扩展读的唯一数据契约
/// ⚠️ schema 必须带版本号——扩展进程可能是旧二进制，读到新字段不能崩
struct SharedSnapshot: Codable, Equatable {
    var schemaVersion: Int
    var generatedAt: Date
    var items: [StockItem]
}

struct StockItem: Codable, Equatable {
    var sku: String
    var name: String
    var onHand: Int
}

final class AppGroupStore {
    // ⚠️ 真实工程中该值来自 entitlements 的 App Group 配置，两端必须一字不差
    static let suiteName = "group.com.enterprise.retailops"

    private let store: KeyValueStore
    private let key = "shared.snapshot.v2"

    init(store: KeyValueStore) { self.store = store }

    func save(_ items: [StockItem], now: Date) throws {
        let snapshot = SharedSnapshot(schemaVersion: 2, generatedAt: now, items: items)
        // ⚠️ suiteName 的 UserDefaults 不随 standard 注册，也不会发跨进程通知——
        //    另一端要么轮询、要么靠 Darwin 通知「敲一下门」（见 14.2.3）
        let encoder = JSONEncoder()
        encoder.dateEncodingStrategy = .iso8601
        store.set(try encoder.encode(snapshot), forKey: key)
    }

    /// 读取并做「新鲜度分级」：Widget 收到的不是布尔值，而是三档可用性
    func load(now: Date, maxAge: TimeInterval) -> SnapshotOutcome {
        guard let raw = store.data(forKey: key) else { return .unavailable }
        let decoder = JSONDecoder()
        decoder.dateDecodingStrategy = .iso8601
        guard let snapshot = try? decoder.decode(SharedSnapshot.self, from: raw) else {
            return .unavailable        // 解码失败按不可用处理，扩展壳绝不裸崩
        }
        let age = now.timeIntervalSince(snapshot.generatedAt)
        if age <= maxAge { return .fresh(snapshot) }
        if age <= 7 * 24 * 3600 { return .stale(snapshot) }   // 过期但可用：显示 + 提示刷新
        return .unavailable                                    // 太旧：宁可显示占位符
    }
}

/// 三档可用性：UI 层按档位选展示策略，而不是拿 nil 自己猜
enum SnapshotOutcome: Equatable {
    case fresh(SharedSnapshot)
    case stale(SharedSnapshot)
    case unavailable
}

14.2.3 跨进程变更感知：写完数据还要「敲门」 ​

App Group 数据写入后，另一端不会收到任何通知——UserDefaults(suiteName:) 不发通知、KVO 只在同进程有效。标准做法是 Darwin 通知（CFNotificationCenterGetDarwinNotifyCenter）：它不携带载荷、只作信号，接收端收到后重新读一次 App Group。

swift
// File: Sources/SystemTouchpoints/CrossProcessPing.swift —— 跨进程「敲门」信号

import CoreFoundation

enum CrossProcessPing {
    // ⚠️ Darwin 通知名是全局命名空间，必须带完整前缀防撞车
    static let snapshotChanged = CFNotificationName("com.enterprise.retailops.snapshotChanged" as CFString)

    static func post() {
        let center = CFNotificationCenterGetDarwinNotifyCenter()
        CFNotificationCenterPostNotification(center, snapshotChanged, nil, nil, true)
    }

    static func observe(_ callback: @escaping () -> Void) {
        let center = CFNotificationCenterGetDarwinNotifyCenter()
        // 回调在 C 层无法捕获 Swift 上下文，惯例是借全局指针转回 Swift 闭包
        // （完整实现属工程模板范畴，正文聚焦机制：只发信号、不传数据）
    }
}

14.3 WidgetKit：时间线、刷新与交互 ​

14.3.1 心智模型：预渲染快照，不是常驻视图 ​

WidgetKit 最大的认知转变：你声明的不是「每秒在跑的视图」，而是「未来一段时间每刻长什么样」。系统按时间线（Timeline）逐刻预渲染成快照缓存，用户看到的是画面；数据陈旧时靠刷新策略排下一班。理解了这一点，「Widget 为什么不更新」「为什么我的网络请求没发出去」这类问题就有了统一答案。

14.3.2 刷新策略：一张决策表管住预算 ​

刷新预算是稀缺资源：系统按 Widget 可见性与用户打开主 App 的频率动态分配，每天大致几十次（不同系统版本与使用习惯有差异）。策略写错有两种翻车方式——数据陈旧（该刷不刷）与预算提前耗尽（后面全天都不刷）。所以刷新策略必须是集中决策的纯函数，不允许每个 Widget 自行 if-else：

swift
// File: Sources/SystemTouchpoints/TimelinePolicy.swift —— 刷新策略决策（14.3.2）
//
// 设计决策：
//   1. 输出用镜像枚举 ReloadDecision 对应 WidgetKit 的 .atEnd / .after / .never——
//      策略是纯逻辑，真正消费它的 Timeline(entries:policy:) 在 Xcode 扩展壳里组装；
//   2. 规则按优先级排列（rare → 预算见底 → 业务节拍 → 兜底），
//      表驱动测试穷举每种事实组合，路由错一条就是预算事故。

/// 用户打开主 App 的频率：决定「把刷新预算花在 Widget 上」还是「留给 App 打开时」
enum EngagementLevel: Equatable, Sendable {
    case daily      // 高频用户：Widget 是常看面板
    case weekly     // 中频
    case rare       // 低频：打开 App 时主动 reload 更划算
}

/// 对应 WidgetKit 的 TimelineReloadPolicy
enum ReloadDecision: Equatable, Sendable {
    case atEnd              // .atEnd：时间线跑完再刷新
    case after(Date)        // .after(date)：指定时刻刷新
    case never              // .never：等 App 打开时 WidgetCenter.reloadTimelines
}

enum TimelinePolicy {

    /// 纯函数：同输入必同输出（全量决策表见 GuideTests）
    /// ⚠️ now 由调用方注入——决策不能隐式依赖系统时钟，否则无法确定性测试
    static func reload(
        now: Date,
        nextNaturalUpdate: Date?,     // 业务节拍（如门店补货后 5:05）
        engagement: EngagementLevel,
        budgetRemaining: Int,         // 粗估的当日剩余刷新次数
        entriesAfterShown: Int        // 当前时间线还剩几个 entry
    ) -> ReloadDecision {
        // 1. 低频用户：别跟系统抢预算，打开 App 时主动刷新
        if engagement == .rare { return .never }
        // 2. 预算见底：只随时间线尾部刷新，不再额外预支「指定时刻」
        if budgetRemaining <= 2 { return .atEnd }
        // 3. 有业务节拍：跟着节拍走（数据什么时候有意义，什么时候刷）
        if let next = nextNaturalUpdate { return .after(next) }
        // 4. 时间线只剩最后一刻：到尾部再续
        if entriesAfterShown <= 1 { return .atEnd }
        // 5. 兜底：6 小时后无理由重排一次，防长期陈旧
        return .after(now.addingTimeInterval(6 * 3600))
    }
}

14.3.3 刷新预算的正确打开方式：主动 reload > 被动等系统 ​

预算机制下最有效的手段是在 App 打开与后台任务完成时主动触发：WidgetCenter.shared.reloadTimelines(ofKind: "InventoryWidget")。这不是立刻渲染（系统仍按预算排队），而是把你的 Widget 标记为「有新数据可取」，提升下一次分配的优先级。

✅ 推荐：主 App 进入前台拉一次最新数据后 reload；后台任务（BGAppRefreshTask）写完 App Group 后 reload + Darwin 通知双保险。❌ 反例：在 Widget 扩展里发起同步网络请求赌一个刷新窗口——网络慢一秒，预算被白吃一次，用户看到的是转圈占位符。

14.3.4 深链：Widget 的每一次露脸都该有去处 ​

点击 Widget 默认打开主 App；widgetURL(_:) 让整卡跳一个目的地，卡内的 Link 可以分区域跳多个目的地。深链 URL 的构建与解析必须走同一套纯函数，做往返一致 + 非法输入拒绝：

examples/Sources/SystemTouchpoints/WidgetDeepLink.swift本地运行：swift run SystemTouchpoints
swift
// File: Sources/SystemTouchpoints/WidgetDeepLink.swift —— 深链构建与解析（14.3.4）
// 对应 14-system-touchpoints.md
//
// 设计决策：
//   1. scheme/host/参数全部集中在这一个文件——评审时「深链改版」只改一处；
//   2. route(for:) 是 url(for:) 的逆运算，二者以参数化单测保证往返一致；
//   3. 非法输入（错 scheme、缺参数、未知 host）一律返回 nil，由调用方决定降级页面。

import Foundation

enum WidgetRoute: Equatable, Sendable {
    case inventory(sku: String)     // 商品库存详情
    case checkIn(taskID: String)    // 盘点任务签到
    case report(day: String)        // 当日经营报表
}

enum WidgetDeepLink {
    static let scheme = "retailops"   // 主 App 的 URL Scheme（Info.plist 注册）

    /// 构建：URLComponents 自动做百分号编码（中文 SKU「杯·大」不会被截断）
    static func url(for route: WidgetRoute) -> URL? {
        var comps = URLComponents()
        comps.scheme = scheme
        switch route {
        case .inventory(let sku):
            comps.host = "inventory"
            comps.queryItems = [URLQueryItem(name: "sku", value: sku)]
        case .checkIn(let taskID):
            comps.host = "checkin"
            comps.queryItems = [URLQueryItem(name: "task", value: taskID)]
        case .report(let day):
            comps.host = "report"
            comps.queryItems = [URLQueryItem(name: "day", value: day)]
        }
        // scheme 与 host 均已设置，url 实际不会为 nil；防御性返回可选
        return comps.url
    }

    /// 解析：主 App 的 onOpenURL 入口把 URL 还原成路由，非法输入拒绝
    static func route(for url: URL) -> WidgetRoute? {
        guard let comps = URLComponents(url: url, resolvingAgainstBaseURL: false),
              comps.scheme == scheme,
              let host = comps.host else { return nil }
        // 取参助手：只认第一个同名参数，缺失返回 nil
        let value: (String) -> String? = { name in
            comps.queryItems?.first(where: { $0.name == name })?.value
        }

        switch host {
        case "inventory":
            guard let sku = value("sku"), !sku.isEmpty else { return nil }
            return .inventory(sku: sku)
        case "checkin":
            guard let taskID = value("task"), !taskID.isEmpty else { return nil }
            return .checkIn(taskID: taskID)
        case "report":
            guard let day = value("day"), !day.isEmpty else { return nil }
            return .report(day: day)
        default:
            return nil
        }
    }
}

14.3.5 多尺寸与锁屏：同一份 Provider，多套族 ​

supportedFamilies 声明支持的尺寸族：桌面 .systemSmall/Medium/Large，锁屏 .accessoryInline/Circular/Rectangular/Corner（iOS 16+）。iOS 17 起 Widget 必须 提供 containerBackground(for: .widget) 才能在待机（StandBy）模式下正确绘制。企业做法：小尺寸只放「一个数字 + 一个动作」，中尺寸放趋势，大尺寸放 Top 列表——同一份快照数据，按族裁剪视图。

14.4 App Intents：一处定义、多处触达 ​

14.4.1 三个核心角色 ​

App Intents（iOS 16+ / macOS 13+）用纯 Swift 定义能力：AppIntent 是动作，AppEntity 是动作的对象，AppShortcutsProvider 把动作注册成可被 Siri / 快捷指令 / Spotlight / 交互 Widget 调用的短语。一次定义，全系统触达——这是它相对旧 SiriKit 最大的工程价值。

swift
// File: Sources/SystemTouchpoints/CheckStockIntent.swift —— 真实 AppIntent（14.4.1）

14.4.2 参数与实体：让系统理解「对象」 ​

AppEntity 让用户以「对象」为单位下达指令（「查 经典白T 的库存」），实体查询把自然语言串匹配成实体。匹配打分必须纯函数化——顺序可预测才有可测试性：

swift
// File: Sources/SystemTouchpoints/EntityScorer.swift —— 实体查询打分（14.4.2）

import AppIntents

struct InventoryItem: AppEntity, Equatable, Sendable {
    static let typeDisplayRepresentation = TypeDisplayRepresentation(name: "库存商品")
    static let defaultQuery = InventoryQuery()

    var id: String      // SKU
    var name: String

    var displayRepresentation: DisplayRepresentation {
        DisplayRepresentation(title: "\(name)", subtitle: "\(id)")
    }
}

/// 打分器：精确 SKU > 名称前缀 > 名称包含；同分按 SKU 排序保证确定性
enum EntityScorer {
    static func rank(matching term: String, in catalog: [InventoryItem]) -> [InventoryItem] {
        let t = term.lowercased()
        guard !t.isEmpty else { return [] }
        return catalog
            .map { item -> (InventoryItem, Int) in
                let id = item.id.lowercased(), name = item.name.lowercased()
                var score = 0
                if id == t { score = 3 }                 // 精确 SKU
                else if name.hasPrefix(t) { score = 2 }  // 名称前缀
                else if name.contains(t) || id.contains(t) { score = 1 }
                return (item, score)
            }
            .filter { $0.1 > 0 }
            .sorted { lhs, rhs in
                lhs.1 != rhs.1 ? lhs.1 > rhs.1 : lhs.0.id < rhs.0.id
            }
            .map(\.0)
    }
}

/// EntityStringQuery：把打分器接入 App Intents 协议
struct InventoryQuery: EntityStringQuery {
    // 演示目录：真实工程从 App Group 快照读取（共享包同一数据源）
    var catalog: [InventoryItem] = InventoryQuery.seedCatalog

    static let seedCatalog = [
        InventoryItem(id: "A-1001", name: "经典白T"),
        InventoryItem(id: "A-1002", name: "经典黑T"),
        InventoryItem(id: "B-2001", name: "保暖卫衣"),
        InventoryItem(id: "B-2002", name: "保龄球包"),
        InventoryItem(id: "C-3001", name: "直筒牛仔裤"),
    ]

    func entities(for identifiers: [String]) async throws -> [InventoryItem] {
        catalog.filter { identifiers.contains($0.id) }
    }

    func entities(matching string: String) async throws -> [InventoryItem] {
        EntityScorer.rank(matching: string, in: catalog)
    }
}

14.4.3 执行上下文：perform 在哪里跑、多久必须结束 ​

perform() 的运行位置由使用场景决定：交互 Widget 里在扩展进程执行（内存受限、跑完即回收）；快捷指令/Siri 默认可在后台执行，若 openAppWhenRun = true 则拉起主 App。共性约束是运行时长有限——秒级任务在扩展里完成，分钟级任务必须移交主 App 并用深链回跳展示结果。

场景进程时限设计要点
交互 Widget 按钮Widget 扩展秒级只做写操作 + 回执；刷新交给 WidgetCenter
快捷指令（openAppWhenRun=false）后台拉起受限结果用 ProvidesDialog 回给系统
快捷指令（openAppWhenRun=true）主 App常规复杂流程 + UI 确认
Spotlight / Siri 实体查询主 App受限查询打分纯函数化，禁止重 IO

❌ 反例：在 perform() 里同步上传图片、跑同步网络请求。意图进程随时可能被系统回收，结果是「快捷指令偶尔成功偶尔静默失败」——这类偶发在客服工单里几乎无法归因。正确姿势：写操作落 App Group / 本地队列，由主 App 的后台任务补完，回执只承诺「已受理」。

14.5 通知触点：Service 与 Content 扩展 ​

14.5.1 Service Extension：展示前的最后一步加工 ​

推送负载带 "mutable-content": 1 时，系统在展示前拉起 Notification Service Extension，给你一次解密、改文案、下附件的机会。IM 端到端加密、金融敏感通知的「脱敏展示」都靠它。两个铁律：时限内必须调 contentHandler（超时/崩溃则原始内容照发）；原始 payload 不要落日志（合规红线）。

swift
// File: Sources/SystemTouchpoints/NotificationEnvelope.swift —— 通知加工决策（14.5.1/14.5.2）
//
// 设计决策：Service Extension 壳只做「取 payload → 套决策 → 回填 content」三步，
// 全部分支都是这里的纯函数——超时前必须完成的代码，越薄越安全。

import Foundation

/// 推送信封：APNs 只透传密文与密钥索引，明文永不经过苹果服务器
struct PushEnvelope: Codable, Equatable, Sendable {
    var keyID: String
    var ciphertext: String        // Base64
    var attachmentMIME: String?
    var attachmentBytes: Int?
}

enum PayloadSource: String, Sendable { case decrypted, fallback }

enum NotificationEnvelope {

    /// 解密降级：成功用明文；任何失败都退回脱敏文案
    /// ⚠️ fallback 文案不得包含密文、错误详情——通知在锁屏可见，等于公示
    static func resolve(
        decrypt: () throws -> String,
        fallbackTitle: String
    ) -> (text: String, source: PayloadSource) {
        do {
            let plain = try decrypt()
            return (plain.isEmpty ? fallbackTitle : plain, .decrypted)
        } catch {
            return (fallbackTitle, .fallback)
        }
    }

    /// 附件决策表：类型 → 大小 → 网络计费状态，逐关放行
    static let allowedMIME: Set<String> = ["image/jpeg", "image/png", "video/mp4"]
    static let maxBytes = 10 * 1024 * 1024        // 硬上限 10MB
    static let meteredMaxBytes = 1024 * 1024      // 计费网络只收 ≤1MB

    static func attachmentDecision(
        mime: String?, sizeBytes: Int?, isMetered: Bool
    ) -> AttachmentDecision {
        guard let mime, allowedMIME.contains(mime),
              let sizeBytes else { return .skip(.unsupported) }
        guard sizeBytes <= maxBytes else { return .skip(.tooLarge) }
        if isMetered && sizeBytes > meteredMaxBytes { return .skip(.metered) }
        return .download
    }
}

enum AttachmentDecision: Equatable, Sendable {
    case download
    case skip(SkipCause)
}

enum SkipCause: String, Equatable, Sendable {
    case unsupported   // 类型不在白名单
    case tooLarge      // 超 10MB 硬上限
    case metered       // 计费网络下的大文件
}

14.5.2 壳的组装与降级语义 ​

扩展壳把决策套进系统回调：解密走 resolve，附件走 attachmentDecision 后用 UNNotificationAttachment.save 挂载。降级语义要在产品层讲清楚：兜底文案是产品承诺（「您收到一条新消息，打开 App 查看」），而不是报错信息——用户不关心解密失败的原因，只关心有没有消息。

决策结果用户体验
解密成功明文标题/正文正常阅读
密钥缺失 / 解密失败脱敏兜底文案「新消息」+ 打开 App
附件白名单外 / 超限仅文本图文降级为纯文本
扩展超时/崩溃系统投递原始内容密文（IM 场景不可接受 → 见下方坑点）

⚠️ 坑点（IM/金融必读）：如果解密失败率不可接受，宁可让服务端把这类通知改为「空文案 + silent」并在 App 内红点提示，也不要让密文出现在锁屏。扩展超时时系统投递的是原始 payload——这是通知链路上唯一一处「降级权不在你手里」的环节，必须在产品评审时给出预案。

14.6 Share/Action 扩展与硬约束 ​

14.6.1 Share 扩展最小实现 ​

Share 扩展承接其他 App 的分享内容：Info.plist 的 NSExtensionActivationRule 声明收什么（如「最多 10 张图片」），实现里通过 NSExtensionContext 取输入、completeRequest(returningItems:) 结束。企业场景常用于「转发到工单 / 网盘 / 审批流」。UI 可用 UIViewController（SwiftUI 经 UIHostingController 包装）。

14.6.2 扩展进程的硬约束清单 ​

约束事实工程对策
内存上限扩展进程内存以十 MB 计，超限被系统静默杀掉大图先降采样；避免整包 JSON 反序列化
运行时长拉起后跑完即回收，无常驻态秒级任务就地做；长任务移交主 App
后台 URLSession❌ 扩展内不可用大文件：现场直传小文件；大文件落 App Group 由主 App 后台传
二进集体量每个扩展都打进 App Bundle共享包一份、壳零业务逻辑
与主 App 通信无直连通道App Group + Darwin 通知（14.2.3）

⚠️ 坑点：「Share 扩展偶发上传失败」的经典根因就是后台 URLSession——扩展里创建 URLSession(configuration: .background) 直接抛异常。现场直传受运行时长约束，大文件的稳妥方案是「扩展把文件移进 App Group 容器 + post 通知，主 App 后台任务接力上传」。

14.7 企业级场景分析 ​

14.7.1 零售连锁：锁屏库存 Widget + 盘点快捷指令 ​

场景：连锁门店 800 家，店长每天开闭店各查一次到货与缺货。目标：锁屏一瞥见「今日到货 3 单 / 缺货 Top3」，语音一句「确认盘点」完成记录。

方案：

触点实现关键决策
锁屏 Widget（accessoryRectangular）主 App 每日 5:00 后台任务生成快照写 App Group → reload刷新策略走 14.3.2 决策表：补货节拍 after(5:05)，店长低频时段 never
桌面中尺寸 Widget快照 + 缺货 Top3 列表，每行一个 Link深链 retailops://inventory?sku=… 往返一致有单测
盘点快捷指令CheckStockIntent（openAppWhenRun=false）+ ProvidesDialog 回执perform 只写 Ledger；「已受理」承诺，后台补对账
数据契约SharedSnapshot v2 + 版本迁移旧版 App 的扩展读到 v2 字段不崩（迁移测试锁定）

结果：闭店盘点从「开机开 App 扫码」的 8 分钟压到「锁屏确认」的 40 秒；Widget 日活渗透率 31% 成为店长端最高频入口。关键经验：Widget 的价值不在炫技，而在「把最频繁的 3 秒决策搬进锁屏」——先用埋点确认高频动作，再决定哪个动作值得占据一个触点。

14.7.2 IM/金融：端到端加密通知的解密链路 ​

场景：企业 IM 的消息通知要求端到端加密：APNs 透传的只有密文信封，密钥经 Keychain 共享组分发给主 App 与通知扩展。合规要求：锁屏不能出现密文，解密失败不能泄露原因。

方案：Service Extension 收到 mutable-content 信封后——① 从 Keychain 共享组按 keyID 取会话密钥；② resolve(decrypt:fallbackTitle:) 解密，失败退「您收到一条新消息」；③ 附件走 attachmentDecision 决策表（计费网络拒收大图）；④ 全程不落明文日志。降级预案：解密失败率超阈值（监控见第 15 章）时，服务端将该类消息改为空文案通知 + App 内红点。

结果：锁屏零密文泄露；解密失败率稳定在 0.02% 以下（旧版密钥轮换窗口期问题，靠 keyID 多代并存解决）。关键经验：通知链路的合规设计要按「最坏路径」审——扩展超时后系统投递原始 payload，这个降级权不在你手里，所以「宁可空文案不可泄密文」必须是服务端与客户端的共同预案。

小结与自测 ​

要点回顾：

  1. 扩展是独立进程：短生命周期、内存受限、与主 App 无共享内存；App Group 与 Keychain 共享组是仅有的合法数据通道，跨进程变更要靠 Darwin 通知敲门；
  2. Widget 是预渲染快照 + 刷新时间表：刷新策略必须集中为纯函数决策表（never → 预算见底 → 业务节拍 → atEnd → 兜底），打开 App 与后台任务完成后主动 reload 才是预算的正确花法；
  3. 深链构建与解析是同一纯函数的往返，非法输入一律拒绝；占位符阶段严禁真实数据；
  4. App Intents 一处定义多处触达：perform 只做薄胶水（秒级写操作 + 回执），实体查询打分纯函数化保证可测试；长任务移交主 App 并深链回跳；
  5. Service Extension 是展示前最后的加工点：解密与附件全走决策表，超时/崩溃系统会投递原始 payload——「宁可空文案不可泄密文」必须是端到端共同预案；
  6. Share 扩展禁用后台 URLSession：大文件移交 App Group 由主 App 接力；逻辑下沉共享包，扩展壳薄到没有 if，决策层在 GuideTests 无头可测。

自测题（先自答再回看正文）：

1. 为什么 Widget 数据陈旧时，第一反应不应是「在扩展里加个网络请求」？

Widget 的刷新由时间线与系统预算驱动，不是常驻视图：扩展进程按预算被拉起，跑完即回收。在扩展里发同步网络请求，慢一秒就白吃一次预算，还可能被系统在渲染前杀掉。正确路径：主 App 打开或后台任务完成后写 App Group 快照，再 WidgetCenter.reloadTimelines 标记「有新数据」；扩展被拉起时只读本地快照生成时间线。

2. 刷新策略决策表里，为什么 rare（低频用户）排在预算规则之前？

低频用户几乎不看 Widget，为其保留刷新预算是纯浪费，还挤占该用户其他 Widget 的配额；其数据新鲜度由「打开 App 时 WidgetCenter.reloadTimelines」承担。这是「预算跟着注意力走」的原则：决策表按优先级短路，第一条命中即返回，保证同一输入永远同一输出。

3. AppIntent 的 perform() 里可以直接上传文件吗？为什么？正确的架构是什么？

不可以。perform 运行在受限进程（交互 Widget 在扩展进程、快捷指令可后台拉起），运行时长与内存都受限，进程随时可能被回收——偶发静默失败且无法归因。正确架构：perform 只做秒级写操作（落 App Group / 本地队列）并回执「已受理」；耗时上传由主 App 后台任务接力，完成后深链回跳展示结果。

4. 通知 Service Extension 超时会发生什么？这对合规设计意味着什么？

系统直接投递原始 payload——如果 payload 是密文，锁屏会出现密文；如果原 payload 含敏感字段，会原样公示。这是通知链路唯一「降级权不在客户端手里」的环节，所以合规设计必须按最坏路径：要么密文信封 + 脱敏兜底文案的降级可接受，要么服务端预案把该类消息改为空文案通知 + App 内提示，绝不能假设「扩展总能来得及」。

5. App Group 写入后，为什么另一端收不到通知？怎么补？

UserDefaults(suiteName:) 的写入不产生跨进程通知，KVO 也只在本进程内有效；两个进程各自持有各自的缓存视图。标准做法是 Darwin 通知（CFNotificationCenterGetDarwinNotifyCenter）post 一个无载荷信号，接收端收到后主动重读 App Group——「信号与数据分离」：Darwin 通知只敲门，数据永远从共享容器读，避免通知本身成为第二个数据通道。
