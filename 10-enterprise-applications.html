第 10 章 Swift/Objective-C 企业级应用场景与实施 ​

前九章解决「怎么写」，本章解决「怎么在企业里赢」。一个 App 在企业环境中是否成功，不只看代码质量，还取决于它能否承载行业业务诉求、融入既有 IT 生态、满足监管合规，并以可度量的方式持续演进。本章把 Swift/Objective-C 技术能力映射到金融、零售、医疗、制造、航空等真实行业，给出架构、性能、安全、集成的完整落地方案与评估方法。

说明：本章案例均采用匿名化描述（以行业 + 规模指代），指标与方案要点来自公开技术实践的综合归纳，不对应任何单一企业的机密信息。

10.0 学习目标 ​

完成本章后，你将能够：

  1. 分析目标行业的业务特征对移动端架构提出的约束（金融合规、门店离线、医疗隐私等）；
  2. 设计企业级 iOS/macOS 应用的分层模块化架构与离线优先数据方案；
  3. 建立面向企业场景的性能指标体系并落地优化手段（启动、弱网、电量、内存）；
  4. 将等保 2.0、个保法、GDPR、HIPAA、PCI DSS 等合规要求转化为具体技术控制；
  5. 制定 SSO、MDM、企业网关、遗留系统与硬件外设的集成方案；
  6. 使用成熟度矩阵、KPI 与风险登记表评估实施效果，并输出分阶段落地路线图；
  7. 落地企业数据治理（主数据、留存与擦除策略）与端侧 AI 的企业治理（授权级别、RACI、供应商尽调）；
  8. 设计业务连续性/灾备方案，并用 TCO 模型量化移动端投入产出、以无障碍标准覆盖全部用户。

10.3 行业应用场景分析 ​

10.3.1 金融：手机银行与证券交易 ​

业务特征：交易类操作零容错；监管对身份核验、数据传输、日志留痕有硬性要求；用户规模大且设备碎片化；黑产攻击（撞库、截屏钓鱼、重打包）活跃。

技术诉求与方案：

诉求落地方案
强身份核验LocalAuthentication 生物认证 + 服务端交易密码双因子；敏感操作二次核验
防抓包防篡改SSL Pinning（证书绑定）、App 完整性校验、越狱检测与运行环境风险评分（RASP）
资金安全关键流程全程服务端对账；客户端不做余额等可信计算；交易报文签名
合规留痕操作日志结构化上报，日志留存周期满足监管（通常 ≥ 6 个月）
高可用行情/资讯走长连接（见第 5 章 WebSocket），交易链路断线重连与幂等保护

⚠️ 坑点（证券类真实事故模式）：行情长连接在地铁/电梯等弱网下频繁重连，若重连不做指数退避，会在大型行情波动时形成「重连风暴」反向打爆接入层。务必按第 2 章的 full-jitter 退避策略实现。

典型合规框架：网络安全等级保护 2.0（三级为手机银行常见定级）、人民银行与银保监相关移动金融应用规范、PCI DSS（涉及卡号处理时）。

10.3.2 零售与连锁：一线门店作业 App ​

业务特征：店员用 iPad/iPhone 完成收银、盘库、补货、价签管理；门店 Wi-Fi 质量参差，高峰期（促销、开店）断网是常态；设备由企业持有、店员轮班共用；培训成本要极低。

技术诉求与方案：

诉求落地方案
断网可作业离线优先：商品/库存数据预下载，本地队列暂存交易，联网后同步
数据冲突处理以服务端为权威 + 业务规则合并（如盘点以最后审核人为准）；冲突 UI 显式提示
共用设备当班登录/下班自动登出；本地数据按租户隔离并在登出时安全擦除
外设集成蓝牙扫码枪、便携打印机、支付终端（CoreBluetooth / MFi 协议）
受控分发Apple Business Manager（ABM）购买 App，经 MDM 静默推送到门店设备

// File: OfflineQueue.swift —— 门店离线交易队列的核心抽象

/// 离线操作的状态机：本地暂存 → 同步中 → 成功 / 需人工处理
enum SyncState: String, Codable {
    case queued       // 已落本地库，等待联网
    case syncing
    case succeeded
    case conflict     // 服务端返回冲突，转人工
    case failed       // 超过最大重试次数
}

/// 离线队列协议：任何可离线执行的业务操作都实现它
protocol OfflineOperation: Codable {
    var id: UUID { get }
    var createdAt: Date { get }
    /// 幂等键：同一操作重复同步不会产生两笔交易（服务端据此去重）
    var idempotencyKey: String { get }
    func execute(using gateway: EnterpriseGateway) async throws
}

@MainActor
final class OfflineQueueStore {
    private(set) var operations: [SyncState] = []

    /// 同步策略：网络恢复触发 + 定时兜底；严格串行，保证「先盘库后补货」类顺序语义
    func flush() async {
        for index in operations.indices where operations[index] == .queued {
            operations[index] = .syncing
            do {
                // 实际实现从本地库取出对应 OfflineOperation 执行
                try await execute(at: index)
                operations[index] = .succeeded
            } catch GatewayError.conflict {
                operations[index] = .conflict   // ✅ 不静默覆盖，转门店主管处理
            } catch {
                operations[index] = .queued     // 退避后下轮重试
            }
        }
    }
}

10.3.3 医疗健康：患者端与医护移动工作站 ​

业务特征：患者端涉及预约、报告查询、健康数据；医护端（iPad）用于查房、医嘱、护理记录。两类 App 均受严格隐私监管，且医护端常部署在院内专网，外网不可达。

维度患者端医护工作站
身份实名注册 + 人脸识别核身工号 + 院内 SSO，班次会话超时自动锁定
网络公网 HTTPS院内专网 / 加密隧道，部分场景纯内网
合规个保法（敏感个人信息）、HIPAA（出海/外资医院）同左 + 电子病历相关规范、操作全程留痕
数据健康数据本地加密存储患者数据禁止落盘或仅加密缓存，登出即清
设备用户自有医院资产，MDM 强制密码、禁止拍照截屏（屏录）、功能限制

✅ 推荐：健康类数据（HealthKit）由系统级框架托管，授权粒度细且存储隔离，优先复用而非自建健康数据库；读取最小必要字段，并在隐私清单中申报。

10.3.4 智能制造：工业现场与设备巡检 ​

业务特征：工厂车间用 iPhone/iPad 做设备点检、工单报工、质量检验；环境噪声大、需戴手套操作（UI 要大按钮、支持外接键盘/扫码枪）；与 MES、SCADA、ERP 系统集成；部分场景需连接工业传感器。

  • 离线：车间地下室/屏蔽房无信号，工单全流程必须可离线，回办公室后批量同步；
  • 外设：通过 BLE/USB（MFi）连接温振传感器、RFID 读取器；条码/二维码是最通用的数据载体；
  • 安全：图纸/工艺参数属于商业秘密，需 DLP（防泄露）：禁止 AirDrop、截屏、第三方分享，可经 MDM 配置限制；
  • 架构提示：复杂表单（检验项数百条）优先用 UIKit 手动管理 cell 复用或 SwiftUI List 配合惰性加载，避免全量渲染卡顿。

10.3.5 航空与物流：机组、司机与现场作业 ​

业务特征：飞行员/乘务组的电子飞行包（EFB）、司机配送 App 都在「长时间离线 + 窗口期批量同步」模式下工作——起飞前下载航图/航线手册，落地后回传飞行报告；司机出发前下载配送单，途中扫描操作，收车后上传。

场景关键技术点
大文件预下载（航图可达数百 MB）后台 URLSession 断点续传、按机场区域增量包、文件完整性校验（哈希）
机上离线全量本地可用；CoreData/SwiftData + 只读资源包（可随 App 或按需下载）
签收凭证手写签名（Core Graphics / PencilKit）、拍照，离线暂存后上传
定位与电量显著位置变更（Significant-Change）而非持续高精度定位，控制耗电
双端一致同一份业务逻辑在 iOS 调度端与 macOS 调度大屏复用（共享 SPM 模块）

分层落地原则：

  1. 领域模型零依赖：struct User、enum OrderState 等纯值类型不 import 任何基础设施模块，保证业务规则可独立单测（见第 7 章）；
  2. 面向协议编程：业务模块依赖 PaymentServicing 协议，App 壳在启动时注入真实/模拟实现，模块编译时不互相引用；
  3. 资源与代码同模块：每个 feature 模块自带资源（xib/xcassets/字符串），通过 SPM 的 resources 声明，删模块时无残留；
  4. 模块边界即团队边界：模块数量应匹配团队结构（康威定律），2~5 人的 feature 团队对应 1~3 个模块最常见。

⚠️ 坑点：过度拆分（10 人团队拆出 40 个包）会让 Xcode 索引、编译与版本治理成本爆炸。模块拆分以「不同团队需要独立发布」或「需要强制隔离」为门槛，单纯代码组织用目录即可。

10.4.2 离线优先与数据一致性 ​

离线不是「加个缓存」，而是数据架构的默认假设。决策要点：

问题选项建议
哪些数据离线可用全量 / 按区域或岗位裁剪只下载用户职责内的数据（医疗、金融尤其注意最小化）
本地存储形态SwiftData / CoreData / SQLite复杂关系与迁移用 CoreData/SQLite；iOS 17 新项目轻量场景可 SwiftData
冲突解决最后写入胜 / 服务端权威 / 字段级合并 / 人工交易类一律服务端权威 + 幂等；草稿类可字段合并
敏感数据普通库 / 加密数据库 / 不落盘金融医疗按合规加密，密钥存 Keychain（见 10.6.3）

10.4.3 BFF 与多端协作 ​

企业后端通常是数十个微服务，App 直连会导致请求数膨胀、版本耦合。**BFF（Backend for Frontends）**为移动端提供专属聚合接口：一个首页请求聚合待办、消息、统计卡片；字段按 App 版本裁剪，老版本 App 也能稳定工作。

10.4.4 iOS 与 macOS 的双端复用策略 ​

企业场景中 iOS 移动作业 + macOS 管理大屏很常见（物流调度、零售总部、医院护士站）。复用边界：

  • 可复用：领域模型、业务规则、网络层、持久化模型、同步引擎（全部是无 UI 的 SPM 模块）；
  • 需适配：交互层——iOS 用 SwiftUI/UIKit 触摸范式，macOS 用 AppKit/SwiftUI 桌面范式（菜单栏、多窗口、键鼠、悬停）；
  • 路线选择：原生双 UI（推荐，体验好）或 Mac Catalyst（UIKit App 快速上 Mac，成本低但桌面感弱）。不要用 Catalyst 承载复杂桌面交互。

10.5.2 企业场景专项优化 ​

启动（门店/机上场景尤其敏感）：店员点击图标后希望立刻进入扫码。除第 6 章通用手段外——首屏只装配当前模块，其余 feature 模块懒加载；离线数据预加载放后台队列，不阻塞首帧；ABM 设备可开启「预热」类 MDM 策略。

内存：长时间运行的门店 App 要警惕内存缓慢增长。图片资源按显示尺寸解码而非原图（CGImageSource 缩略图），长列表用第 6 章窗口化策略；页面退出时确认大对象释放，重点排查单例持有的数组无上限增长（工单 App 常见）。

电量：定位、蓝牙扫描、音频是三大耗电项。BLE 外设采用「连接时按需扫描、操作完断开」；定位用显著位置变更或区域监控（Geofence）而非持续 full accuracy；后台任务交给 BGTaskScheduler 在充电窗口执行。

包体积：离线资源（商品库、手册）不要打进 App 包，改为首启后按需下载并做版本增量；多架构/重复资源用第 6 章手段清理。金融 App 尤其关注监管要求的「在低速网络下 X 分钟内完成下载」。

swift
// File: PinningURLSession.swift —— 公钥绑定的核心校验（挂在 URLSessionDelegate）

import Foundation

final class PinningSessionDelegate: NSObject, URLSessionDelegate {
    /// 允许的 SPKI SHA-256 集合（新旧双公钥，轮换时先加新后删旧）
    let allowedPublicKeyHashes: Set<String>

    func urlSession(_ session: URLSession,
                    didReceive challenge: URLAuthenticationChallenge,
                    completionHandler: @escaping (URLSession.AuthChallengeDisposition, URLCredential?) -> Void) {
        guard challenge.protectionSpace.authenticationMethod == NSURLAuthenticationMethodServerTrust,
              let serverTrust = challenge.protectionSpace.serverTrust,
              Self.evaluate(serverTrust, allowedHashes: allowedPublicKeyHashes) else {
            completionHandler(.cancelAuthenticationChallenge, nil)   // ✅ 校验失败直接断连
            return
        }
        completionHandler(.useCredential, URLCredential(trust: serverTrust))
    }

    /// SecTrust 校验链 → 取叶子证书公钥 → 算 SPKI SHA-256 → 与白名单比对
    static func evaluate(_ trust: SecTrust, allowedHashes: Set<String>) -> Bool {
        var error: CFError?
        guard SecTrustEvaluateWithError(trust, &error) else { return false }
        let certificate = SecTrustGetCertificateAtIndex(trust, 0)!
        let publicKey = SecCertificateCopyKey(certificate)!
        // 实际工程建议直接使用经过审计的 TrustKit 等库；此处给出决策骨架，
        // SPKI DER 头 + 公钥数据 SHA-256 的完整编解码不要手写自创
        return allowedHashes.contains(Self.spkiSHA256(of: publicKey))
    }

    static func spkiSHA256(of key: SecKey) -> String { "" /* 见上：优先使用成熟库 */ }
}

import Foundation
import Security

/// Keychain 封装：存「小而关键」的数据（令牌、密钥），不是通用数据库
final class KeychainStore {
    /// 对称密钥只存 Keychain；业务数据用该密钥加密后放普通数据库
    @discardableResult
    func saveToken(_ token: Data, account: String) -> Bool {
        let query: [String: Any] = [
            kSecClass as String: kSecClassGenericPassword,
            kSecAttrAccount as String: account,
            kSecValueData as String: token,
            kSecAttrAccessible as String: kSecAttrAccessibleWhenUnlockedThisDeviceOnly, // ✅ 不进 iCloud 备份、锁屏不可读

                nil, kSecAttrAccessibleWhenUnlockedThisDeviceOnly,
                .userPresence, nil   // 读取需生物认证（按需使用）
            )!
        ]
        SecItemDelete(query as CFDictionary)
        return SecItemAdd(query as CFDictionary, nil) == errSecSuccess
    }
}

swift
// File: DataGovernance.swift
// 数据分类 + 留存策略：过期/擦除逻辑集中在存储层，业务模块不自行决定「存多久」。

/// 数据分类：决定存储位置、加密要求与留存周期
enum DataClass: String, Codable {
    case masterData   // 主数据只读副本，权威源在主数据平台
    case transaction  // 事务数据，与个人相关
    case derived      // 缓存/索引，可清空重建
    case sensitive    // 敏感个人信息，加密存储、登出即删
}

struct RetentionRule {
    let dataClass: DataClass
    let ttlDays: Int?              // 留存上限（天）；nil = 不自动过期
    let eraseOnLogout: Bool
    let requiresEncryption: Bool
}

/// 留存策略注册表：与 10.6.1 合规追溯矩阵同口径，审计时直接出示本表
enum RetentionPolicy {
    static let rules: [DataClass: RetentionRule] = [
        .masterData:  RetentionRule(dataClass: .masterData,  ttlDays: 30, eraseOnLogout: false, requiresEncryption: false),
        .transaction: RetentionRule(dataClass: .transaction, ttlDays: 90, eraseOnLogout: true,  requiresEncryption: true),
        .derived:     RetentionRule(dataClass: .derived,     ttlDays: 7,  eraseOnLogout: true,  requiresEncryption: false),
        .sensitive:   RetentionRule(dataClass: .sensitive,   ttlDays: 30, eraseOnLogout: true,  requiresEncryption: true),
    ]

    /// 账号注销（被遗忘权）：必须删除的数据类别；主数据是设备级公共副本，不属于个人
    static func classesToEraseForAccountDeletion() -> Set<DataClass> {
        [.transaction, .derived, .sensitive]
    }
}

/// 受治理存储协议：任何持久化实现都必须支持按类别批量过期与擦除
protocol GovernedDataStore {
    @discardableResult func purgeExpired(now: Date) throws -> Int  // 返回删除条数
    @discardableResult func erase(_ classes: Set<DataClass>) throws -> Int
}

③ 第三方模型 / SDK 供应商尽调清单

采购或引入前逐项核实并归档：

  • 数据流向：推理是否端侧完成；若上云，数据存储地点（是否跨境）、留存周期、是否被用于再训练；
  • 授权与 SLA：商用许可证范围、模型更新承诺、故障责任与赔付；
  • 可验证材料：模型卡、评测报告、安全/隐私证明（SOC 2、ISO 类）作为合同附件；
  • 退出预案：业务代码依赖抽象协议（ReceiptRecognizing 这类接口）而非具体模型，保证模型可替换、防供应商锁定。

④ 监管定性必须前置

医疗影像/诊断辅助可能触发医疗器械分类；金融授信与风控模型可能触发算法备案与可解释性要求；人脸/声纹按敏感个人信息处理（见 10.6）。立项阶段由合规出具定性意见，不允许先上线后定性。

运营侧三指标（叠加在第 12 章工程指标之上）：建议接受率、人工修正率（修正字段分布反哺评测集）、AI 相关差错率（与无 AI 流程对照）。这三个指标是授权级别升降的依据。

10.8.4 成本管理与 TCO 评估 ​

内部 App 立项答辩的核心问题永远是「这笔钱值不值」。TCO（总拥有成本）与 ROI（投资回报）必须在立项时由 IT 与业务侧共同背书，而不是上线后补算账。

10.8.5 无障碍、本地化与包容性：企业视角 ​

代码与工程模式不在此重复——第 13 章已完整覆盖：String Catalog / FormatStyle / CLDR（13.2）、翻译纳入 CI 与伪本地化（13.3）、无障碍四层模型（13.4）、SwiftUI/UIKit 适配（13.5）、自动化审计（13.6）、EAA / WCAG 2.2 合规追溯矩阵与银行/零售场景（13.7）。本节只讲四组组织与现场问题。

① 强制性按市场认定，法务先出清单

  • 美国：ADA、Section 508（联邦及受联邦资助场景）；欧盟：EAA（欧洲无障碍法案，2025 年起适用，技术对齐 EN 301 549 / WCAG 2.2）；
  • 立项时法务/市场按「产品销售地 + 员工所在地」列出强制清单，逐项映射到 13.7 矩阵的验收项——无障碍缺口与合规缺口是同一张表，不另立口径。

② 语言与区域是发布范围，不是技术决策

  • 每版本支持哪些语言、货币、区域规则，由市场与 HR 决定；研发交付的是「新语言可随时加入」的基础设施（13.2/13.3）与资源完整性门禁；
  • 译文质量由业务侧术语表和审校负责；IT 不做翻译，但对「key 缺失、未翻译内容上线」负责（伪本地化与 CI 门禁见 13.3.2 / 13.3.3）。

10.9 成功案例研究 ​

案例一：某股份制银行手机银行的 ObjC → Swift 渐进迁移 ​

背景：装机量数千万级的手机银行，核心代码为 8 年历史的 ObjC 工程，编译慢、新人上手难、并发崩溃占比高。监管要求强化移动安全能力。

策略（与第 4 章方法论一致）：

  1. 不重写：新功能（理财、信用卡专区）一律 Swift，通过桥接与 ObjC 互操作；
  2. 按模块灰度迁移：选「低耦合高收益」的消息中心试点 → 工具类 → 业务模块，每个模块独立双跑回归；
  3. 并发收口：把自组线程池与回调链路逐步替换为 Swift 6 结构化并发 + actor，严格并发检查分批打开；
  4. 安全同步建设：证书绑定、隐私清单、密钥治理随模块迁移落地。

结果指标（综合公开实践的典型量级，非单一企业精确数据）：编译速度显著改善；并发相关崩溃率下降；新功能交付周期缩短。关键经验：迁移的节奏由风险而非技术偏好决定——交易核心最后迁，且必须有完整自动化测试兜底（第 7 章）。

案例二：某连锁零售品牌 2000+ 门店的 iPad 作业平台 ​

背景：门店原有 PDA 体验差、断网即停业。目标统一为 iPad + 自研 App，承载收银辅助、盘库、价签、到货验收。

架构决策：离线优先（10.3.2 的队列模型）；ABM + MDM 零接触部署；BLE 扫码枪 + 便携打印机；BFF 聚合门店当日所需数据，开店前定时预热。

关键挑战与处理：

挑战处理
促销日全网断网全流程离线可作业，网络恢复后幂等同步；冲突转店长审核
店员流动率高工号登录 + 班次超时自动登出，登出即擦除缓存，全程培训压到 30 分钟内
2000 台设备运维MDM 分组策略、远程查看、自动更新；设备故障门店直接换机，配置云端恢复
数据口径一致性离线期间库存为预估值，UI 明确标注，以服务端审核后数据为准

结果：门店断网投诉与作业等待时间大幅下降，新店开店 IT 准备从数天缩到小时级。经验：内部工具的 ROI 主要来自「不中断业务」与「低培训成本」，而非炫酷功能。

案例三：某航空公司机组 EFB 的离线改造 ​

背景：纸质手册重（数十公斤）、更新慢。目标用 iPad EFB 替代，覆盖航图、手册、飞行计划与起飞性能计算。

方案：ABM 监管设备；航图/手册按机队与机场区域增量包，后台下载断点续传 + 哈希校验；起飞性能计算为本地纯函数（无网也必须可用），逻辑模块在 iOS 与 macOS 培训端复用；落地窗口期回传飞行报告。

关键经验：① 离线数据必须有「版本有效期 + 强制更新拦截」——过期航图宁可停摆不许使用，这是安全红线；② 关键计算结果双人复核 UI；③ 设备丢失远程擦除，所有文档加密。

10.12 小结与自测 ​

要点回顾：

  1. 行业业务约束（合规、离线、设备模式、外设）是企业架构的真正输入；
  2. 分层模块化、离线优先、BFF、双端复用是四个高频架构决策；
  3. 性能以「预算 + 分桶监控 + 门禁」治理，弱网/电量/长时运行是企业专项；
  4. 合规靠追溯矩阵把法规落成可验证控制；证书绑定、Keychain、加密、隐私清单是技术基座；
  5. 集成靠 SSO、MDM、网关与外设标准方案，优先 BFF 消化遗留系统；
  6. 落地以路线图推进、以成熟度矩阵与 KPI 度量、以风险登记表兜底；
  7. 数据治理把数据分层、留存与擦除代码化；AI 治理以授权级别和 RACI 划界，第三方模型先尽调后引入；
  8. 业务连续性以 RTO/RPO 驱动三层防线；TCO 让立项可答辩；无障碍与本地化按市场合规落地，一线工况即包容性设计。

1. 为什么交易类操作的冲突解决不能用「最后写入胜」？

资金交易要求强一致，客户端离线期间的状态可能已过期；必须以服务端事务为权威，配合幂等键保证重复提交不产生两笔交易，冲突直接拒绝或转人工，绝不静默覆盖。

2. 证书绑定选证书还是公钥？为什么必须配降级预案？

优先公钥绑定：证书轮换（通常每年）不必强制发版，预置新旧双公钥即可过渡。绑定逻辑错误或网络环境异常会导致全量客户端无法联网，且服务端无法修复，只能靠灰度发现与远程开关降级。

3. MDM 的 Managed Configuration 解决了什么工程问题？

把网关地址、租户、策略等环境差异从代码中移出，由 MDM 按设备组下发只读配置，同一个 App 包可安全部署到不同子公司/门店/环境，无需多套构建产物。

4. 为什么性能指标必须按机型档位分桶而不能只看平均值？

企业设备常为统一采购的中端机型，平均值会被少量高端机拉高而掩盖真实主流体验；分桶（机型 × 系统 × 版本）才能定位低端/老旧设备的劣化并设定针对性门禁。

5. 合规审计时，「做了」与「可证明做了」差别在哪？

合规要求的是证据链：追溯矩阵、配置截图、测评报告、审计日志、发布记录都需归档且与条款对应。口头声明不构成证据，因此技术控制从设计之初就要内置留痕与可导出能力。

6. 新上线的 AI 功能为什么必须从 L0/L1 起步，而不能直接开放 L2？

L2 允许 AI 在阈值满足时自动执行，其风险（误判、分布漂移、被对抗样本绕过）只有在真实业务流量下才能观测。没有足够的接受率、修正率与差错率数据，阈值与白名单场景都是拍脑袋；因此先用 L0/L1 收集一个季度运营证据，再由业务 owner 决定升级。

7. 一份被财务认可的 TCO 测算，和「硬件报价单」差在哪里？

TCO 必须覆盖全周期：一次性开发与集成（SSO/ERP/外设对接）、硬件折旧、MDM/云/SaaS 订阅、培训与停机损失等隐性成本，收益侧数字要有业务 owner 背书。只列设备采购价既不包含三分之二以上的真实成本，也无法回答回收期，立项答辩不成立。
