第 7 章 测试策略与质量保障 ​

企业级质量保障 = 合理分层的自动化测试 + 可量化的覆盖率 + 统一规范的静态检查。本章把测试金字塔真正落到 Apple 生态。

7.0 学习目标 ​

完成本章后，你将能够：

  1. 依据测试金字塔为 Apple 生态设计分层测试策略；
  2. 编写 XCTest 单元测试（含参数化思路与性能测试 measure）；
  3. 用 XCUITest + Page Object 模式编写可维护的 UI 测试；
  4. 接入快照测试（swift-snapshot-testing）与协议注入 Mock；
  5. 用 xccov 产出覆盖率报告，落地 SwiftLint / SwiftFormat 规范与危险 API 扫描。

7.1 核心知识点速览 ​

知识点一句话要点企业级关注度
测试金字塔大量单元测试 + 适量集成 + 少量 UI极高（策略总纲）

7.3 XCTest 实战 ​

基础结构与参数化思路 ​

XCTest 无内置参数化注解（注：Xcode 16 起 Swift Testing 已原生支持参数化，见 7.10 新小节），用「用例数组 + 循环断言」实现等价效果：

swift
// File: PriceFormatterTests.swift
import XCTest
@testable import MyApp                      // ✅ @testable 访问 internal

final class PriceFormatterTests: XCTestCase {

    // 参数化：表驱动测试（Table-Driven Test）
    func testFormat_cases() {
        let cases: [(input: Decimal, expected: String)] = [
            (0, "¥0.00"),
            (9.9, "¥9.90"),
            (1234.5, "¥1,234.50"),
            (-1, "¥0.00")                   // 负数兜底
        ]
        for c in cases {
            XCTAssertEqual(PriceFormatter.format(c.input), c.expected,
                           "input=\(c.input)")
        }
    }

    // 异步测试
    func testFetchUser() async throws {
        let repo = UserRepository(client: MockAPIClient())   // 协议注入
        let user = try await repo.user(id: 1)
        XCTAssertEqual(user.name, "Mock")
    }

    // 异常断言
    func testInvalidIDThrows() async {
        let repo = UserRepository(client: MockAPIClient())
        do {
            _ = try await repo.user(id: -1)
            XCTFail("应当抛出错误")
        } catch let error as RepoError {
            XCTAssertEqual(error, .invalidID)
        } catch {
            XCTFail("错误类型不符：\(error)")
        }
    }
}

7.4 XCUITest 与 Page Object 模式 ​

裸写 UI 测试 = 选择器散落、一改全崩。Page Object 把「页面结构」与「测试步骤」分离：

swift
// File: LoginPage.swift
import XCTest

struct LoginPage {
    let app: XCUIApplication

    var usernameField: XCUIElement { app.textFields["login.username"] }  // ✅ accessibilityIdentifier
    var passwordField: XCUIElement { app.secureTextFields["login.password"] }
    var submitButton: XCUIElement { app.buttons["login.submit"] }
    var errorLabel: XCUIElement { app.staticTexts["login.error"] }

    @discardableResult
    func login(user: String, pass: String) -> Self {
        usernameField.tap()
        usernameField.typeText(user)
        passwordField.tap()
        passwordField.typeText(pass)
        submitButton.tap()
        return self
    }
}

// File: LoginUITests.swift
final class LoginUITests: XCTestCase {
    private var app: XCUIApplication!

    override func setUp() {
        continueAfterFailure = false
        app = XCUIApplication()
        app.launchArguments = ["-UITesting"]        // ✅ App 内识别后注入 Mock 数据
        app.launch()
    }

    func testLoginFailure_showsError() {
        LoginPage(app: app).login(user: "bad", pass: "wrong")
        XCTAssertTrue(app.staticTexts["login.error"].waitForExistence(timeout: 3))
    }
}

7.5 快照测试（Snapshot Testing） ​

UI 回归的高性价比方案：把视图渲染结果与基线图片/文本对比。社区标准库是 Point-Free 的 swift-snapshot-testing（SPM 接入）。

swift
// File: ProfileCardSnapshotTests.swift
import XCTest
import SnapshotTesting
@testable import MyApp

final class ProfileCardSnapshotTests: XCTestCase {
    func testProfileCard_states() {
        // 多状态 × 多设备 组合快照
        let view = ProfileCardView(user: .preview)
        assertSnapshot(of: view, as: .image(layout: .device(config: .iPhone13Pro)))
        assertSnapshot(of: view, as: .image(layout: .device(config: .iPhoneSe),
                                            traits: .init(preferredContentSizeCategory: .accessibilityExtraExtraLarge)))
    }
}

  • ✅ 适用：组件库、设计系统（Design System）、卡片/弹窗等高复用 UI。
  • ⚠️ 快照对字体渲染、系统版本敏感：基线必须固定机型 + 系统版本 + 语言环境，CI 镜像与录制环境一致。
  • ⚠️ 不要把整个 App 都快照化——基线图片的评审成本（diff 看图）会随数量爆炸，聚焦核心组件。

7.6 Mock / Stub：协议注入是可测试性的前提 ​

swift
// File: RepositoryTesting.swift
import Foundation

// 生产代码：依赖协议而非实现（第 1、5 章的设计在此兑现）
protocol APIClientProtocol: Sendable {
    func request(path: String) async throws -> Data
}

struct UserRepository: Sendable {
    let client: any APIClientProtocol
    func userName(id: Int) async throws -> String {
        let data = try await client.request(path: "/users/\(id)")
        let obj = try JSONSerialization.jsonObject(with: data) as? [String: Any]
        return obj?["name"] as? String ?? ""
    }
}

// 测试代码：Stub 返回固定数据
struct StubAPIClient: APIClientProtocol {
    var stubData: Data
    var stubError: Error?

    func request(path: String) async throws -> Data {
        if let stubError { throw stubError }
        return stubData
    }
}

概念区别
Stub返回固定数据，验证「状态」
Mock记录调用（次数/参数），验证「行为」
Fake轻量真实现（如内存数据库），集成测试用
  • ⚠️ Swift 无成熟运行时 Mock 框架（语言限制），手写 Stub/Mock 或代码生成（如 Sourcery 模板）是主流——这更凸显协议设计的重要性。
  • ❌ 反例：为测试把 URLSession 方法全改成静态变量替换——污染生产代码，且并发下互相干扰。

7.9 危险 API 静态扫描 ​

用 SwiftLint 自定义规则把「团队血泪教训」变成编译期拦截：

yaml
# File: .swiftlint.yml（追加 custom_rules）
custom_rules:
  no_usernames_in_defaults:
    name: "禁止 UserDefaults 存敏感信息"
    regex: "UserDefaults\\..*set\\(.*(token|password|secret)"
    message: "敏感数据请使用 KeychainStore（见第 6 章）"
    severity: error
  no_main_thread_io:
    name: "主线程同步 IO"
    regex: "DispatchQueue\\.main\\.sync"
    message: "主线程同步调用存在死锁风险"
    severity: error
  no_force_date_format:
    name: "禁止裸用 DateFormatter 单例共享"
    regex: "DateFormatter\\(\\)\\s*$"
    match_kinds: [expression]
    message: "DateFormatter 非线程安全，请使用共享池或 ISO8601DateFormatter"
    severity: warning

7.10 新一代测试框架：Swift Testing ​

Swift Testing（Xcode 16 原生） ​

Swift Testing 是 Xcode 16 / Swift 6 工具链内置的新一代框架，与 XCTest 同 target 可共存：

维度XCTestSwift Testing
用例声明class: XCTestCase + func testX()@Test 标记普通方法（struct/顶层均可）
断言XCTAssertEqual 系列#expect（记录失败继续）/ #require（失败即终止），自动展开表达式各子值
参数化无内置，表驱动循环（见 7.3）@Test(arguments:) 原生，每参数独立用例
分组XCTestCase 类@Suite struct，支持嵌套与标签
并行默认串行默认方法级并行
工具链全版本Xcode 16 / Swift 6
swift
// File: MathTests.swift（Tests/MathKitTests/，被测源码提供 MathKit.add/divide 与 MathError）
import Testing
@testable import MathKit

struct MathTests {
    // 参数化：元组数组自动展开为 4 个独立用例，失败报告带具体入参
    @Test(arguments: [(0, 0, 0), (1, 1, 2), (-1, 1, 0), (100, 200, 300)])
    func addCases(a: Int, b: Int, expected: Int) {
        #expect(MathKit.add(a, b) == expected)   // 失败时自动打印 a、b、两侧实际值
    }

    @Test func divideWorks() throws {
        #expect(try MathKit.divide(10, 2) == 5)
    }

    // #require(throws:)：必须抛出指定错误，否则用例失败并终止
    @Test func divideByZeroThrows() throws {
        try #require(throws: MathError.divideByZero) {
            _ = try MathKit.divide(1, 0)
        }
    }
}

@Suite("边界场景")                    // 分组：类似 XCTestCase 类，但可嵌套
struct EdgeCaseSuite {
    @Test(arguments: [Int.min, -1, 0, Int.max])
    func identity(x: Int) {
        #expect(MathKit.add(x, 0) == x)
    }
}

企业级场景分析 ​

场景：金融 App 的回归测试体系重建 ​

某银行 App 从「发版前人工回归 3 天」到「自动化 2 小时」的过程：

  1. 盘点核心链路：登录、转账、理财申购、信用卡还款 4 条链路共 60 个用例，先用 XCUITest + Page Object 覆盖（约 2 人月）。
  2. Mock 服务器：UI 测试通过 launchArguments 切换到内置 Mock Server（拦截 URLProtocol 返回 fixture），消除对测试环境的依赖，flaky 率从 30% 降到 3%。
  3. 单元层补厚度：把 ViewModel 中埋着的金额计算、风控判断逻辑抽为纯函数，单元测试从 200 个补到 1800 个——大量 UI 层发现的边界问题下沉到单元层。
  4. CI 门禁：PR 触发单元测试 + lint；每日 nightly 跑全量 UI 测试 + 快照；增量覆盖率 ≥80% 才允许合并（与第 8 章流水线衔接）。
  5. 效果：发版周期从双周变为每周，线上缺陷率下降 55%。

经验：测试 ROI 排序 ​

从企业实践看投入产出比：协议化 + 单元测试 > 危险 API 扫描 > UI 冒烟 > 快照 > 全量 UI 回归。预算有限时，先把「可测试架构」（第 1、5 章的协议注入）做扎实，再谈覆盖率数字。

实践任务 ​

任务 1：表驱动单元测试（★） ​

为字符串工具（如手机号脱敏 138****5678）写表驱动测试，覆盖边界：空串、非数字、长度不足、国际区号。

任务 2：异步测试（★★） ​

用 Stub 客户端测试 Repository 的成功/失败/超时三个分支，异常类型必须精确断言。

任务 3：Page Object 改造（★★） ​

把一个裸写的 XCUITest（选择器内联）改造成 Page Object，并给被测视图补齐 accessibilityIdentifier。

任务 4：性能基线（★） ​

为 JSON 解析器写 measure 性能测试并设定 baseline；故意把算法改慢，观察测试失败。

任务 5：CI 门禁脚本（★★★） ​

写一个脚本：解析 xccov JSON，计算「本次改动文件」的覆盖率，低于 80% 退出码非零；再附加一条 SwiftLint custom rule 检查 print( 调试语句残留。

小结与自测 ​

要点回顾

  • 金字塔：70% 单元 + 20% 集成 + 10% UI；问题尽量在最低层暴露。
  • XCTest：表驱动实现参数化；measure 建性能基线；异步用 async 测试直接 await。
  • XCUITest 靠 Page Object + accessibilityIdentifier + waitForExistence 三件套对抗 flaky。
  • 快照测试聚焦核心组件；Mock 靠协议注入，Swift 手写为主。
  • 覆盖率看增量；SwiftLint/SwiftFormat 分工明确；危险 API 用 custom_rules 编译期拦截。

自测题

  1. 为什么 UI 测试不适合承担主要回归职责？
  2. @testable import 开放了什么访问级别？有什么代价？
  3. waitForExistence(timeout:) 相比 sleep 的本质优势是什么？
  4. Stub 与 Mock 的验证目标有何不同？Swift 生态为何以手写为主？
  5. 「增量覆盖率门禁」相比「全量覆盖率门禁」解决了什么实际问题？
参考答案
  1. UI 测试慢（分钟级）、flaky（环境时序敏感）、维护贵（UI 变动频繁）；同样的问题用单元测试能毫秒级覆盖。UI 测试应只做核心链路冒烟。
  2. 开放 internal 成员给测试 target。代价：测试可能依赖实现细节而非公开接口，重构时测试跟着碎——约定优先测 public 行为，@testable 仅用于必要的白盒场景。
  3. waitForExistence 是条件轮询，元素一出现立即继续（快）且超时明确报错（稳）；sleep 无论元素是否就绪都等满时间（慢），且时间设短了就 flaky。
  4. Stub 验证「给定输入的输出状态」；Mock 验证「协作行为是否发生」（调用次数/参数）。Swift 缺乏修改运行时类行为的能力（静态派发、类型安全），无法像 ObjC 时代 OCMock 那样运行时替换，故以手写 Stub/Mock 或代码生成为主。
  5. 遗留工程全量覆盖率基数低（如 15%），全量门禁要么形同虚设要么不可达成；增量门禁只要求「新代码有测试」，覆盖率随迭代自然爬升，可执行且不惩罚历史。
