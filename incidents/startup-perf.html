INC-01 冷启动白屏 3 秒 ​

症状

  • 用户反馈：点击图标后白屏约 3 秒才出现首页骨架；埋点测得冷启动 P90 3.2s、首帧 2.8s，热启动仅 0.6s（进程已驻留，省掉了 dyld 与初始化）。
  • 首次安装后的第一次启动更差（约 4.5s），低端机（A12）比新机多 1s 以上；部分用户在「预热（Prewarming）」后启动看似变快，样本需分层。

假设树

  • H1：pre-main 阶段偏慢（动态库加载、ObjC setup、+load），启动尚未进入 main。
  • H2：didFinishLaunching 中同步初始化 SDK、数据库迁移或发起网络请求。
  • H3：首屏 UI 构建过重（Storyboard 解码、视图层级深、同步 Auto Layout）。
  • H4：首屏数据强依赖网络且无本地缓存，必须等接口返回才开始渲染。
  • H5：首帧前主线程被同步等待阻塞（信号量、锁、DispatchQueue.main.sync），后台任务完成前无法绘制。

定位动作

bash
# 1) pre-main 分段耗时：Scheme → Run → Environment Variables 加 DYLD_PRINT_STATISTICS=1
#    控制台会输出 dylib loading / rebase / bind / ObjC setup / initializer 各段毫秒数
# 2) 冷启动全过程（模拟器先杀进程，真机手动上滑杀 App）
xcrun simctl terminate booted com.example.shop
xcrun xctrace record --template "App Launch" --device-name "iPhone 15" \
  --time-limit 10s --launch -- com.example.shop
# 3) 主线程热点（Profile 默认 Release 配置）
xcrun xctrace record --template "Time Profiler" --device-name "iPhone 15" \
  --time-limit 20s --launch -- com.example.shop

验证与排除

  • H1：DYLD_PRINT_STATISTICS 的 pre-main 总耗时若 < 200ms，排除 H1 因为慢发生在 main 之后；若 initializer/ObjC setup 占大头，转 INC-02/INC-03 继续下钻。
  • H2：用启动参数或 Feature Flag 临时关闭非必要 SDK 冷启动复测；首帧提前 ≥ 500ms 则确认 H2，若几乎无变化则排除 H2 因为初始化不是瓶颈。
  • H3：Time Profiler 中 layoutSubviews/NSLayoutConstraint/UINib 占比高即确认；临时把首屏换成纯代码占位视图，首帧大幅提前则 H3 成立。
  • H4：飞行模式 + 已有缓存启动；若仍白屏 3 秒，排除 H4 因为网络不是前置条件；若仅断网时明显变慢，则 H4 成立。
  • H5：主线程栈长时间停在 dispatch_semaphore_wait/__psynch_cvwait/dispatch_sync，且能看到等待的后台任务；删除该等待后首帧恢复即确认。若主线程是纯计算热点，排除 H5。

修复要点

  • ✅ 首屏数据「缓存直出 + 后台刷新」：本地快照先渲染，接口返回后增量更新，把白屏压到首帧预算内（60Hz 约 16.6ms，120Hz 约 8.3ms 只是绘制预算，感知启动另算）。
  • ✅ didFinishLaunching 只保留日志/崩溃/网络栈；埋点、AB、推送注册拆到首帧后的空闲批次（参照 6.3 的 LaunchTaskManager），首屏常见提前 100~500ms。
  • ✅ 首屏视图代码构建、固定行高/预估高度，避免 Storyboard 解码与一次性全量布局。
  • ⚠️ 延迟初始化要维护依赖顺序与「首帧后」时机；回归用 Release 包 + 低端机各测 10 次看 P90，单次冷启动方差大，不足以作结论。预期 pre-main 800ms→300ms、首帧 2.8s→1.2s 量级，因工程而异；线上以 MetricKit MXAppLaunchMetric 的直方图复核。

INC-02 首帧前 +load / 静态初始化阻塞 ​

症状

  • 冷启动 2.6s，其中 main 之前约 1.4s；控制台在 didFinishLaunching 之前就没有任何业务日志，用户看到黑/白屏而不是首页。
  • 重装后无改善（与缓存无关），且与机型相关：接入大量历史 ObjC SDK 的包更慢；DYLD_PRINT_STATISTICS 的 initializer 段异常突出。

假设树

  • H1：大量 +load 在每个类加载时同步执行（日志注册、swizzling、单例预热）。
  • H2：__attribute__((constructor)) 或 C++ 全局对象构造在 initializer 阶段同步跑。
  • H3：Category 的 +load 里做 swizzling，遍历方法列表、构造字符串/字典，单线程串行累积。
  • H4：静态初始化里做同步 IO/Keychain/网络（读配置、取设备指纹、预拉开关）。
  • H5：ObjC 类与 Category 数量膨胀导致 ObjC setup 本身变慢（不一定是 +load 代码）。

定位动作

bash
# Scheme → Run → Environment Variables 加 DYLD_PRINT_STATISTICS=1
# 观察 initializer / ObjC setup 两段耗时
xcrun xctrace record --template "App Launch" --device-name "iPhone 15" \
  --time-limit 8s --launch -- com.example.app
# 辅助统计镜像规模（判断 ObjC setup 成本）
nm -m MyApp.app/MyApp | grep -c '_OBJC_CLASS_$_'
size -m MyApp.app/MyApp

运行方式：终端执行；DYLD_PRINT_STATISTICS 建议同时在 Xcode Scheme 中配置，便于反复 Run 对比。

  • 工具与看什么：App Launch 模板看 initializer/ObjC setup 两段及首帧起点；Time Profiler 反转调用树后搜 load_images、call_load_methods、+load，看这些帧是否出现在 main 之前；在 +load 与 AppDelegate 入口打 signpost，可确认时间归属。
  • ⚠️ 模拟器上的 pre-main 绝对值不可直接外推到真机（磁盘、CPU、签名验证不同），比例与调用栈可参考。

验证与排除

  • H1：Time Profiler 的 pre-main 区间存在 call_load_methods/+load 且占比高，临时移除一批 SDK 的 +load 后 initializer 明显下降 → 确认 H1；若几乎没有 +load 帧，排除 H1。
  • H2：initializer 段高且栈里能看到构造器/C++ 静态初始化符号；若 initializer 段很小，排除 H2 因为耗时不在这一阶段。
  • H3：+load 栈里 method_exchangeImplementations、class_copyMethodList、字符串构造占比高 → 确认；若 swizzling 只有少量且耗时集中在 IO，排除 H3。
  • H4：栈中出现 SecItemCopyMatching、read、同步网络调用；断网/清空 Keychain 复测，若 pre-main 不变则排除 H4。
  • H5：nm 统计类数量异常（例如数万类）且 ObjC setup 段远大于 initializer 段 → 确认 H5；此时即使删掉 +load 收益也有限，需要减类/合并 Category。

修复要点

  • ✅ 把 +load 里的业务逻辑改为显式入口（+start），在首帧后由启动调度器调用；仅保留必须早于任何消息发送的 swizzling。
  • ✅ swizzling 收敛为注册表：按模块登记、启动时一次性安装，避免每个 Category 各自交换与重复字符串构造。
  • ✅ 配置/设备指纹/开关改为懒加载或后台预取，禁止在 initializer 中同步 IO/Keychain/网络。
  • ⚠️ swizzling 延后要验证「首次调用前已安装」，否则会出现偶发方法未交换；合并 Category 要检查重复方法与加载顺序。预期 initializer 1.4s→250ms 量级；回归用冷启动 P90 + 功能冒烟（尤其依赖 swizzling 的模块）。

INC-03 动态库过多导致 pre-main 变慢 ​

症状

  • pre-main 约 1.8s，App 包内 60+ 个动态 framework；冷启动 3.0s，热启动 2.2s 仍明显偏慢（每次进程启动都要重新加载/绑定）。
  • 低端机更差；DYLD_PRINT_STATISTICS 的 dylib loading 与 rebase/bind 段占比高，业务代码却只在 main 之后才执行。

假设树

  • H1：动态库数量过多，dyld 对每个镜像做打开、映射、符号绑定，成本随数量上升（Apple 建议 ≤ 6 个）。
  • H2：Fixups/Rebase/Bind 指针数量大（ObjC 元数据、Swift 协议一致性、大量全局变量）。
  • H3：多个框架重复链接同一三方库/重复符号，镜像体积大、加载页多。
  • H4：每个 dylib 各自的 initializer/+load 串行执行，叠加成 pre-main 大头。
  • H5：冷启动的首次页 fault 与代码签名验证（仅冷启动显著，热启动应大幅缓解）。

定位动作

bash
# Scheme → Run → Environment Variables 加 DYLD_PRINT_STATISTICS=1
# 统计嵌入 framework 数与主二进制直接依赖
ls MyApp.app/Frameworks | wc -l
otool -L MyApp.app/MyApp | grep '@rpath' | wc -l
size -m MyApp.app/MyApp
xcrun xctrace record --template "App Launch" --device-name "iPhone 15" \
  --time-limit 10s --launch -- com.example.app

运行方式：终端执行；先用 ls/otool 做静态盘点，再用 App Launch 录冷启动看各阶段占比。

  • 工具与看什么：DYLD_PRINT_STATISTICS 的 dylib loading 与 rebase/bind 毫秒数；App Launch 模板的 Dynamic Linking 阶段；otool -L 核对每个 framework 是否重复依赖同一 @rpath 库；size -m 看 __TEXT/__DATA 段规模。

验证与排除

  • H1：把大部分 Pod 从 use_frameworks! 动态改为静态链接（或合并 framework），dylib 数下降后 pre-main 同步下降 → 确认 H1；若数量下降而耗时几乎不变，排除 H1。
  • H2：rebase/bind 毫秒数明显大于 dylib loading，且减少全局/ObjC 元数据后有收益 → 确认 H2；若 dylib loading 占绝对大头，排除 H2 作为主因。
  • H3：otool -L 显示多个 framework 依赖同一库，或 du -sh 显示重复镜像体积异常 → 确认；若依赖树干净，排除 H3。
  • H4：App Launch 的 initializer 段随 dylib 数线性增长，移除某个 SDK 后该段下降 → 确认 H4；若 initializer 段很小，排除。
  • H5：冷启动减热启动的差值若主要来自首次页 fault/签名，热启动应明显更快；若热启动同样慢，排除 H5 因为页缓存不是主因。具体签名验证成本因设备/系统而异，待真机验证。

修复要点

  • ✅ 能静态链接的三方库一律静态化（CocoaPods use_modular_headers!/静态库，或 SwiftPM 静态产品），只保留 Apple 建议的少量动态库（≤ 6 个为经验值）。
  • ✅ 清理重复依赖与重复三方库，合并同源 SDK；用 otool -L 做 CI 依赖白名单。
  • ✅ 各 dylib 的 initializer 下沉为首帧后显式初始化，减少 pre-main 串行叠加。
  • ⚠️ 静态化会增大主二进制、可能引入重复符号与 Category 冲突；需核对 6.4 包体/App Thinning 变化，并在低端机复测冷启动 P90。预期 60+→6 个动态库、pre-main 1.8s→0.6s 量级，取决于工程。

INC-04 列表滑动掉帧/卡顿 ​

症状

  • 120Hz ProMotion 机型上信息流滑动只有 48~55fps，肉眼可见顿挫；P90 帧耗时约 20ms，远超 8.3ms 预算；60Hz 机型「勉强能用」但仍有卡顿。
  • 首次进入页面后的第一屏滑动最差（图片尚未解码/缓存），之后略好但未达标；Hangs 仪器偶尔记录到 250ms 级主线程阻塞（默认阈值 250ms），说明有长任务叠加。

假设树

  • H1：cell 内 Auto Layout 复杂或动态高度，每次复用都重新求解布局。
  • H2：主线程同步图片解码/磁盘读取（cellForRow 里 UIImage(contentsOfFile:)、大图直接解码）。
  • H3：每帧重复创建 DateFormatter/NumberFormatter/正则/富文本。
  • H4：离屏渲染或视图层级过深（圆角 + 阴影 + masksToBounds、blur、shouldRasterize）。
  • H5：主线程被非 UI 任务抢占（埋点落盘、日志字符串拼接、网络回调、锁等待）。

定位动作

bash
# 帧生命周期与 hitch：先看哪一帧超预算、主线程在做什么
xcrun xctrace record --template "Animation Hitches" --device-name "iPhone 15 Pro" \
  --time-limit 20s --attach MyApp
# CPU 热点（Invert Call Tree + Hide System Libraries）
xcrun xctrace record --template "Time Profiler" --device-name "iPhone 15 Pro" \
  --time-limit 20s --attach MyApp
# 主线程阻塞超过 250ms 的 hang（Hangs 仪器，阈值默认 250ms）
xcrun xctrace record --template "Time Profiler" --instrument "Hangs" \
  --device-name "iPhone 15 Pro" --time-limit 20s --attach MyApp

  • 工具与看什么：Animation Hitches 看每帧的 hitch 时长与主线程栈；Time Profiler 找 layoutSubviews、drawRect、图片解码、DateFormatter 的热点；Hangs 仪器看超过阈值的阻塞；Instruments 的 Core Animation FPS 仪器可看实时帧率，Color Offscreen-Rendered/Color Blended Layers（模拟器调试菜单）辅助验证 H4。

验证与排除

  • H1：Time Profiler 中 layoutSubviews/NSLayoutConstraint/sizeThatFits 自耗时高 → 确认；临时改为固定行高、translatesAutoresizingMaskIntoConstraints = true 的手工布局，帧耗时下降则 H1 成立。
  • H2：主线程栈出现 ImageIO/CGImageSource/read；把解码挪到后台或改为按显示尺寸下采样，hitch 明显减少 → 确认；若图片已缓存仍掉帧，排除 H2。
  • H3：热点里反复出现格式化器创建/正则编译 → 确认；把格式化器改为 static let 复用后复测，若帧耗时下降则成立。
  • H4：模拟器打开离屏渲染/混合层调试，红色/黄色区域与掉帧 cell 对应 → 确认；给阴影加 shadowPath、圆角改用预裁剪图片后复测。若无可视化异常，排除 H4。
  • H5：Time Profiler 显示主线程时间花在日志/埋点/锁，而非 UIKit；关闭埋点或改为异步批量写，掉帧消失 → 确认；若热点全在 UI，排除 H5。

修复要点

  • ✅ 图片按显示尺寸下采样（ImageIO thumbnail）并在后台解码，主线程只赋值；cell 复用取消未完成请求。
  • ✅ 固定行高或一次性算高缓存，减少 Auto Layout 求解；文本预排版，避免每帧创建格式化器。
  • ✅ 阴影用 shadowPath、圆角用预裁剪/cornerCurve 合理设置，减少离屏渲染与图层混合。
  • ⚠️ 埋点/日志异步化要保证顺序与落盘可靠性（退后台 flush）；用 120Hz 真机回归，不用模拟器 FPS 代替。预期 48~55fps → 接近满帧、P90 帧耗时回到预算内；具体收益因列表复杂度而异。

INC-05 主线程同步 IO/网络导致卡顿或无响应 ​

症状

  • 点击「查看订单」后界面冻结 2~5 秒，转圈不动、按钮无反馈；无崩溃，但用户反复点击后出现更长的无响应。
  • 线上 MXHangDiagnostic 记录到主线程 hang；低端机/弱网更频繁，强网时缩短但不消失。

假设树

  • H1：主线程同步网络请求（信号量等待 URLSession、Data(contentsOf: URL)）。
  • H2：主线程同步文件 IO/数据库查询（大 JSON 读取、SQLite/CoreData 主线程 fetch、日志写盘）。
  • H3：主线程等待后台任务（DispatchSemaphore.wait、DispatchGroup.wait、跳到串行队列 sync）。
  • H4：锁竞争或死锁（os_unfair_lock 重入、@synchronized 嵌套、主队列 sync 自锁）。
  • H5：主线程纯 CPU 重活（大 JSON 解析、加密、图片解码、日期格式化）造成长时间占用。

定位动作

bash
# 主线程 hang + 线程调度：看主线程卡在等待还是计算
xcrun xctrace record --template "System Trace" --device-name "iPhone 15" \
  --time-limit 20s --attach MyApp
xcrun xctrace record --template "Time Profiler" --instrument "Hangs" \
  --device-name "iPhone 15" --time-limit 20s --attach MyApp
# 应用日志（真机用 Console.app 按 process 过滤）

  • 工具与看什么：System Trace 看主线程是否被阻塞、哪些线程在跑、锁等待与线程切换；Time Profiler + Hangs 看主线程栈与超阈值区间；在「点击事件 → 首帧响应」打 signpost，定位耗时落在网络、IO 还是计算。

验证与排除

  • H1：主线程栈在 dispatch_semaphore_wait 且另一线程在 URLSession 回调；让服务端人为延迟 2s，hang 同步变长 → 确认；若断网后立即返回错误而非长 hang，也侧面印证 H1。若等待与网络无关，排除 H1。
  • H2：栈中出现 read/fsync/sqlite3_step/CoreData fetch；把该操作移到后台队列后 hang 消失 → 确认；若主线程无 IO 帧，排除 H2。
  • H3：栈中 dispatch_group_wait/sync 等待的是普通后台任务而非网络；改异步回调后恢复 → 确认；若等待对象是网络，归入 H1 而非 H3。
  • H4：调试器暂停后 thread backtrace all 看到两条线程互相等待锁，连续两次暂停栈不变 → 确认死锁；若只是单线程长时间运行，排除 H4。
  • H5：主线程 CPU 占用接近 100%，热点在解析/加密/格式化且无等待与 IO → 确认；把计算移走后 hang 消失。若主线程大部分时间在 wait，排除 H5。

修复要点

  • ✅ 主线程只做 UI；网络、数据库、文件、图片解码全部异步化（async/await + 后台执行器，UI 回 MainActor）。
  • ✅ 移除所有 semaphore.wait/group.wait/main.sync 式「把异步转同步」桥接，改为回调或 withCheckedContinuation（注意取消与超时）。
  • ✅ 大数据分片/流式处理，解析与加密放后台；UI 先展示骨架，结果回来再填充。
  • ⚠️ 异步化后要处理顺序、取消与超时，避免回调回来时页面已销毁（[weak self]/Task 取消）；回归用弱网 + 低端机复测 hang 率。预期单次 hang 3.8s→200ms 以内，MetricKit hang 计数明显下降。
