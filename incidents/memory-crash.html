INC-06 图片解码内存暴涨 / OOM 被 jetsam ​

症状

  • 图片流浏览 20~30 屏后 App 直接退回桌面，没有异常栈；系统日志出现 JetsamEvent，MetricKit MXAppExitMetric 显示内存相关异常退出。
  • 6GB 机型能撑更久，3GB 老机型几十秒即被杀；Instruments 记录峰值 1.5~1.8GB，Leaks 没有报泄漏。Jetsam 阈值因设备/系统/前后台状态而异，待真机验证。

假设树

  • H1：全尺寸解码——UIImage(data:) 按原图分辨率解码，4032×3024×4B ≈ 46MB/张。
  • H2：图片缓存无上限——NSCache 未设 totalCostLimit，或用字典/数组强引用所有图片。
  • H3：cell 复用或请求闭包持有已离屏 cell/图片，导致不释放。
  • H4：批量处理缺少 autoreleasepool，临时 UIImage/NSData 峰值叠加。
  • H5：内存增长来自 WebView/地图/视频等其他模块，与图片管线无关。

定位动作

bash
# 图片浏览过程中录制分配轨迹（真机）
xcrun xctrace record --template "Allocations" --device-name "iPhone 15" \
  --time-limit 30s --attach MyApp
# 模拟器/宿主进程：VM 概况与堆上大对象（真机改用 Instruments 的 VM Tracker 仪器）
vmmap -summary MyApp
heap -s MyApp | head -30

  • 工具与看什么：Allocations 看 Persistent Bytes 与峰值，用 Mark Generation 对比「进入列表前 / 浏览 10 屏后」；VM Tracker 看 dirty/compressed；heap -s 看大类占用；Xcode Organizer 与 MetricKit 确认退出类型是 jetsam 而非崩溃。

验证与排除

  • H1：单张图解码字节约等于像素宽×高×4，峰值随浏览张数线性上升；改为按显示尺寸下采样后峰值显著下降 → 确认。若下采样无变化，排除 H1。
  • H2：回到列表页后 Persistent Bytes 不回落，清空缓存立即下降 → 确认；若退出页面即回落，排除 H2 因为缓存不是主因。
  • H3：Memory Graph 显示 cell 被请求闭包持有，prepareForReuse 后仍未释放 → 确认；若引用链干净，排除 H3。
  • H4：峰值呈锯齿且大量临时对象，循环外套 autoreleasepool 后峰值下降 → 确认；若无变化，排除 H4。
  • H5：VM Tracker 中 WebView/地图区域占主导，禁用该模块后内存下降 → 确认；若 CGImage/ImageIO 区域占主导，排除 H5。

修复要点

  • ✅ 用 ImageIO 按显示尺寸下采样（CGImageSourceCreateThumbnailAtIndex + maxPixelSize），后台解码，主线程只绑定。
  • ✅ NSCache 设 totalCostLimit/countLimit，cost 用解码字节数；页面退出主动清理。
  • ✅ cell 复用取消未完成图片请求，闭包 [weak self]；批处理套 autoreleasepool。
  • ⚠️ 下采样要处理 EXIF 方向与动图首帧；缓存上限过小会掉命中率。预期峰值 1.8GB→400MB 量级；在 3GB 低端机上做前后台切换回归，观察 jetsam 率。

INC-07 大图 mmap 与大对象分配 ​

症状

  • 打开一张 48MP 照片或扫描 PDF 后内存立刻冲到 600~900MB，3GB 设备被杀；关闭页面后常驻内存也不完全回落。
  • vmmap 能看到数百 MB 的 MALLOC_LARGE/图像相关 region；首次打开明显更慢，第二次同一图稍好但内存仍高。

假设树

  • H1：UIImage(contentsOfFile:)/UIImage(data:) 全尺寸解码，生成整幅位图。
  • H2：ImageIO 直接用 CGImageSourceCreateImageAtIndex，未生成缩略图、未按显示尺寸解码。
  • H3：单个大 buffer 超过 malloc 阈值走 mmap，形成不可压缩大 region；数组扩容多次拷贝放大峰值。
  • H4：预加载/相邻页同时解码多张大图，峰值叠加。
  • H5：误把文件 mmap（如 .mappedIfSafe）当成泄漏——大部分是 clean file-backed 页，可被系统回收。

定位动作

bash
# 内存区域与大对象
vmmap -summary MyApp
vmmap -sortBySize MyApp | head -25
heap -s MyApp | head -30
# 单块分配的来源栈（需 Scheme 环境变量 MallocStackLogging=1；模拟器/宿主进程）
malloc_history 12345 -allBySize

运行方式：打开大图后执行；vmmap/heap/malloc_history 针对模拟器或 macOS 进程，真机用 Allocations + VM Tracker 并开启 Malloc Stack Logging。

  • 工具与看什么：vmmap 看 MALLOC_LARGE、CG/Image 相关 region 的 dirty 大小；heap -s 看 CGImage/NSData 等类总占用；malloc_history -allBySize 看最大单块及其分配栈；Allocations 的 Mark Generation 对比打开前/关闭后。

验证与排除

  • H1/H2：单张图的内存增量约等于像素数×4，且 Allocations 中 CGImage/ImageIO 占主导；改缩略图解码后增量下降到显示尺寸 → 确认。若增量与图片分辨率无关，排除 H1/H2。
  • H3：vmmap 出现单个数百 MB 的 MALLOC_LARGE，malloc_history 能指向一次大分配 → 确认；若只是大量小块累加，排除 H3 作为主因。
  • H4：峰值与「同时预加载的图片数」成正比，关闭预加载后明显下降 → 确认；若单张就爆，排除 H4。
  • H5：vmmap 中文件映射 clean 页很大但 dirty 很小 → 排除 H5 因为可回收页通常不是 jetsam 主因；若 dirty 与文件映射同量增长，再回头查解码缓冲。计入规则因系统版本而异，待真机验证。

修复要点

  • ✅ 全面改用 ImageIO 缩略图（kCGImageSourceCreateThumbnailFromImageAlways + kCGImageSourceThumbnailMaxPixelSize），按显示尺寸解码。
  • ✅ 大 PDF 分页渲染、流式读取；不要一次性把整本/整图读入内存。
  • ✅ 避免大数组反复扩容，预分配容量；大 buffer 用完及时释放，批处理套 autoreleasepool。
  • ⚠️ 缩略图要处理方向、透明通道与质量；分页渲染要验证滚动衔接。预期峰值 900MB→120MB 量级，因图片尺寸而异；回归覆盖最大图与连续翻页。

INC-08 闭包 / Timer / 通知导致内存持续增长 ​

症状

  • 设置页反复进出 20 次，内存从 120MB 涨到 600MB，且不再回落；低端机随后被 jetsam。
  • 控制器 deinit 日志不打印，Memory Graph 里能看到 VC/ViewModel 仍存活；Leaks 模板却不报泄漏（循环引用常被漏报）。

假设树

  • H1：闭包强引用 self（网络回调、动画 completion、闭包属性），self 又持有闭包形成环。
  • H2：Timer.scheduledTimer(target:self)/CADisplayLink 被 RunLoop 持有，target 是 self，VC 永不释放。
  • H3：block 形式的 NotificationCenter.addObserver(forName:...) token 未移除；selector 形式在 iOS 9+ 会自动注销，不能混为一谈。
  • H4：单例/静态缓存/强 delegate 持有 VC 或 ViewModel（缓存 key 从不淘汰）。
  • H5：长生命周期 Task/AsyncSequence 未取消，任务持有 self 并永久挂起。

定位动作

bash
# Xcode 调试会话：Debug Memory Graph → 选中 VC → 查看引用链
xcrun xctrace record --template "Leaks" --device-name "iPhone 15" \
  --time-limit 30s --attach MyApp
xcrun xctrace record --template "Allocations" --device-name "iPhone 15" \
  --time-limit 30s --attach MyApp
leaks MyApp --list

运行方式：先进入页面再 attach；leaks 只对模拟器/宿主进程有效，真机用 Memory Graph/Allocations。Leaks 对循环引用常漏报，不能只看它。

  • 工具与看什么：Memory Graph 的引用链能直接指出「谁持有 VC」；Allocations 用 Mark Generation 看每次进出后的 Persistent Bytes 是否单调上升；leaks --list 只作补充；deinit 断点/日志是最便宜的存活探针。

验证与排除

  • H1：Memory Graph 引用链为 VC → 闭包 → self；把回调改成 [weak self] 后 deinit 打印 → 确认；若引用链不经过闭包，排除 H1。
  • H2：viewWillDisappear 主动 invalidate 后 VC 释放；不 invalidate 则不释放 → 确认 H2；若 Timer 已正确失效仍不释放，排除 H2。
  • H3：代码里只有 selector 形式（iOS 9+ 自动注销）则不成立，排除 H3；若用了 block 形式且 token 未移除，移除后释放 → 确认。
  • H4：Memory Graph 显示单例/静态字典到 VC 的强引用；清缓存或改为 weak 后释放 → 确认；若引用链不经过单例，排除 H4。
  • H5：存在未取消的长任务，cancel() 后释放 → 确认；若没有跨页面存活的 Task，排除 H5。

修复要点

  • ✅ 闭包一律 [weak self]（或明确 guard let self 的短生命周期场景），delegate 用 weak。
  • ✅ Timer/DisplayLink 在页面消失或 deinit 前 invalidate()；更推荐 block 形式并用弱引用避免 target 持有。
  • ✅ 保存通知 token 与 NSKeyValueObservation，在 deinit/退出时移除；不要依赖「系统会自动清理」。
  • ⚠️ 缓存要设上限与淘汰策略；取消 Task 后确认回调不会更新已释放 UI。预期 20 次进出后内存稳定在 ±10MB；回归加一条「弱引用断言」单测，CI 可跑。

INC-09 EXC_BAD_ACCESS 野指针 ​

症状

  • 线上偶发 EXC_BAD_ACCESS (SIGSEGV)，地址常见 0x0000000000000010 一类近空指针或已释放对象地址；栈顶多在 objc_msgSend。
  • Debug 包难复现、Release 偶发；某些页面关闭后必现，Zombie 模式下会打印「message sent to deallocated instance」。

假设树

  • H1：悬垂引用——unowned/unsafe_unretained/assign 指向的对象已释放，随后被访问。
  • H2：MRC/桥接代码过度释放（autorelease 后又 release、CFRelease 重复）。
  • H3：MRC 下栈 Block 未 copy 到堆，函数返回后异步执行，访问已销毁栈内存。
  • H4：多线程数据竞争——A 线程释放/修改对象，B 线程同时读取；集合无锁并发修改。
  • H5：CFType/Unmanaged 所有权用错（passUnretained、Get 规则误用）导致 use-after-free。

定位动作

bash
# 1) 符号化崩溃报告（symbolicatecrash 不在 PATH，用 Xcode 内置脚本路径）
SYMBOLICATE=/Applications/Xcode.app/Contents/SharedFrameworks/DVTFoundation.framework/Versions/A/Resources/symbolicatecrash
$SYMBOLICATE report.crash MyApp.app.dSYM
# 2) 已知镜像加载地址时用 atos（地址取自崩溃报告 Binary Images）
atos -arch arm64 -o MyApp.app.dSYM/Contents/Resources/DWARF/MyApp \
  -l 0x1024c0000 0x1024c1234
# 3) 复现：Scheme → Diagnostics 勾选 Zombie Objects / Address Sanitizer / Malloc Scribble
# 4) 分配历史（需 MallocStackLogging=1；模拟器/宿主进程）
malloc_history 12345 0x600002a0c000

  • 工具与看什么：atos 把地址还原到函数/行号；Zombie Objects 打印被释放对象的类与释放后消息；ASan 给出 heap-use-after-free 的分配栈与释放栈；malloc_history 还原该地址的分配来源；TSan 用于 H4。

验证与排除

  • H1：Zombie 输出对象类名且崩溃点紧跟消息发送 → 确认悬垂引用；ASan 的 free 栈与 crash 栈能对应。若对象仍存活（无 zombie 记录），排除 H1。
  • H2：崩溃栈出现重复 objc_release/CFRelease，且代码含 MRC 或手动桥接 → 确认；若工程全 ARC 且无 CF 代码，排除 H2。
  • H3：崩溃发生在函数返回后的异步回调，代码存在未 copy 的栈 Block（MRC）→ 确认；ARC 工程通常自动 copy，排除 H3。
  • H4：TSan 报 data race，且 free/read 来自不同线程 → 确认；若单线程稳定复现，排除 H4。
  • H5：崩溃涉及 CF 对象，ASan 显示重复释放或释放后使用，且存在 Unmanaged/passUnretained → 确认；否则排除 H5。

修复要点

  • ✅ 生命周期不保证时用 weak，unowned 只用于确定「被引用者活得更久」；delegate/back reference 一律 weak。
  • ✅ 异步使用对象前先强持有（guard let self/局部强引用），跨线程共享加锁或收敛到 actor/串行队列。
  • ✅ Block 属性声明 copy；CF 对象严格按 Create/Copy/Get 规则配对释放。
  • ⚠️ 修复后开 ASan/TSan 跑核心路径与压力测试，Zombie 只用于定位；确认没有把崩溃变成静默错误。回归用同一崩溃指纹在线上看是否归零。

INC-10 强制解包 / 数组越界崩溃 ​

症状

  • 崩溃集中在 Fatal error: Unexpectedly found nil while unwrapping an Optional value 与 Index out of range；某次后端字段调整后崩溃率升到 5%。
  • 只在特定账号/特定列表为空时复现，Debug 手工点不出，Release 全量可见；崩溃栈顶多在业务解析/取下标处。

假设树

  • H1：对可空字段使用 !/as!/try!，服务端返回 null 或类型变化即崩。
  • H2：数组直接下标 [0]、remove(at:)、prefix/区间取子串越界（空列表、长度变化）。
  • H3：Codable/JSON 模型类型不匹配（Int vs String、null）后用 try! 或手工强转。
  • H4：多线程并发修改数组/字典，遍历或取下标时结构已变。
  • H5：IBOutlet/Storyboard 连线缺失或类名错误，隐式解包 IBOutlet 为 nil。

$SYMBOLICATE report.crash MyApp.app.dSYM
# 控制台 fatal error（真机用 Console.app 或 Xcode Devices 日志）
log show --last 2h --predicate 'process == "MyApp" AND eventMessage CONTAINS "Fatal error"'

运行方式：终端符号化离线报告；log show 对模拟器/宿主有效，真机日志通过 Console.app 或 Xcode Devices 导出。线上按崩溃指纹聚合（MetricKit MXCrashDiagnostic / 第三方平台）。

  • 工具与看什么：崩溃栈的函数与行号直接指向强解包/取下标位置；按「异常类型 + 堆栈指纹」分群，看是否集中在同一接口/页面；对照该版本后端字段变更与灰度人群。

验证与排除

  • H1/H3：把 null、缺字段、Int/String 错型的响应喂给解析单测，能复现崩溃 → 确认；若构造异常数据也不崩，排除 H1/H3。
  • H2：构造空数组、单元素数组、超长/超短字符串跑边界测试；[0]/remove(at:)/substring 崩溃 → 确认；若边界测试全过，排除 H2。
  • H4：TSan 或 Main Thread Checker 报并发修改，崩溃栈含 __NSArrayM 变更 → 确认；若串行访问仍崩，排除 H4。
  • H5：从 Storyboard 实例化 VC 的 UI 测试中 outlet 为 nil，崩溃发生在 viewDidLoad → 确认；若崩溃与 UI 无关，排除 H5。
  • 还可对照灰度/版本：仅新版本出现且伴随接口字段变更，优先 H1/H3；老版本同样崩，优先 H2/H4。

修复要点

  • ✅ 用 guard let/if let/可选链替代 !；解析失败走错误分支并上报，不 try!。
  • ✅ 提供安全下标（越界返回 nil 并记录日志，参照第 3 章「安全数组」），删除元素前校验 index。
  • ✅ 服务端契约校验：字段可选性、类型、空数组都进单测夹具；Codable 用 init(from:) 做兼容解析。
  • ⚠️ 安全下标/默认值不能吞掉问题：必须配日志与告警，否则数据错误被静默掩盖。IBOutlet 用断言或可选绑定，并在 UI 测试覆盖。回归加 null/空数组夹具与崩溃率看板。

INC-11 KVO/通知移除不当或线程问题崩溃 ​

症状

  • 关闭详情页时偶发崩溃：移除 KVO 时报「not registered as an observer」一类异常，或回调里访问已释放对象导致 EXC_BAD_ACCESS。
  • 另一类崩溃发生在刷新回调：Main Thread Checker 报 UI API 在后台线程调用；打开页面后立即返回、异步刷新稍后到达时最易复现。

假设树

  • H1：removeObserver 与 addObserver 不配对，或两条关闭路径重复移除。
  • H2：观察者先于被观察对象释放，KVO 仍向其发送通知（野指针）。
  • H3：被观察对象 dealloc 时仍有观察者，动态子类 isa 恢复/dealloc 阶段崩溃。
  • H4：block 形式通知 token 未移除，block 在 self 释放后执行并访问 self。
  • H5：KVO/通知回调在非主线程，回调中更新 UI 或访问非线程安全状态。

验证与排除

  • H1：崩溃原因包含「not registered as an observer」，且代码存在多路径 remove → 确认；若每个 add 都严格配对且仅移除一次，排除 H1。
  • H2：Zombie 打印观察者类名，被观察对象仍存活 → 确认；若观察者仍存活，排除 H2。
  • H3：崩溃栈落在 dealloc/objc_destructInstance，且被观察对象释放前未移除 → 确认；若崩溃与 dealloc 无关，排除 H3。
  • H4：崩溃发生在通知 block 内且 self 已释放；移除 token 后不再崩 → 确认；若只用 selector 形式且系统自动注销，排除 H4。
  • H5：Main Thread Checker 报「UI API called on a background thread」，回调线程与主线程不同 → 确认；若回调本就在主线程，排除 H5。

修复要点

  • ✅ 新代码用 NSKeyValueObservation 并把 token 存进数组，随对象释放自动失效；Swift 属性需 @objc dynamic 才可 KVO。
  • ✅ 老代码固定「谁 add 谁 remove」，用唯一 context 区分 keyPath；deinit 中只移除确实注册过的观察。
  • ✅ 通知 token 在 deinit/退出时移除，block 内 [weak self]；回调切回主线程再碰 UI。
  • ⚠️ 移除时机要早于被观察对象释放，避免 dealloc 顺序问题；主线程派发要防重复刷新。回归用「打开-立即返回-刷新到达」的竞态用例 + 真机压力测试。
