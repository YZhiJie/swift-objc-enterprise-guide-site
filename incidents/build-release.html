INC-17 包体膨胀：资源未压缩/重复资源 ​

症状

  • 一次版本从 86 MB 涨到 142 MB，App Store Connect 出现体积警告，低存储用户下载转化下降。
  • App Thinning Size Report.txt 显示资源占绝对大头，主二进制变化很小；同一批 onboarding 图片在多个 bundle 里都能看到。
  • 本地 Archive 大小与用户实际下载大小不一致，团队对「到底超没超」意见不统一。

假设树

  • H1：大图/视频未压缩，且以普通 bundle 资源平铺，没有进 Asset Catalog，享受不到系统压缩与按需变体。
  • H2：同一套资源被主 App 与 PlugIns 下的 Widget/Share Extension 各复制一份，多个 bundle 都打进同一个 IPA。
  • H3：多语言 .lproj、旧版本遗留图片/xib 未清理，历史资源持续累积。
  • H4：三方 SDK 打包了示例资源、测试图片或未裁剪的二进制，主工程无法感知。
  • H5：导出方式不是 App Store 分发，App Thinning 未生效，拿 IPA 总大小误判用户下载体积。

定位动作

bash
# 1. 归档并按 App Store 方式导出，生成各设备变体的体积报告
xcodebuild archive -workspace MyApp.xcworkspace -scheme MyApp \
  -configuration Release -archivePath build/MyApp.xcarchive
xcodebuild -exportArchive -archivePath build/MyApp.xcarchive \
  -exportPath build/out -exportOptionsPlist ExportOptions.plist

# 2. 拆 IPA 看未压缩资源清单，按大小排序找异常项
unzip -l build/out/MyApp.ipa | sort -k1 -nr | head -40

# 3. 对同名资源做内容哈希，确认是否真的重复
shasum -a 256 build/out/Payload/MyApp.app/Assets.car build/out/Payload/MyApp.app/*.png

# 4. 看主二进制与资源目录各占多少
size -m build/out/Payload/MyApp.app/MyApp
du -sh build/out/Payload/MyApp.app

运行方式：终端在归档产物目录执行；App Thinning Size Report.txt 在导出目录中，需按设备变体阅读；unzip/shasum/du 用于资源级下钻。

  • 工具与看什么：App Thinning 报告看「Download Size」与「Install Size」的差值；unzip -l 看大文件路径与所属 bundle；shasum 对比同名文件是否内容相同；du 定位资源目录。

验证与排除

  • 排除 H1：若大图/视频在 MyApp.app 根目录而不是 Assets.car，且压缩后体积明显下降，H1 成立。
  • 排除 H2：在 IPA 里同时找到 MyApp.app 与 MyApp.app/PlugIns/*.appex 下同名且同哈希的资源，H2 成立。
  • 排除 H3：统计 .lproj 数量并和上一版资源清单对比；删掉遗留资源后体积下降，确认 H3。
  • 排除 H4：按路径定位到 Frameworks/*.framework 内的资源，对照 SDK 文档确认是示例/测试资源，H4 成立。
  • 排除 H5：对比 App Thinning 报告中单设备下载体积与 IPA 总大小；若单设备体积远低于 142 MB，说明是统计口径问题，不是真实包体回归。

修复要点

  • 图片进 .xcassets，用 HEIF/WebP 或 pngquant 压缩；视频/离线地图等大资源改用 On-Demand Resources，首装不携带。
  • 共享资源收敛到一个 resource bundle/framework，主 App 与扩展都引用它，禁止每个 target 各拷一份。
  • 清理未引用资源与旧本地化目录，三方 SDK 的示例资源在集成时剔除；归档脚本输出资源 Top 20 清单。
  • CI 用 App Thinning 报告做单设备体积门禁，超过基线 3% 失败；预期收益常见 20%~40% 资源缩减。
  • 风险：过度压缩影响画质、ODR 首次进入需下载；需要按业务场景设置压缩质量与预取策略。

INC-18 动态库/静态库重复符号与单例双份 ​

症状

  • 链接日志出现 duplicate symbol '_OBJC_CLASS_$_NetworkManager'，或运行时打印 Class NetworkManager is implemented in both ... One of the two will be used. Which one is undefined.。
  • 单例内存状态出现两份：登录态在一处已更新、另一处仍是旧值；埋点被重复上报。
  • 只在某次依赖调整后出现，Debug 偶发、Release 归档更明显。

假设树

  • H1：同一个库被 SPM 与 CocoaPods 各引一份，两个构建产物都参与链接。
  • H2：动态 framework 与静态库同时链接，或同一 framework 在 Frameworks 目录出现两份。
  • H3：多个自研动态 framework 各自静态链接同一 Core 静态库，Core 的 ObjC 类与单例被复制进每个 framework。
  • H4：OTHER_LDFLAGS 带 -all_load/-force_load，把两个归档里的同名目标文件全量拉入。
  • H5：ObjC 类名没有前缀，与三方 SDK 同名，链接时被覆盖或合并，并非真正的重复依赖。

定位动作

bash
# 1. 保留完整构建日志，抓重复符号与两个来源路径
xcodebuild build -workspace MyApp.xcworkspace -scheme MyApp \
  -configuration Debug -destination 'generic/platform=iOS Simulator' 2>&1 | tee build.log

# 2. 看最终二进制依赖了哪些动态库
otool -L build/Debug-iphonesimulator/MyApp.app/MyApp

# 3. 看符号由哪个目标文件定义（-m 显示来源）
nm -m build/Debug-iphonesimulator/MyApp.app/MyApp | grep NetworkManager

# 4. 核对链接参数与库搜索路径
xcodebuild -showBuildSettings -workspace MyApp.xcworkspace -scheme MyApp \
  | grep -E 'OTHER_LDFLAGS|LIBRARY_SEARCH_PATHS|FRAMEWORK_SEARCH_PATHS'

运行方式：终端在工程根目录执行；build.log 搜索 duplicate symbol、implemented in both；nm -m 对最终二进制与各 framework 二进制分别执行。

  • 工具与看什么：otool -L 看是否存在同名的两个 @rpath 依赖；nm -m 看符号定义来自哪个 .o/framework；构建日志看重复符号的两条路径；showBuildSettings 看是否有粗暴的全量加载参数。

验证与排除

  • 排除 H1：Package.resolved 与 Podfile.lock 同时出现同一产品，且 nm -m 显示两个不同构建目录的 .o，H1 成立。
  • 排除 H2：otool -L 出现同一 framework 两次，或 App 内 Frameworks 目录存在两份同名产物，H2 成立。
  • 排除 H3：分别对 MyKit.framework 与 MyFeature.framework 执行 nm -m，若两者都定义 NetworkManager，H3 成立。
  • 排除 H4：showBuildSettings 的 OTHER_LDFLAGS 含 -all_load/-force_load；移除后重复符号消失，确认 H4。
  • 排除 H5：符号名与三方 SDK 完全同名、且依赖树里没有重复产品，属于命名冲突；加前缀后验证。

修复要点

  • 建「依赖归属表」，同一库只能有一个来源；迁移期新增依赖一律 SPM，存量 Pod 逐个替换后 pod deintegrate。
  • Core 只链接一次：要么做成独立动态 framework 供多方依赖，要么在各产物中不重复静态打包；Xcode 15+ 可用 Mergeable Libraries 在 Release 合并。
  • 移除 -all_load/-force_load，仅对确需的库使用 -force_load 并限定路径；ObjC 类统一加团队前缀。
  • CI 把 duplicate symbol 从警告升级为失败；预期收益是单例状态一致、埋点不再双报。
  • 风险：静态改动态会增加 dylib 装载成本，合并库会改变产物形态，需要回归启动耗时与包体。

INC-19 证书过期/描述文件不匹配导致签名失败 ​

症状

  • 归档后在导出阶段失败：No signing certificate "iOS Distribution" found，或 Provisioning profile ... doesn't include signing certificate。
  • 另一类报错是 Provisioning profile ... doesn't match the entitlements，或 codesign failed with exit code 1。
  • 上一周还能正常出包，证书续期或新增能力后突然失败，开发同学本地却可能正常。

假设树

  • H1：发布证书过期或被吊销，钥匙串里只剩旧证书。
  • H2：描述文件与 Bundle ID/证书不匹配，例如用了开发 profile 或另一个 App 的 App Store profile。
  • H3：Entitlements 与描述文件能力不一致（Push、App Groups、Associated Domains 新增后未同步 profile）。
  • H4：钥匙串里有证书但没有私钥，.p12 未导入或导入到了错误的 keychain。
  • H5：导出配置错误：ExportOptions.plist 的 method/teamID 不对，或 manual/automatic 签名方式冲突。

定位动作

bash
# 1. 本机有哪些可用签名身份，关注有效期与证书类型
security find-identity -v -p codesigning

# 2. 看构建实际使用的签名配置
xcodebuild -showBuildSettings -workspace MyApp.xcworkspace -scheme MyApp -configuration Release \
  | grep -E 'CODE_SIGN|DEVELOPMENT_TEAM|PROVISIONING_PROFILE'

# 3. 看归档产物的签名与 entitlements
codesign -dv --verbose=4 build/MyApp.xcarchive/Products/Applications/MyApp.app
codesign -d --entitlements :- build/MyApp.xcarchive/Products/Applications/MyApp.app

# 4. 解码描述文件，核对 App ID、证书、能力与有效期（参数待真机验证）
security cms -D -i build/MyApp.xcarchive/Products/Applications/MyApp.app/embedded.mobileprovision | plutil -p -

# 5. 核对导出配置
plutil -p ExportOptions.plist

  • 工具与看什么：find-identity 看 identity 是否有效、是否带私钥；codesign -dv 看 Authority/TeamIdentifier；codesign -d --entitlements 与 profile 中的 Entitlements 对照；plutil -p 看 method、teamID、signingStyle。

验证与排除

  • 排除 H1：find-identity 无有效 identity，或证书过期日期已过，codesign -dv 显示旧 Authority，H1 成立。
  • 排除 H2：profile 的 application-identifier 与 Bundle ID 不一致，或 profile 类型为 Development，H2 成立。
  • 排除 H3：codesign -d --entitlements 中的能力在 profile 的 Entitlements 里不存在，H3 成立。
  • 排除 H4：find-identity 能列出证书但签名报 no identity/无法建链，检查 Keychain 中证书是否带私钥，H4 成立。
  • 排除 H5：ExportOptions.plist 的 method 与目标渠道不符，或 CI 设置 Automatic 却指定了手写 profile，H5 成立。

修复要点

  • 证书过期走 match 重新生成并同步；CI 只读拉取，管理员本地负责写入，禁止在流水线里自动创建证书。
  • .p12 与私钥成对导入专用 keychain，构建结束清理；描述文件在能力变更后重新生成，Entitlements 与 profile 逐项对齐。
  • Config/Release.xcconfig、Build Settings 与 ExportOptions.plist 三处签名参数保持一致；归档前先跑 security find-identity 与 codesign 预检。
  • 预期收益：签名失败从「发布日阻塞」变成构建前可发现；风险是吊销旧证书会影响其他机器，必须在发布窗口外执行并通知团队。

INC-20 CI 自动签名 revoke 冲突 ​

症状

  • 多台 CI runner 并行构建时随机失败：The certificate ... has been revoked、Your account already has a signing certificate。
  • 同一个发布证书的序列号每隔几次构建就变化，TestFlight 上传偶发失败，本地开发却正常。
  • 事故集中在「多个人同时加设备/多人同时触发发布」的时段。

假设树

  • H1：CI 仍开启 automatic signing，证书名额满时 Xcode 自动吊销旧证书再创建新证书。
  • H2：多台 runner 共享同一 Apple ID 与钥匙串，并发写入证书/描述文件，互相覆盖。
  • H3：开发者本地自动签名与 CI 发布证书同类型，本地新增设备或续期时顶掉 CI 的证书。
  • H4：match 实际不是只读：CI lane 传了 readonly: false，或直接用了 development 类型去写仓库。
  • H5：Xcode 自动生成 profile，覆盖了 match 下发的描述文件，导致每次构建 UUID 漂移。

定位动作

bash
# 1. 在 runner 上看签名身份与证书序列/有效期
security find-identity -v -p codesigning

# 2. 看 CI 是否仍为 Automatic，以及 profile 指定方式
xcodebuild -showBuildSettings -workspace MyApp.xcworkspace -scheme MyApp -configuration Release \
  | grep -E 'CODE_SIGN_STYLE|CODE_SIGN_IDENTITY|PROVISIONING_PROFILE_SPECIFIER|DEVELOPMENT_TEAM'

# 3. 保留构建日志并抓证书/描述文件动作
grep -E 'revoke|Revoking|Creating new certificate|Provisioning profile|Match' build.log

# 4. 核对 match 调用参数是否只读
grep -n 'match' fastlane/Fastfile

运行方式：终端在 runner 与仓库根目录执行；build.log 需由 xcodebuild/fastlane 完整保留，不能只留最后几十行。

  • 工具与看什么：find-identity 对比不同 runner 的证书序列是否一致；showBuildSettings 看 CODE_SIGN_STYLE 是否 Automatic；日志看 revoke/创建证书的时间点是否与并行构建重合；Fastfile 看 readonly。

验证与排除

  • 排除 H1：若 CODE_SIGN_STYLE=Automatic 且日志出现 revoke/创建新证书，H1 成立；切 Manual 后稳定可复验。
  • 排除 H2：两台 runner 拉取到同一证书序列，且失败时间与 keychain 写入重叠，H2 成立。
  • 排除 H3：吊销时间与开发者本地登录/新增设备时间吻合，且本地证书类型与 CI 相同，H3 成立。
  • 排除 H4：Fastfile 或 lane 日志显示非只读写入，match 日志出现写仓库而不是读取，H4 成立。
  • 排除 H5：对比多次构建的 profile UUID；UUID 每次变化且不受 match 控制，H5 成立。

修复要点

  • CI 全面切手动签名：固定 certificate/profile，CODE_SIGN_STYLE=Manual，关闭 -allowProvisioningUpdates。
  • match(type: "appstore", readonly: true) 在 CI 强制只读；只有发布管理员机器保留写权限，match 仓库加锁并串行发布。
  • 开发证书与发布证书分两套：开发者本地自动签名只碰开发证书，CI 永不创建发布证书。
  • Runner 使用专用 keychain，构建后清理证书与 profile；预期收益是并行构建不再互踩。
  • 风险：人工维护证书增加发布前操作，需要用预检 lane 和文档抵消；不要用共享 Apple ID 图省事。

INC-21 灰度放量后崩溃率上升需回滚 ​

症状

  • 版本 4.2.0 分阶段发布到 20% 后，会话无崩溃率从 0.997 跌到 0.975，客服开始收到结算页闪退反馈。
  • 崩溃聚合里新出现 EXC_BAD_ACCESS，栈指向 CheckoutViewController；部分用户仍停留在旧版本且指标正常。
  • 团队需要在一小时内决定「继续放量、暂停还是回滚」，但群里同时有人怀疑是后端变更。

假设树

  • H1：新构建存在代码回归，崩溃栈只出现在 4.2.0，旧版本无同类栈。
  • H2：同版本内新功能 Flag 放量导致，只有 treatment 桶用户崩溃，control 桶干净。
  • H3：后端接口或远程配置变更，跨版本同时出现，与新包无直接关系。
  • H4：指标归因问题：Adoption 过低、崩溃上报延迟或 dSYM 版本错配，导致误报。
  • H5：特定机型/系统组合放大，新代码路径只在这些设备触发，整体崩溃率被小样本拉高。

定位动作

bash
# 1. 确认线上包版本与 build，避免看错样本
plutil -p MyApp.app/Info.plist | grep -E 'CFBundleShortVersionString|CFBundleVersion'

# 2. 核对工程里的版本号与归档是否一致
xcodebuild -showBuildSettings -workspace MyApp.xcworkspace -scheme MyApp -configuration Release \
  | grep -E 'MARKETING_VERSION|CURRENT_PROJECT_VERSION'

# 3. 拉取最近一小时崩溃前后系统日志（真机日志建议先在 Console.app 导出）
log show --last 1h --predicate 'process == "MyApp"' --style compact

# 4. 复现时实时看结算链路与 Flag 决策
log stream --predicate 'subsystem == "com.example.flags" OR subsystem == "com.example.checkout"' --level debug

  • 工具与看什么：plutil -p 看崩溃样本版本；showBuildSettings 确认发出去的 build 与 dSYM 匹配；日志看崩溃前最后一步与 Flag source；Organizer 看符号化栈与设备/OS 分布。

验证与排除

  • 排除 H1：符号化栈只落在 4.2.0 的 dSYM，4.1.x 无同栈；若旧版本也出现，H1 不成立。
  • 排除 H2：把崩溃事件与 Flag 决策关联，若 treatment 桶崩溃率显著高于 control，H2 成立；两边一致则排除。
  • 排除 H3：后端变更时间点前后，旧版本崩溃率是否同步上升；旧版本稳定则 H3 不成立。
  • 排除 H4：Adoption 已高于 5%，崩溃上报无延迟，dSYM UUID 与包匹配；若样本极小或符号错版本，先 hold 而不是 rollback。
  • 排除 H5：按机型/OS 分群；若单一机型占比异常且新代码路径只在该机型执行，H5 是放大因素，但仍需回答 H1/H2 的根因。

修复要点

  • 按发布门禁决策表执行：崩溃率跌破回滚线（如 0.98）立即 rollback；处于 hold 区间则暂停放量等修复版。
  • 第一动作优先用 Flag 的 remoteOverride 关掉新结算流程，秒级止血；同时暂停 Phased Release，不急着从 App Store 撤版。
  • 只有新装用户也受影响时才考虑撤版；保留 archive、dSYM 与构建日志，热修版本走加速审核通道。
  • 回滚后持续观察 24 小时，确认 crashFree 回到基线，再做复盘与灰度重放。
  • 预期收益：把「群里讨论」变成可执行的分钟级止血；风险是误回滚损失功能进度，或 Flag 关不掉原生无条件崩溃路径。

INC-22 Feature Flag Kill Switch 未生效 ​

症状

  • 运维把 checkout_v2 的 remoteOverride 设为 false，看板显示开关已生效，但线上仍有约 30% 用户看到新结算流程。
  • 内部员工与部分城市用户始终命中新流程；客服反馈与 Flag 看板的「已关闭」状态矛盾。
  • 客户端日志里同一用户有时 source=remoteOverride，有时 source=targeting，行为不稳定。

假设树

  • H1：评估瀑布顺序错误，remoteOverride 没有放在第一级，targeting/bucket（SHA-256 分桶）先命中并短路。
  • H2：客户端配置缓存未刷新（只启动拉一次、TTL 过长或离线），新的 override 没有到达设备。
  • H3：环境或 key 配错：prod 开关写进了 staging namespace，或代码读取的 key 与平台配置不一致。
  • H4：本地缓存/本地 override 的优先级高于远程值，远程下发后被本地旧值覆盖。
  • H5：新流程代码路径没有真正接 Flag，或存在两个 SDK 实例，业务读的是旧实例/默认值。

定位动作

bash
# 1. 实时看 Flag 决策日志：key、value、source、config version
log stream --predicate 'subsystem == "com.example.flags"' --level debug

# 2. 统计最近 10 分钟各 source 的分布，确认 override 是否被绕过
log show --last 10m --predicate 'subsystem == "com.example.flags"' --style compact

# 3. 看包里默认配置与 key 名，排除默认值本身就是 treatment
plutil -p MyApp.app/Flags.plist

# 4. 对比服务端实际下发内容（token 从 CI Secret 注入，不要硬编码）
curl -v -H "Authorization: Bearer $TOKEN" https://config.example.com/v1/flags

验证与排除

  • 排除 H1：若用户已拿到 override 但仍返回 source=targeting/bucket，且代码中 override 不是第一级，H1 成立。
  • 排除 H2：日志里的 config version/timestamp 早于平台发布时间；强制刷新或清缓存后值翻转，H2 成立。
  • 排除 H3：下发 payload 的 environment 为 staging，或 key 与代码不一致，H3 成立。
  • 排除 H4：删除本地缓存后远程值生效，或日志显示本地 override 覆盖远程，H4 成立。
  • 排除 H5：新流程路径没有任何 Flag 评估日志，或两个 SDK 实例各打印一次决策，H5 成立。

修复要点

  • 固定四级瀑布：remoteOverride → targeting → bucket → default，每级命中即短路；用参数化单测锁顺序，覆盖「override 为 false 但用户命中定向」的用例。
  • 配置下发带版本号与 ETag，前台恢复/关键操作前刷新，设置合理 TTL；override 变更走高优先级通道。
  • 生产环境做 namespace/key 白名单校验，启动时打一条配置摘要日志；禁止本地 override 进入生产构建。
  • 新流程所有入口统一走同一个 Flag 评估函数，避免 SDK 多实例；每次评估记录 source 供审计。
  • 预期收益：Kill Switch 秒级真实生效；风险是缓存刷新增加请求、默认值若为新行为会在配置服务不可用时放大故障，default 必须保持旧行为。
