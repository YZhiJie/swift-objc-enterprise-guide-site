INC-23 隐私清单缺失 / Required Reason API 原因码错误被拒审 ​

症状

  • 提交审核后 Resolution Center 邮件点名隐私清单问题（如 ITMS-91053 / ITMS-91056），指出缺少 NSPrivacyAccessedAPICategoryUserDefaults 声明或原因码无效。
  • 本地 archive 成功、upload 也成功，但构建在 App Store Connect 长时间「正在处理」，随后审核被拒；邮件同时点名某个三方 SDK。

假设树

  • H1：主 App 根本没有 PrivacyInfo.xcprivacy，或文件没有加入主 target 的 Copy Bundle Resources，归档产物根目录不存在该文件。
  • H2：文件存在，但原因码与真实用法不符：UserDefaults(suiteName:) 共享 App Group 却只填了主 App 自用的 CA92.1。
  • H3：三方二进制 SDK 没有自带隐私清单，主工程无法替三方代码声明 accessed API。
  • H4：NSPrivacyTracking 与 NSPrivacyCollectedDataTypes 自相矛盾：实际做归因却填 false，或收集类型漏报。
  • H5：清单 plist 语法合法但位置/命名错误，例如放在子目录、文件名大小写不符或重复 key。

定位动作

bash
# 1. 找到最近归档，检查主 App 根目录清单
find ~/Library/Developer/Xcode/Archives -maxdepth 2 -name "*.xcarchive" -print
APP=MyApp.xcarchive/Products/Applications/MyApp.app
ls -l "$APP/PrivacyInfo.xcprivacy"
plutil -lint "$APP/PrivacyInfo.xcprivacy"
plutil -p "$APP/PrivacyInfo.xcprivacy"

# 2. 列出包内所有清单（含三方 framework 与扩展）
find "$APP" -name "PrivacyInfo.xcprivacy" -print

# 3. 核对 App Group 用法与 entitlements 是否一致
codesign -d --entitlements :- "$APP" | plutil -p -

  • 工具与看什么：App Store Connect → 对应构建 → Resolution Center 邮件点名的 SDK/键名；Organizer 归档告警；plutil -p 重点看 NSPrivacyAccessedAPITypes 下的 NSPrivacyAccessedAPITypeReasons。

验证与排除

  • 排除 H1：ls 能看到文件、plutil -lint 返回 OK 且文件位于 .app 根目录，说明清单已随包。
  • 确认 H2：代码中确有 UserDefaults(suiteName: "group.com.enterprise.retailops")，而清单只写 CA92.1。按 08 章口径，主 App 自用偏好域才是 CA92.1，App Group 共享是 1C8F.1；文件时间戳 C617.1、系统启动时间 35F9.1（App 内绝对事件时间 8FFB.1）、磁盘空间 E174.1 / 85F4.1。
  • 排除 H3：find 能找到三方 SDK 自带清单，且拒审邮件没有点名该 SDK；若邮件点名，则 H3 成立，交回 SDK 供给方处理。
  • 排除 H4：NSPrivacyTracking、NSPrivacyTrackingDomains、NSPrivacyCollectedDataTypes 与隐私政策、SDK 实际行为逐项一致。
  • 排除 H5：plutil -lint 通过，文件名与根目录位置正确；否则修正后重新归档。

修复要点

  • 将清单加入主 target（file target membership / Copy Bundle Resources），把 App Group 场景的原因码改为 1C8F.1；三方 SDK 升级到自带清单的版本，禁止主工程替它声明。
  • 重新 Archive 后先在 Organizer 检查 Privacy Manifest 告警，再上传；旧归档不可复用，因为清单是包内资源。
  • 风险/回归：改清单会改变审核材料，需同步隐私政策；CI 增加 plutil -lint 与原因码白名单检查，缺少清单直接 fail。

INC-24 埋点上报 PII 未脱敏 ​

症状

  • 数据平台抽样发现 attributes 里有明文手机号或邮箱；安全扫描在埋点样本中命中 PII 规则，合规团队要求说明。
  • 真机日志里直接看到完整手机号；同一个事件在服务端按 event_name 抽样仍能还原用户身份。

假设树

  • H1：脱敏只做在 UI 展示层，EventPipeline.record 入缓冲时仍保存原值，上传链路直接透传。
  • H2：脱敏正则只处理「整个值就是手机号/邮箱」的情况；备注、URL query 等值内嵌 PII 没有被替换。
  • H3：存在绕过管道的数据通道，例如三方分析 SDK 直传，或某个后台任务自己拼请求体。
  • H4：历史版本或 QA 造的数据本就含原文，且服务端没有按留存策略清理；schema 也没有 PII 字段清单可供拒绝。
  • H5：PII 其实漏在 Logger / OSLog / 崩溃面包屑里，而不是埋点 payload 本身。

定位动作

bash
# 真机上抓埋点日志（Console.app 可用同一 predicate）
log stream --predicate 'subsystem == "com.enterprise.analytics"' --info --debug

# 回放脱敏用例，确认打码发生在入缓冲之前
swift test --filter EventPipelineTests

# 查找直接打印原始属性的位置
grep -Rn "attributes" Sources --include="*.swift" | grep -i "log\|print"

  • 工具与看什么：EventPipeline 单测断言「入缓冲前已打码」；网络侧确认是否只有唯一埋点域名；数据平台按 app_version 抽样定位首次出现原值的版本。

验证与排除

  • 排除 H1：单测在 record 之后读取缓冲，值已是 138****5678 / a***@example.com；若缓冲仍是原值，则 H1 成立，脱敏位置需要前移。
  • 确认 H2：输入 note=联系 13812345678 报价，输出仍含原号，说明正则只匹配独立值；这是最常见的漏点。
  • 排除 H3：抓包/域名白名单只见统一埋点端点，后台任务也走同一 actor；若出现第二个上传域名，则 H3 成立。
  • 排除 H4：原值样本的 app_version 低于脱敏上线版本，当前版本样本干净；否则按当前版本复现。
  • 排除 H5：日志检索不到 PII 模式，说明泄露只在埋点链路；若日志命中，则 H5 成立，需清理日志字段。

修复要点

  • 把打码固定在 record 入缓冲之前，覆盖嵌套属性与 URL query；对 phone / email / idCard / bankCard 建字段 deny-list，值内嵌也要替换。
  • 需要稳定关联用户或实验分桶时不要传原值：关联用带 salt 的 SHA-256，分桶用 SHA-256(experiment:salt:key) % 100；绝对禁止 Swift hashValue，其种子随进程随机。
  • 清理 Logger 中的原始属性，只记事件名与条数；服务端按留存策略删除历史原文；CI 增加「PII 正则扫描样本 payload」门禁。
  • 风险/回归：过度打码会损失分析粒度，需确认看板指标不依赖原文；回归用固定样本集断言脱敏输出稳定。

INC-25 权限用途说明缺失或过度申请 ​

症状

  • 审核被拒：ITMS-90683 指出缺少某个 NS*UsageDescription；或在首次启动就弹相机/定位，用户拒绝率明显偏高。
  • 审核意见指出申请了与当前功能无关的通讯录/定位权限，违反最小必要；扩展内触发相机时直接闪退。

假设树

  • H1：调用了授权 API 却没有对应的 Info.plist key，例如读相册缺 NSPhotoLibraryUsageDescription，只写不读却漏了 NSPhotoLibraryAddUsageDescription。
  • H2：key 存在但文案空泛（「需要相机权限」），没有说明具体场景，审核判定不合格。
  • H3：过度申请：启动或引导页就请求通讯录/定位，而真实功能只在某个二级页面用到。
  • H4：扩展 target 自己的 Info.plist 缺 key；主 App 的用途说明不会自动覆盖 Share/Widget 等扩展进程。
  • H5：三方 SDK 在后台申请了权限（如 IDFA、通讯录），但 App 的用途说明与隐私清单都没有对应申报。

定位动作

bash
APP=MyApp.xcarchive/Products/Applications/MyApp.app
plutil -p "$APP/Info.plist" | grep -i "UsageDescription"

for p in "$APP"/PlugIns/*.appex/Info.plist; do
  echo "== $p"
  plutil -p "$p" | grep -i "UsageDescription"
done

# 列出源码中的授权调用点，与 key 对照
grep -Rn "requestAuthorization\|requestAccess\|ATTrackingManager" \
  --include="*.swift" Sources

# 观察系统 TCC 在何时触发哪个服务
log stream --predicate 'subsystem == "com.apple.TCC"' --info

  • 工具与看什么：Resolution Center 邮件点名的 key；plutil -p 看每个 target 的 NS*UsageDescription；TCC 日志看服务类型与触发调用栈时间点。

验证与排除

  • 确认 H1：拒审邮件点名某个 key，且源码调用点确实没有对应声明；补 key 后本地触发不再闪退。
  • 确认 H2：文案只有「需要相机」这类通用描述，没有「扫码登录 / 拍摄工单附件」等场景；审核意见与之一致。
  • 确认 H3：TCC 日志显示弹窗发生在启动/引导页，而功能入口在后续页面；拒绝率数据佐证。
  • 排除 H4：扩展 Info.plist 里已有同名 key；若扩展触发即闪退且 plist 缺 key，则 H4 成立。
  • 排除 H5：三方 SDK 的隐私报告与 strings 检查未发现额外授权调用；若发现，则升级/移除 SDK 或补申报。

修复要点

  • 为每个 API 补精确用途说明，写清触发场景；把请求移动到真正的功能入口，拒绝后提供降级路径。
  • 删除不用的权限声明；相册选择优先用 PHPickerViewController（无需全库权限），仅保存图片时用 Add-only key。
  • 扩展 target 单独补齐 key；三方 SDK 要么升级到合规版本，要么移除。
  • 风险/回归：删权限可能破坏旧流程；新增 key 需要重新出包；CI 用脚本扫描 API 调用与 plist key 的对应关系，真机做权限重置回归。

INC-26 App 扩展被系统 jetsam 杀 ​

症状

  • 分享 4K 视频或连拍照片时 Share 扩展瞬间消失；Widget 长时间停在占位符；通知 Service 扩展超时后锁屏直接显示原始 payload。
  • Organizer 能看到扩展进程的终止记录，主 App 本身没有崩溃；用户反馈「点一下就没反应」。

假设树

  • H1：扩展把整张原图/整段 JSON 一次性解码进内存，峰值超过扩展内存上限（以十 MB 计，具体因设备与扩展类型而异，待真机验证）。
  • H2：扩展 target 链接了主 App 的重模块或大量依赖，静态初始化与缓存把基础内存抬高。
  • H3：扩展内有泄漏或循环引用，运行期间内存持续增长直至被杀。
  • H4：终止原因是 watchdog/CPU/时长限制（如 0x8badf00d），不是 jetsam——扩展里做了同步网络或长耗时任务。
  • H5：扩展依赖宿主 App 的状态或用了扩展内不可用的后台 URLSession，异常后反复重试直至被回收。

定位动作

bash
# 设备日志里区分内存终止与 watchdog
log show --last 2h --predicate 'eventMessage CONTAINS[c] "jetsam" OR eventMessage CONTAINS[c] "0x8badf00d"' --info

# 只看扩展进程
log stream --predicate 'process == "MyShareExtension" OR process == "MyWidgetExtension"' --level debug

# 检查扩展链接了哪些库与体积
otool -L "$APP/PlugIns/MyShareExtension.appex/MyShareExtension"

  • 工具与看什么：Organizer 的 Termination Reason / Exception Type；Instruments Allocations 以扩展 scheme 跑最坏输入；MetricKit MXDiagnosticPayload.crashDiagnostics 的 terminationReason（真机次日回传）。

验证与排除

  • 确认 H1：峰值内存与「解码原图」时刻重合，改为降采样后同一输入可存活；阈值按目标机型复测，标「待真机验证」。
  • 排除 H2：otool -L 与 link map 显示扩展未链接主模块/重依赖，包体没有异常膨胀。
  • 排除 H3：Memory Graph / Leaks 未见持续增长，内存曲线在解码后回落。
  • 确认 H4：终止原因为 0x8badf00d 或 CPU 超限，日志显示同步网络/长任务；此时不是内存问题。
  • 排除 H5：日志没有后台 URLSession 异常，扩展不依赖宿主内存状态。

修复要点

  • 进入扩展前用 ImageIO 生成缩略图（如 CGImageSourceCreateThumbnailAtIndex），限制输入数量与单文件大小；大 JSON 改流式解析。
  • 把重活移回主 App：扩展只把文件落 App Group 并 post Darwin 信号，主 App 后台任务接力；扩展 target 移除重依赖，禁止后台 URLSession。
  • 风险/回归：移交会增加一次延迟，用户可能在主 App 接力前杀掉进程；需持久化待处理队列。回归用最坏 payload 在目标机型 profile，断言峰值低于设备上限（待真机验证），并覆盖 watchdog 场景。

INC-27 App Group 共享容器读写失败 / 跨进程缓存不一致 ​

症状

  • 主 App 已写入快照，Widget 仍显示空数据或旧数据；Share 扩展找不到刚导入的文件；重装后短时正常，升级后又复发。
  • 日志出现 containerURL(forSecurityApplicationGroupIdentifier:) 返回 nil，或 UserDefaults(suiteName:) 读到 nil；主 App 与扩展看到的值不一致。

假设树

  • H1：App Group entitlement 只配在其中一个 target，或两端 group id 字符串不一致（拼写/大小写差异）。
  • H2：entitlement 正确，但代码里 UserDefaults(suiteName:) 的 suiteName 与 group id 不是同一个字符串。
  • H3：读写其实成功，但另一端持有旧缓存：App Group 写入不产生跨进程通知，Darwin 信号没发或发漏。
  • H4：存储正常但 schema 版本漂移：旧扩展二进制解码新快照失败，被上层当成「数据不可用」。
  • H5：写入非原子或文件保护等级过高：另一端读到半截 JSON；锁屏 Widget 在设备锁定后读不到 NSFileProtectionComplete 文件。

定位动作

bash
APP=MyApp.xcarchive/Products/Applications/MyApp.app
codesign -d --entitlements :- "$APP" | plutil -p -
codesign -d --entitlements :- "$APP/PlugIns/MyWidget.appex" | plutil -p -

# 模拟器确认 group 容器是否存在、路径是否一致
xcrun simctl get_app_container booted com.example.app data
find ~/Library/Developer/CoreSimulator/Devices -type d -name "group.com.enterprise.retailops"

log stream --predicate 'subsystem == "com.enterprise.shared"' --level debug

运行方式：终端核对签名内 entitlements 与模拟器容器；真机用 Console.app 观察共享层日志。

  • 工具与看什么：codesign -d --entitlements 的两端输出；containerURL 是否为 nil；共享层日志里的 schemaVersion、写入时间与 postDarwin 记录。

验证与排除

  • 确认 H1：任一 target 的 entitlements 缺少 group，或字符串不一致；containerURL 返回 nil。
  • 确认 H2：文件路径能取到而 UserDefaults(suiteName:) 为 nil，说明 suiteName 与 entitlement 不一致。
  • 确认 H3：容器文件 mtime 已更新，但 Widget 仍显示旧值，且写入路径没有 CFNotificationCenterGetDarwinNotifyCenter 的 post。
  • 排除 H4：日志显示解码成功、schemaVersion 匹配；若报解码失败且存储内容完整，则 H4 成立，进入迁移修复。
  • 确认 H5：设备锁屏时读失败，或非原子写入期间读到半截数据；对比加锁/解锁与原子写后结果。

修复要点

  • 两端 entitlements 配同一个 group id，并从单一常量读取，禁止各处手写字符串；suiteName 与 group id 对齐。
  • 写入用 .atomic，快照带 schemaVersion 并做向后兼容解码；把「写快照 + post Darwin」封进同一函数，Darwin 只做信号，数据仍从容器读。
  • 锁屏场景选择可用的文件保护等级（如 NSFileProtectionCompleteUntilFirstUserAuthentication），敏感数据不要放共享容器；必要时改由 Keychain 共享组承载。
  • 风险/回归：降低文件保护等级会扩大攻击面，需评审；回归覆盖双 target 重装、杀扩展后重启、锁屏/解锁与 schema 迁移。

INC-28 Widget 时间线不刷新 / 刷新预算耗尽 ​

症状

  • Widget 停留在昨天甚至更早的数据，打开主 App 后才更新一次，随后又长期不刷新。
  • 用户反馈「装了 Widget 却不动」；系统设置里 Widget 可见，但时间线 entries 早已过期。

假设树

  • H1：刷新策略对高频用户也返回 .never 或过长的 .after，时间线没有后续 entry。
  • H2：主 App 在每次视图刷新/状态变化都调用 reloadTimelines，把每日预算提前耗尽（预算大致几十次，因系统版本与使用习惯而异，待真机验证）。
  • H3：数据已写入 App Group，但从未调用 WidgetCenter.shared.reloadTimelines(ofKind:)，或 kind 字符串与 Widget 配置不一致。
  • H4：TimelineProvider 在扩展里发同步网络请求，超时或被系统杀掉，时间线生成失败。
  • H5：Widget 不在可见桌面/锁屏，或处于低电量模式、后台 App 刷新关闭，系统直接不分配预算。

  • 确认 H3：快照 mtime 已更新，但日志没有任何 reloadTimelines 记录；或记录中的 kind 与配置不一致。
  • 排除 H4：刷新窗口附近没有扩展终止记录，时间线正常生成；若扩展在窗口内被杀且 provider 有网络调用，则 H4 成立。

  • 刷新策略集中为纯函数决策表：never（低频用户）→ 预算见底 .atEnd → 业务节拍 .after → 兜底 .atEnd，第一条命中即返回。
  • 只在主 App 进前台拉完数据、后台任务写完后各 reload 一次，禁止在 Widget 视图 body 或每次状态变更时调用；kind 用常量。
  • Provider 只读 App Group 本地快照，绝不在扩展里发同步网络请求；无数据时返回占位符并安排短间隔重试。
  • 风险/回归：降低刷新频率会影响新鲜度，需按业务节拍验收；回归跑策略表驱动测试，并在真机统计 24 小时刷新分配次数（阈值因系统而异，待真机验证）。

INC-29 埋点丢失：flush 策略与退后台兜底失效 ​

症状

  • 用户在前台操作明明有记录，服务端只收到一部分；短会话或最后几步操作完全缺失。
  • 退后台、锁屏或上滑杀 App 后，本地缓冲里的事件没有上传；次日看板出现固定比例的缺口。

假设树

  • H1：只按条数阈值 flush（如 20 条），没有时间条件或定时器，短会话永远攒不满。
  • H2：进入后台时没有调用 flushAll，或上传没有包在 beginBackgroundTask 里，任务被系统挂起。
  • H3：用户上滑强杀时生命周期回调根本不会执行，而缓冲区只在内存中，进程结束即丢。
  • H4：上传失败没有重试或没有持久队列；收到 4xx/5xx 也把队列清空，数据静默丢失。
  • H5：时间判定有 bug：lastFlushAt 未更新、客户端时钟被改动，或 actor 重入导致重复/空 flush。

  • 工具与看什么：flush 日志中的 bufferedCount、触发原因（count / interval / background）、HTTP 状态码；服务端按 event_id 对账。

验证与排除

  • 确认 H1：会话只产生 5 条事件、停留超过 30 秒，退后台后缓冲仍非空，说明时间条件未生效。
  • 确认 H2：日志没有 beginBackgroundTask 或出现 expiration，上传请求在后台被取消。
  • 确认 H3：记录 5 条后上滑强杀，重启 App 队列为空、服务端为 0，内存缓冲随进程消失。
  • 确认 H4：mock 500 后队列被清空且无重试记录；或 4xx 被当成成功。
  • 排除 H5：注入固定时钟跑单测，flushIfNeeded 的条数与时间分支均符合预期；若 lastFlushAt 未推进，则 H5 成立。

修复要点

  • flush 采用「条数 + 时间」双条件（示例 20 条 / 30 秒，可配置），时间由外部注入，禁止隐式 Date()。
  • scenePhase 进入 .background / .inactive 时 flushAll，用 beginBackgroundTask 包裹上传；上传成功再清理队列。
  • record 后写前日志到磁盘队列（App Group 或 Application Support），重启恢复；只在 2xx 后删除，失败指数退避并设上限。
  • 风险/回归：重试会造成重复上报，服务端按 event_id 幂等去重；磁盘队列需设容量上限。回归覆盖强杀、500、时钟回拨与后台过期场景。

INC-30 埋点 schema 漂移导致下游报表口径错 ​

症状

  • 新版本上线后购买转化率腰斩或翻倍，实际业务量没有变化；同一动作在数据里出现三个事件名。
  • 金额字段求和放大 100 倍或出现大量 null；下游 ETL 因缺必填属性失败，数据团队与客户端互相甩锅。

假设树

  • H1：同一业务语义被重命名或重复上报（purchase_done / buy_complete / orderPaid），新旧版本并行，下游只消费其中一个。
  • H2：属性类型或单位变了却没有版本（金额从「元」字符串改成「分」整数、突然新增币种），下游按旧口径聚合。
  • H3：客户端 schema 白名单过期/远端 schema 未拉取，新事件被静默拒绝；或校验只警告不抛错，脏数据照常入仓。
  • H4：命名规范漂移（camelCase 与 snake_case 混用、事件名与属性名互换），下游去重键/关联键对不上。
  • H5：原本可选的属性改成必填，但某个页面路径没有补值，导致该路径事件缺失或大量 null。

  • 确认 H1：同一批订单在数据里同时出现两个以上事件名，或旧版本客户端仍占一定流量且只发旧名。
  • 确认 H2：同一 order_id 在新旧版本样本中 amount 类型/单位不同，报表恰好相差 100 倍。
  • 确认 H3：客户端日志有 invalidName / missingRequiredField 抛错，或远端 schema 版本落后于发版；若只警告，则脏数据已入仓。
  • 确认 H4：事件名大小写/分隔符不一致，下游按去重键聚合时把一个动作拆成多条。
  • 确认 H5：按页面路径分组看必填属性的 null 率，某条新路径为 100%；字段定义变更与发版时间吻合。

修复要点

  • 建立唯一事件名注册表与 schema 白名单，CI 门禁要求新事件必须先登记；校验抛错而不是警告，脏数据在端上被拒。
  • 破坏性变更（重命名、类型/单位变更）必须带 schema 版本与弃用窗口；过渡期在数仓视图里映射旧名，禁止客户端双发造成重复。
  • 事件带 event_id 供下游幂等；金额统一「最小货币单位 + 币种」并在契约测试中锁定。
  • 风险/回归：门禁可能阻塞发版，需要登记流程；历史数据需回刷/重算。回归用旧版与新版样本回放同一套 schema 测试，核对看板口径。
