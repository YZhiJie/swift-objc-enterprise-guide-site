INC-12 ATS 拦截明文 HTTP ​

症状

  • 首页图片与埋点上报在 iOS 17+ 真机全部失败，Android 与浏览器正常。
  • 控制台出现 App Transport Security has blocked a cleartext HTTP (http://) resource load since it is insecure，URLSession 返回 NSURLErrorAppTransportSecurityRequiresSecureConnection (-1022)。
  • 同一 URL 在 Safari 里能打开，说明服务端可达，失败发生在系统安全策略层。

假设树

  • H1：最终产物的 Info.plist 没有为旧 CDN 配置 ATS 例外，默认策略直接阻断 HTTP。
  • H2：写了 NSExceptionDomains，但域名键带端口、大小写不一致或拼错，例外没有命中。
  • H3：请求先到 HTTPS 域名，30x 重定向到另一个 HTTP 域名，例外只覆盖了第一段。
  • H4：Debug 配置临时开了 NSAllowsArbitraryLoads，Release 的 Info.plist 合并或变量替换后并未生效。
  • H5：请求由 App 扩展（Widget/Share Extension）或三方 SDK 发出，其 target 使用独立 Info.plist，主 App 的例外不生效。

定位动作

bash
# 1. 看构建产物里最终生效的 ATS 配置，而不是源码目录里的 Info.plist
plutil -p build/Release-iphoneos/MyApp.app/Info.plist

# 2. 用系统 ATS 诊断工具跑目标域名，观察默认策略与例外策略分别是否通过
nscurl --ats-diagnostics --verbose http://legacy-cdn.example.com/path

# 3. 确认是否发生跨域重定向，关注 Location 与最终状态码
curl -v --max-time 10 http://legacy-cdn.example.com/path

# 4. 模拟器/本机复现时看 ATS 拒绝日志；真机用 Console.app 选择设备查看
log stream --predicate 'process == "MyApp"' --level debug

  • 工具与看什么：plutil -p 看 NSAppTransportSecurity 下的 NSExceptionDomains 是否精确匹配 host；nscurl 输出中对比 "ATS Default Connection" 与 "ATS with Exception" 的结果；curl -v 看 30x 与 Location；日志里看被拦截的完整 URL。

验证与排除

  • 排除 H1：若产物 plist 已有目标域名例外且 nscurl 的例外组合通过，但 App 仍报 -1022，说明不是「完全没配」。
  • 排除 H2：用 plutil -p 核对键名与 host 逐字符一致；若例外键带端口或子域未声明，nscurl 会显示对应组合失败。
  • 排除 H3：curl -v 若没有 30x，或最终响应直接在原 host 返回 200，则重定向假设不成立；若 Location 指向另一个 http:// 域名，则确认 H3。
  • 排除 H4：分别导出 Debug 与 Release 产物并对比 plist；只有 Debug 含 NSAllowsArbitraryLoads 时，H4 成立。
  • 排除 H5：用主 App 内最小 URLSession 请求同一 URL 能成功、而扩展/SDK 失败，或检查扩展 target 的 Info.plist，即可确认 H5。

修复要点

  • 首选把旧 CDN 迁到 HTTPS；过渡期只对必要域名做最小例外，禁止全局关闭 ATS：

INC-13 证书固定导致换证后全量请求失败 ​

症状

  • 服务端在凌晨轮换 TLS 证书后，新版本 3.2.0 的 API 请求几乎全部失败，3.1.x 老版本仍正常。
  • 客户端报 NSURLErrorServerCertificateUntrusted (-1202) 或 pin 校验失败后主动取消产生的 -999（具体错误码以真机日志为准）。
  • 系统默认 TLS 校验可以通过，只有启用了证书固定的构建失败，说明不是普通断网或服务端不可达。

假设树

  • H1：新版本固定的是叶子证书 SPKI，换证后旧 pin 不匹配；老版本固定的是中间 CA，因此不受叶子轮换影响。
  • H2：只配置了当前证书的一个哈希，没有预留备用哈希，换证前也没有提前发版下发新哈希。
  • H3：pin 哈希算的是裸公钥（X9.63/PKCS#1），不是完整的 SPKI DER，因此与服务端/TrustKit 配置的值天然不一致。
  • H4：TLS 终止层或 CDN 更换供应商，证书链的中间 CA 发生变化，固定中间 CA 的老版本也会失效。
  • H5：新证书换了密钥算法（如 RSA 换 ECDSA），TrustKit 的 TSKPublicKeyAlgorithms 未包含新算法，即使哈希在列表里也被拒绝。

定位动作

bash
# 1. 先确认系统默认信任链是否正常：若全部通过，问题在 pin 层
nscurl --ats-diagnostics --verbose https://api.example.com/health

# 2. 看服务端当前证书链的颁发者与 Subject，和固定目标比对
curl -v --max-time 10 https://api.example.com/health

# 3. 计算当前叶子/中间 CA 的 SPKI SHA-256（与 TrustKit 的 pin 格式一致）
openssl x509 -in leaf.pem -pubkey -noout \
  | openssl pkey -pubin -outform der \
  | openssl dgst -sha256 -binary | openssl enc -base64

# 4. 看产物里实际生效的固定哈希与算法白名单
plutil -p build/Release-iphoneos/MyApp.app/Info.plist

# 5. 真机复现时抓 TLS/URLSession 失败日志
log stream --predicate 'process == "MyApp"' --level debug

运行方式：终端执行；证书 PEM 可从服务端导出或由运维提供，plutil 读取 App 产物中的 TrustKit 配置。

  • 工具与看什么：nscurl 用来区分「系统信任失败」与「pin 额外失败」；curl -v 看 leaf issuer 与链长度；openssl 输出与 TSKPublicKeyHashes 逐项比对；日志看失败 URL 是否集中在同一 host。

验证与排除

  • 排除 H1：把新版本 pin 列表与当前叶子哈希比对；若老版本 pin 的是中间 CA 且仍正常，而新版本 pin 叶子失败，H1 成立。
  • 排除 H2：数 TSKPublicKeyHashes 的条目；只有一条且不等于当前证书哈希时，H2 成立；若第二条已匹配当前链，则不是缺备用哈希。
  • 排除 H3：用 openssl 分别对完整 SPKI 与裸公钥做 SHA-256；若配置值等于裸公钥哈希，确认 H3。
  • 排除 H4：curl -v 对比新旧中间 CA 的 Subject/Serial；若中间 CA 也变了，老版本同样会失败，H4 成立。
  • 排除 H5：哈希匹配但 TrustKit 仍拒绝时，检查 TSKPublicKeyAlgorithms 是否包含当前密钥算法；不包含则确认 H5。

修复要点

  • 固定中间 CA 的 SPKI，而不是叶子证书；配置「当前 + 下一个」至少两个哈希，换证前先发版下发新哈希，再执行轮换。
  • TrustKit 的算法白名单要覆盖 RSA 与 ECDSA；TSKEnforcePinning 保持开启，禁止用远程开关关闭 pin（那等于给中间人留后门）。
  • 轮换按灰度节奏走：先内部/TestFlight 验证新哈希，再 5%→25%→100%；同时监控 pin 失败率并按域名告警。
  • 预期收益：换证不再造成全网断连；风险是备用哈希长期有效会扩大攻击面，需在轮换完成后清理过期哈希并保留书面 runbook。

INC-14 弱网/无超时导致请求堆积与雪崩 ​

症状

  • 早高峰弱网时首页一直转圈，用户反复下拉刷新；后端同一时间 QPS 涨到平时 3 倍，出现 502/504。
  • 客户端日志大量 NSURLErrorTimedOut (-1001) 与 NSURLErrorNetworkConnectionLost (-1005)，重试日志在数秒内成串出现。
  • 进程内 URLSession 任务数从个位数涨到 100+，内存与耗电同步上升，网络恢复后仍持续一段时间。

假设树

  • H1：URLSessionConfiguration 沿用默认超时（请求 60s、资源 7 天），弱网下请求长期挂起，占满连接与回调。
  • H2：重试没有上限、没有指数退避与抖动，失败后立即重试，形成重试风暴并放大后端压力。
  • H3：列表每个 cell、每次刷新都发同一请求，没有去重/合并，也没有并发上限。
  • H4：页面退出或刷新覆盖时旧任务未取消，completion 闭包继续持有页面与数据。
  • H5：开启了 waitsForConnectivity 且没有配套超时，无网时任务永久排队，网络恢复瞬间集中释放。

定位动作

bash
# 1. 复现时看网络层结构化日志：taskID、URL、开始/结束、耗时、重试次数
log stream --predicate 'subsystem == "com.example.network"' --level debug

# 2. 统计 15 分钟内的超时与重试，确认是否集中在同一 URL
log show --last 15m --predicate 'subsystem == "com.example.network" AND eventMessage CONTAINS "timeout"' --style compact

# 3. 用 curl 对比服务端正常耗时与客户端超时阈值，排除服务端本身慢
curl -v --max-time 15 https://api.example.com/feed

# 4. 用 Instruments 的 Time Profiler 看回调开销，System Trace 看线程与阻塞
open -a Instruments

运行方式：终端与 Instruments 配合；日志需在代码里用 Logger(subsystem:category:) 为任务生命周期打点，否则只能看到系统错误。

  • 工具与看什么：日志按 taskID 聚合「开始→重试→结束」；log show 统计超时条数与 URL 分布；curl 看服务端 P50/P99；Instruments 看主线程是否被回调反序列化拖慢。

验证与排除

  • 排除 H1：若超时错误集中在 60s 附近，且配置里没有显式设置 timeoutIntervalForRequest，H1 成立；把超时降到 15s 后堆积明显下降可复验。
  • 排除 H2：统计单任务重试次数与间隔；若 3 次以上且间隔小于 1s，后端访问日志也成倍增长，确认 H2。
  • 排除 H3：同一刷新周期内同一 URL 的并发 task 数大于 1，或不同 cell 重复请求同一资源，确认 H3。
  • 排除 H4：页面退出后任务数不降、deinit 不打印，Instruments 显示闭包仍持有页面，确认 H4。
  • 排除 H5：飞行模式下任务长期不结束，恢复网络后瞬间全部完成；关闭 waitsForConnectivity 或加超时后不再堆积，确认 H5。

修复要点

  • 按接口设置超时（交互型 10~15s、上传/下载单独放宽），资源超时不要沿用默认值；超时后走统一错误分类。
  • 只对幂等请求重试，最多 2 次，指数退避加随机抖动；服务端连续 5xx 时熔断一段时间，避免继续放大。
  • 请求去重：以「URL + 参数」为 key，用 actor 维护 in-flight 任务；并发限制在 4~6，列表 cell 复用取消旧任务。
  • 页面退出/刷新覆盖时显式 task.cancel()，completion 用 [weak self]；waitsForConnectivity 仅在后台同步等场景使用，并配超时。
  • 预期收益：弱网下任务数与后端 QPS 受控；风险是短超时可能误伤慢接口，需按接口分级并监控超时率。

INC-15 跨线程写共享状态的数据竞争 ​

症状

  • TestFlight 高并发场景下，未读数偶尔少 1、订单 ID 偶发重复，低概率出现 Simultaneous accesses to 0x..., but modification requires exclusive access。
  • Xcode 打开 Thread Sanitizer 后复现，报告 WARNING: ThreadSanitizer: data race，一条栈在 URLSession 回调，另一条栈在主线程读取。
  • 模拟器轻负载难复现，真机快速切换页面并连续刷新时概率升高。

假设树

  • H1：共享可变 Dictionary/Array 被多个队列同时读写，没有锁或串行隔离。
  • H2：单例持有 var 状态，网络回调写、主线程读，二者没有统一隔离。
  • H3：用 @unchecked Sendable 或 nonisolated(unsafe) 绕过编译检查，实际仍存在竞争。
  • H4：每个实例各自创建一个 serial queue，但写的是同一份 static/global 状态，两个队列互不互斥。
  • H5：工程停留在 Swift 5 模式、SWIFT_STRICT_CONCURRENCY 未开，CI 也不跑 Thread Sanitizer，问题被工具链漏掉。

定位动作

bash
# 1. Xcode Scheme → Run/Test → Diagnostics 勾选 Thread Sanitizer，复现后看读写两侧栈
# 2. CI 无人工复现时，用 xcodebuild test 开启 TSan
xcodebuild test -workspace MyApp.xcworkspace -scheme MyApp \
  -destination 'platform=iOS Simulator,name=iPhone 16' \
  -enableThreadSanitizer YES

# 3. 看当前 Swift 版本与并发检查级别
xcodebuild -showBuildSettings -workspace MyApp.xcworkspace -scheme MyApp \
  | grep -E 'SWIFT_VERSION|SWIFT_STRICT_CONCURRENCY'

# 4. Debug 包复现时看运行时排他性冲突日志
log stream --predicate 'process == "MyApp"' --level debug

运行方式：TSan 建议在模拟器/真机 Debug 包运行；xcodebuild test 适合把并发用例放进 CI 夜间任务。

  • 工具与看什么：TSan 报告里的两个栈必须落到同一地址的读与写；showBuildSettings 确认是否仍是 Swift 5 + 未开 complete；日志看运行时 exclusivity 冲突的对象类型。

验证与排除

  • 排除 H1：TSan 同时给出读栈与写栈、且没有共同锁/队列，确认 H1；加锁或改 actor 后报告消失可复验。
  • 排除 H2：TSan 栈指向单例属性，代码审计确认写发生在网络回调、读发生在主线程，确认 H2。
  • 排除 H3：搜索该类型的 @unchecked Sendable/nonisolated(unsafe) 声明；若 TSan 仍报告，说明标注只是压掉了编译警告，H3 成立。
  • 排除 H4：打印/审查所有 queue label 与保护对象；两个不同 queue 保护同一 static 状态时，H4 成立。
  • 排除 H5：若 SWIFT_STRICT_CONCURRENCY 不是 complete 且 CI 无 TSan，H5 是问题长期漏检的原因，但不能替代 H1/H2 的根因。

修复要点

  • 把共享状态收敛到 actor（缓存、计数器、连接池），跨 actor 只传 Sendable 值类型；UI 状态用 @MainActor。
  • 旧 ObjC/回调代码若暂不能改 actor，使用单一串行队列或并发队列 + barrier 写，读也必须走同一队列。
  • 移除无依据的 @unchecked Sendable；确需保留时补注释说明锁协议与不变量。
  • 分阶段开启 SWIFT_STRICT_CONCURRENCY=complete，修完模块再切 Swift 6；CI 增加 TSan 夜间任务和并发用例。
  • 预期收益：丢更新与偶发崩溃消失，编译器开始兜底；风险是 actor 重入（await 后不变量可能变化）和频繁 hop 的性能开销，需要压测。

INC-16 主线程同步等待异步回调导致死锁/卡死 ​

症状

  • 点击「保存」后界面完全无响应，约 20s 后被系统以 watchdog 杀死，终止原因 0x8badf00d。
  • 主线程栈停在 __dispatch_semaphore_wait / DispatchSemaphore.wait，或 DispatchGroup.wait；网络请求本身很快返回。
  • 有时不是崩溃而是长时间卡住，用户强杀后重进正常，线上表现为「偶发卡死」。

假设树

  • H1：主线程 DispatchSemaphore.wait() 等一个被派发回主队列的 completion，主线程等主队列、主队列等主线程，形成互等。
  • H2：主线程 DispatchGroup.wait()，或后台回调里执行 DispatchQueue.main.sync，把主队列阻塞住。
  • H3：用 withCheckedContinuation 包装旧回调，但在同步函数里用信号量等待 async 结果，桥接层自己制造了死锁。
  • H4：不是死锁，而是主线程同步做 JSON 解码、图片解码或文件 IO，栈上显示实际计算而非 wait。
  • H5：URLSession 的 delegateQueue 设为 .main，主线程又在同步等 delegate 回调，回调永远没有机会执行。

定位动作

bash
# 1. 复现卡死时在 Xcode 暂停执行，直接看主线程栈是 wait 还是实际计算
# 2. 用 Instruments 的 Hangs / System Trace 模板录制，定位主线程阻塞区间
open -a Instruments

# 3. 抓 watchdog 终止日志（真机日志建议先在 Console.app 导出）
log show --last 1h --predicate 'eventMessage CONTAINS "0x8badf00d"' --style compact

# 4. 真机复现时实时看业务日志最后停在哪一步

验证与排除

  • 排除 H1：主线程栈是 semaphore_wait，completion 又固定在 DispatchQueue.main.async；把等待改到后台或改成 async 后恢复，确认 H1。
  • 排除 H2：栈上出现 dispatch_group_wait 或 dispatch_sync，且调用方在后台，确认 H2。
  • 排除 H3：检查桥接函数是否在同步上下文里等待 continuation；改成全 async 调用链后不再卡，确认 H3。
  • 排除 H4：Time Profiler 显示主线程 CPU 饱和在解码/IO 函数，而不是空等；把工作移到后台后帧率恢复，确认 H4。
  • 排除 H5：delegateQueue 设为 .main 且 delegate 回调日志从未打印；改为独立 delegate queue 后恢复，确认 H5。

修复要点

  • 禁止在主线程 wait 任何异步结果；把「保存」API 改成 async throws，调用方用 Task/await，UI 更新回到 @MainActor。
  • 旧 completion API 用 withCheckedThrowingContinuation 桥接，确保每条分支恰好 resume 一次；不要再用信号量包一层「同步版」。
  • 若必须提供同步接口，放到后台队列并设置超时，绝不在主线程暴露；后台也不要 DispatchQueue.main.sync。
  • URLSession 使用独立 delegate queue；给关键路径加 signpost，配合 Hangs 监控提前发现主线程阻塞。
  • 预期收益：卡死与 watchdog 终止消失；风险是 API 改成 async 会波及调用方，超时设置不当可能把慢请求误判为失败。
