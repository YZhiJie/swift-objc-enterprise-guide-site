第 8 章 构建与部署 ​

构建与部署是「代码到用户」的最后一公里。本章覆盖 Xcode 构建系统、依赖管理、签名体系、fastlane 自动化与 CI/CD、TestFlight 灰度及 App Store 上架全流程。

8.0 学习目标 ​

完成本章后，你将能够：

  1. 使用 xcodebuild 完成命令行构建/测试/归档，用 xcconfig 分层管理配置；
  2. 在 SPM 与 CocoaPods 之间做出选型并处理混用场景；
  3. 讲清签名体系四要素（证书/描述文件/Entitlements/App Groups）与自动签名原理；
  4. 用 fastlane（match/scan/gym）搭建全自动化流水线；
  5. 落地 GitHub Actions / Xcode Cloud CI，掌握 TestFlight 灰度、App Store 审核要点与 macOS 公证。

8.2 Xcode 构建系统：xcodebuild ​

常用命令 ​

bash
# File: build.sh
# 列出工程信息（scheme / target / configuration）
xcodebuild -list -workspace MyApp.xcworkspace

# 构建（不签名，CI 编译验证）
xcodebuild build -workspace MyApp.xcworkspace -scheme MyApp \

运行方式：Xcode 工程 Info → Configurations 中为 Debug/Release 分别指定对应 xcconfig。语法要点：引用变量用 $(VAR_NAME)（如 $(inherited) 继承上层值、$(SRCROOT) 引用工程根目录），include 路径等场景无需额外转义；但 // 在行中会被当作行注释，因此 URL 里的 // 要写成 /$()/（空变量展开为空串）来规避。

Mergeable Libraries（可合并库，Xcode 15+） ​

Mergeable Libraries 让同一份 framework 在不同配置下自动切换链接形态，开发期动态链接（编译快）、发布期合并为单库（启动快），同时拿到静态库的启动性能与动态库的迭代速度，用来替代过去手写的「动态库合并」脚本（与 6.3 启动优化的 dylib 数量治理直接呼应）：

三种自建库形态对比：

形态Debug 迭代速度Release 启动成本额外维护
纯动态 framework快（只重编库）高（每个 dylib 一次装载与 rebase/bind）需手写合并，或忍受启动损耗
纯静态 framework慢（改库要重链接 App）低（无独立 dylib）Debug/Release 两份链接配置
Mergeable快（Debug 保持动态）低（Release 自动合并）✅ 零脚本，链接器按配置切换

涉及两个构建设置，分别放在不同 target 上，不要混设：

设置作用对象取值
MERGEABLE_LIBRARYframework / library targetYES 产出可合并库、NO 关闭；新工程 framework 默认 Automatic（即 YES）
MERGED_BINARY_TYPEApp 等消费方 targetautomatic（默认）：Debug 动态、Release 自动合并；manual：自行在链接参数中控制
text
// File: Config/Mergeable.xcconfig（旧工程手动开启示例）
// ① framework target：声明「我可以被合并」
MERGEABLE_LIBRARY = YES
// ② App target：automatic 是默认值通常无需显式写；manual 时在 Other Linker Flags 加：
MERGED_BINARY_TYPE = automatic
// OTHER_LDFLAGS = -merge_framework $(SRCROOT)/Frameworks/MyKit.framework/MyKit

运行方式：Xcode 15+ 工程修改设置后，分别执行 Debug 构建与 Release 归档，用 otool -L build/Release-iphoneos/MyApp.app/MyApp 对比链接表——Debug 能看到各 framework 依赖，Release 产物中被合并的库不再作为独立 dylib 出现。

  • ✅ 适用对象：自研 framework（含 SPM 源码包、源码 Pod 产物）；App target 不设置 MERGEABLE_LIBRARY（它只标记「可被合并的库」），消费侧用 MERGED_BINARY_TYPE。
  • ✅ 替代手写方案：删掉自研「把 N 个动态 framework 打成一个 uber framework」的脚本与双份产物维护，交给链接器自动完成——6.3 表格中「自定义动态库合并至 ≤ 6 个」的收益零脚本获得。
  • ✅ 除 otool -L 外，归档日志搜索 Merging 可看到逐个库被合并的记录；Debug 产物因附带合并元数据会略大，属正常现象，不进 Release 包体。

旧工程启用步骤：

  1. 给自研 framework target 设 MERGEABLE_LIBRARY = YES（或新建一个 framework 工程对照 Xcode 写入的默认值）；
  2. 确认 App target MERGED_BINARY_TYPE = automatic，且整体部署目标 ≥ iOS 12（合并产物的系统支持下限）；
  3. 删除原有动态库合并脚本/聚合 target，Release 归档后用 otool -L 核对 dylib 数量、对比包体与启动耗时。
  • ⚠️ 合并发生在 Release 归档链接阶段，普通 Debug build 看不到效果；含资源 bundle / 混编静态库的复杂工程先验 Debug 链接、再验 Release 产物，CI 的归档 lane（8.5 gym）天然覆盖该验证。
  • ❌ 不适用：运行时 dlopen 按需加载的插件式 dylib、以及要作为独立 SDK 对外分发的 framework——合并后没有独立产物，分发仍走 8.9 XCFramework；三方二进制 SDK 能否合并取决于供给方产物。

核心概念澄清 ​

概念作用常见误区
开发/发布证书证明「你是团队成员」，私钥在本机钥匙串⚠️ 私钥（.p12）丢失 = 证书作废需重建
App IDBundle ID 的服务端注册通配符 App ID 不能用推送等能力
EntitlementsApp 能力清单（沙盒、推送、App Groups）必须与描述文件中能力一致，否则签名失败
描述文件把以上三者「打包授权」给设备Development 含设备 UDID 白名单；Distribution（App Store）不含设备
App Groups同团队多 App/扩展共享容器（如主 App 与 Widget）group identifier 需在 Developer 后台注册并启用

自动签名原理 ​

勾选「Automatically manage signing」后，Xcode 代为完成：创建/更新证书（在团队名额内）、注册设备、生成并下载描述文件。本质是把上述手工步骤自动化——CI 环境不适合自动签名（不可控、易冲突），应使用手动签名 + fastlane match 统一管理。

  • ✅ 企业实践：证书与描述文件集中由 match 存入私有 Git 仓库加密管理，CI 机器只读拉取，人员流动不影响签名能力。
  • ❌ 反例：多人各自开自动签名，互相 revoke 证书，发布日前夜「证书被吊销」事故——几乎每个团队都经历过。

8.5 fastlane 全自动化 ​

ruby
# File: fastlane/Fastfile
default_platform(:ios)

platform :ios do
  desc "同步签名（团队共享）"
  lane :certificates do
    match(type: "appstore", readonly: true)   # CI 只读；管理员本地用非 readonly 生成
  end

  desc "运行测试"
  lane :test do
    scan(scheme: "MyApp",
         devices: ["iPhone 16"],
         code_coverage: true,
         result_bundle: true)
  end

  desc "打包并上传 TestFlight"
  lane :beta do
    increment_build_number(xcodeproj: "MyApp.xcodeproj")
    match(type: "appstore", readonly: true)
    gym(scheme: "MyApp",
        export_method: "app-store",
        output_directory: "build",
        include_symbols: true)                # ✅ dSYM 上传，崩溃符号化必需
    upload_to_testflight(
      changelog: "自动化构建 #{lane_context[SharedValues::BUILD_NUMBER]}",
      distribute_external: false)             # 先内部组，人工再放外部
    # 包体回归门禁（衔接第 6 章）
    app_size = File.size(Dir["build/*.ipa"].first)
    UI.user_error!("包体超限") if app_size > 200 * 1024 * 1024
  end
end

8.6 CI/CD：GitHub Actions 与 Xcode Cloud ​

GitHub Actions + self-hosted macOS Runner ​

yaml
# File: .github/workflows/ios-ci.yml
name: iOS CI
on:
  pull_request:
  push:
    branches: [main]

jobs:
  build-test:
    runs-on: [self-hosted, macos, xcode16]     # ✅ 自托管 runner：Xcode 版本可控
    steps:
      - uses: actions/checkout@v4

      - name: 选择 Xcode 版本
        run: sudo xcode-select -s /Applications/Xcode_16.2.app/Contents/Developer

      - name: 安装签名（match 只读）
        env:
          MATCH_PASSWORD: ${{ secrets.MATCH_PASSWORD }}
        run: bundle exec fastlane certificates

      - name: 单元测试 + Lint 门禁
        run: |
          bundle exec fastlane test
          swiftlint lint --strict

      - name: 上传覆盖率产物
        uses: actions/upload-artifact@v4
        with:
          name: coverage
          path: fastlane/test_output

  beta:
    if: github.ref == 'refs/heads/main' && github.event_name == 'push'
    needs: build-test
    runs-on: [self-hosted, macos, xcode16]
    steps:
      - uses: actions/checkout@v4
      - name: 打包上传 TestFlight
        env:
          MATCH_PASSWORD: ${{ secrets.MATCH_PASSWORD }}
          APP_STORE_CONNECT_API_KEY: ${{ secrets.ASC_API_KEY }}
        run: bundle exec fastlane beta

Apple 官方 CI：与 App Store Connect 深度集成（签名、上传、TestFlight 分发开箱即用），按构建时长计费。

对比GitHub Actions + self-hostedXcode Cloud

8.7 TestFlight 灰度与 App Store 上架 ​

TestFlight 分层 ​

  • 内部测试（Internal）：团队 100 人，构建上传即可测，无需审核——适合每日构建。
  • 外部测试（External）：1 万用户，需 Beta 审核（比正式审核宽松，通常数小时）——适合灰度。

隐私清单缺失（Privacy Manifest）三方 SDK 全部核对含 PrivacyInfo.xcprivacy；Required Reason API 声明用途
权限用途说明空泛NSUsageDescription 写具体场景（「用于扫码登录」而非「需要相机」）
最小化原则违反审核账号/演示视频预置，拒绝要求真实身份信息才能体验
热更新/隐藏功能❌ 严禁可执行代码下发；A/B 实验用配置而非代码
支付合规数字内容必须 IAP；实物/服务可用第三方支付（地区政策随法规更新，上架前核对最新审核指南）
IPv6 / 机型适配审核在纯 IPv6 网络进行；确保无 IPv4 硬编码

发布策略 ​

  • ✅ 分阶段发布（Phased Release）：7 天内 1%→2%→5%→10%→20%→50%→100%，配合崩溃率/差评监控，随时暂停（Pause）。
  • ✅ 版本节奏：TestFlight 每日构建（内部）→ 每周 RC（外部灰度）→ 双周正式发布，与第 7 章测试节奏对齐。

8.8 macOS 公证（Notarization）与企业分发 ​

App Store 之外分发 macOS App（开发者 ID 签名），必须经 Apple 公证，否则 Gatekeeper 拦截：

bash
# File: notarize.sh
# 1. 用 Developer ID Application 证书签名：自内向外，先签内嵌产物，最后签 App 本体
#    （--deep 已被 Apple 废弃，它只做递归粗签，无法正确处理各自的 entitlements）
APP="MyApp.app"
IDENTITY="Developer ID Application: Example Inc (TEAMID)"

# 1a. 内嵌 helper / XPC 工具
codesign --force --options runtime --timestamp \
  --sign "$IDENTITY" "$APP/Contents/MacOS/MyAppHelper"
# 1b. 内嵌动态库
codesign --force --options runtime --timestamp \
  --sign "$IDENTITY" "$APP/Contents/Frameworks/libNetwork.dylib"
# 1c. 内嵌 framework（同样先内后外）
codesign --force --options runtime --timestamp \
  --sign "$IDENTITY" "$APP/Contents/Frameworks/MyKit.framework/Versions/A"
# 1d. 最后签 App bundle（汇总所有内层签名）
codesign --force --options runtime --timestamp \
  --entitlements MyApp.entitlements --sign "$IDENTITY" "$APP"

# 2. 提交公证（Apple notarytool，Xcode 13+；先打成 zip 或 dmg）
xcrun notarytool submit MyApp.zip \
  --keychain-profile "AC_PROFILE" --wait

# 3. 装订票据（stapler），离线设备也能验票
xcrun stapler staple MyApp.app

# 4. 校验
codesign --verify --deep --strict --verbose=2 MyApp.app  # 仅用于校验签名完整性
spctl -a -vv MyApp.app   # 期望：accepted source=Notarized Developer ID

8.9 二进制分发与隐私清单 ​

XCFramework 制作与二进制分发 ​

XCFramework 把同一 framework 的真机 / 模拟器两切片（还可加 Mac Catalyst 等）聚合为一个产物，是 SPM binaryTarget 唯一支持的二进制格式：

bash
# File: make-xcframework.sh
# 1a. 归档真机切片（BUILD_LIBRARY_FOR_DISTRIBUTION=YES 生成 .swiftinterface，保证模块稳定性）
xcodebuild archive -scheme MyKit -configuration Release \
  -destination "generic/platform=iOS" -archivePath build/MyKit-device.xcarchive \
  SKIP_INSTALL=NO BUILD_LIBRARY_FOR_DISTRIBUTION=YES
# 1b. 归档模拟器切片
xcodebuild archive -scheme MyKit -configuration Release \
  -destination "generic/platform=iOS Simulator" -archivePath build/MyKit-sim.xcarchive \
  SKIP_INSTALL=NO BUILD_LIBRARY_FOR_DISTRIBUTION=YES
# 2. 聚合两切片为 .xcframework
xcodebuild -create-xcframework \
  -framework build/MyKit-device.xcarchive/Products/Library/Frameworks/MyKit.framework \
  -framework build/MyKit-sim.xcarchive/Products/Library/Frameworks/MyKit.framework \
  -output build/MyKit.xcframework
# 3. 打包并计算校验和（binaryTarget 必备）
(cd build && zip -qr MyKit-1.3.0.xcframework.zip MyKit.xcframework)
swift package compute-checksum build/MyKit-1.3.0.xcframework.zip

隐私清单（PrivacyInfo.xcprivacy） ​

Required Reason API 政策：只要代码（含三方 SDK）使用 UserDefaults、文件时间戳、系统启动时间、磁盘空间等受限 API，就必须在隐私清单声明用途原因码（以官方文档为准，填错等同未声明），常见：UserDefaults 主 App 自用=CA92.1、App Group 共享=1C8F.1；文件时间戳（访问容器内文件）=C617.1；系统启动时间（计算事件间隔/计时器）=35F9.1（App 内事件绝对时间戳用 8FFB.1）；磁盘空间写入前检查是否充足=E174.1、向用户展示空间=85F4.1。

企业级场景分析 ​

场景：20 人团队的发布火车（Release Train） ​

某工具类 App 的发布流水线设计：

  1. 节奏：每周三发版。周一 code freeze，CI 从 release 分支构建 RC 上传 TestFlight 外部组；周二全量 UI 回归 + 人工探索测试；周三 Phased Release 开启。
  2. 签名治理：match 仓库存证书，仅发布机器有写权限；开发者本地全部自动签名（开发证书），CI 只读 match（发布证书）——两套证书互不干扰。
  3. 门禁链：PR 合并需「单测通过 + lint 0 警告 + 增量覆盖 ≥80%」；RC 构建需「包体环比增幅 ❤️% + 符号表完整」；发布需「灰度 24h 崩溃率 <0.1%」。
  4. 事故预案：保留「一键撤架 + 热修复版本通道」——审核加速通道（Expedited Review）每年慎用额度，留给 P0 事故。

场景：金融 App 的合规构建 ​

金融 App 构建特殊要求：源码防泄漏（构建机物理隔离 + 私有 runner）、依赖审计（SPM 依赖锁定 Package.resolved 入库评审，禁止 floating version）、构建产物公证留档（每次发布的 archive + dSYM + 构建日志归档保存，满足监管溯源）。这些能力用本章的 xcconfig 分层 + fastlane + self-hosted runner 均可落地。

实践任务 ​

任务 1：xcconfig 改造（★★） ​

把工程的 Bundle ID、API 地址、显示名抽离到 Shared/Debug/Release 三个 xcconfig，验证 Debug 包可与正式包同机共存。

任务 2：命令行全链路（★） ​

写一个脚本完成 clean → build → test → archive → export IPA 全流程，失败时输出明确错误段。

任务 3：SPM 模块化（★★） ​

把工程中的网络层抽为本地 SPM 包（含 Package.swift 与单测），主工程改为依赖该包，验证 swift test 可在包内独立运行。

任务 4：fastlane 三板斧（★★） ​

配置 match（可用临时仓库）+ scan + gym，跑通「测试 → 签名 → 打包」一条 lane，并加入包体大小门禁。

任务 5：CI 流水线（★★★） ​

搭建 GitHub Actions（或 Xcode Cloud）流水线：PR 触发 lint + 单测 + 覆盖率门禁；main 分支合并后自动上传 TestFlight 内部组。写出 secrets 清单与回滚预案。

小结与自测 ​

要点回顾

  • xcodebuild 是自动化底座；xcconfig 让配置可评审、可继承、多环境共存。
  • 依赖管理：新项目 SPM 默认，CocoaPods 存量维护，混用期防重复引入。
  • 签名 = 证书（身份）+ App ID + Entitlements（能力）→ 描述文件（打包授权）；团队级用 match 统一。
  • fastlane：match 签名、scan 测试、gym 打包、pilot/deliver 分发。
  • CI/CD：self-hosted runner 控 Xcode 版本；Xcode Cloud 省心做分发。
  • 上架：隐私清单、权限说明、IAP 合规、Phased Release 灰度；macOS 分发必过公证。

自测题

  1. xcconfig 中配置不生效，最常见的两个原因是什么？
  2. Development 与 App Store 描述文件的关键差异是什么？
  3. 为什么 CI 环境不建议使用「自动签名」？
  4. 同一依赖被 SPM 与 CocoaPods 各引入一份会导致什么问题？
  5. macOS 公证（Notarization）与 App Store 审核有何本质区别？
参考答案
  1. 一是 Build Settings 面板存在手动加粗值覆盖了 xcconfig（优先级更高）；二是 xcconfig 赋值未加 $(inherited)，把上层/平台默认值覆盖或顺序错误。
  2. Development 描述文件包含设备 UDID 白名单（仅注册设备可安装）；App Store 描述文件不含设备列表，只能经 App Store/TestFlight 分发，不可直接安装到设备。
  3. 自动签名由 Xcode 代管证书与描述文件，多台 CI 机器并发操作时易互相 revoke/重建导致状态混乱且不可审计；CI 应手动签名 + match 只读拉取，保证确定性。
  4. 符号重复警告/链接错误；更隐蔽的是同一单例/全局状态存在两份，跨边界的类型不相等（is/as 判断失败）、通知中心各收各的，产生极难排查的运行时 bug。
  5. 公证是自动化安全检查（恶意软件扫描 + 签名验证，分钟级），不涉及内容与商业模式审核；App Store 审核是人工 + 自动的全维度审核（功能、合规、隐私、支付），周期以天计。
