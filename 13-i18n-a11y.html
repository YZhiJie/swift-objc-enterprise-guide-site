第 13 章 国际化、本地化与无障碍：EAA 合规方向 ​

国际化（i18n）、本地化（l10n）、无障碍（a11y）三个词的共性是：都在为「非默认的那批用户」解决工程质量问题——非英文用户、非硅谷时区用户、非典型视觉/听觉/运动能力的用户。它们长期被当成「上线前的冲刺项」，结果是每一轮国际化改造都变成全局回归事故，而无障碍在《欧洲无障碍法案》（EAA）2025 年 6 月 28 日生效后，对面向欧盟的 B2C 服务已从「加分项」变成法定义务。本章的主线是：把三者做成架构属性与 CI 流程的一部分，而不是最后一次发版前的补救清单。

说明：本章配套 examples/ 的 LocalizationA11y target（swift run LocalizationA11y），六段演示全部是纯逻辑、零 UI 框架、零 bundle 资源：显式 Locale 格式化、CLDR 复数规则、伪本地化、RTL 判定、WCAG 对比度审计、VoiceOver 播报描述——这些恰是无障碍与国际化中可以被单测守住的部分；需要 Xcode 工程与界面的部分（String Catalog、Accessibility Auditor、XCTest 审计）在正文对应小节用真实工程做法讲清。

版本基线：String Catalog（.xcstrings）需 Xcode 15+；performAccessibilityAudit 需 Xcode 15+ / iOS 17+；EAA 自 2025-06-28 起适用于欧盟 B2C 服务。

13.0 学习目标 ​

完成本章后，你将能够：

  1. 说清 i18n / l10n / a11y 的工程边界，并解释为什么「上线前补翻译、提审前补无障碍」的模式必然超支；
  2. 用 String Catalog + String(localized:) + FormatStyle 显式 Locale 组织代码，使「新增一种语言」变成纯翻译工作而非代码工作；
  3. 说出至少四种 CLDR 复数类别的真实差异（zh / en / ru / ar），并解释为什么字符串拼接是国际化的一等反例；
  4. 建立伪本地化 + CI 门禁（死 key / 缺翻译 / 占位符漂移 / 截断）的本地化工程流；
  5. 用四层模型（系统层 / 语义层 / 交互层 / 认知层）组织无障碍适配，在 SwiftUI 与 UIKit 双框架下选择正确的 API，并知道哪些必须靠真机 VoiceOver 手工验证；
  6. 建立 EAA / WCAG 2.2 追溯矩阵：每条成功标准（SC）→ 技术控制 → 验证方式 → 证据，像 10.6.1 的法规映射一样可审计。

13.2 i18n 基础设施：String Catalog、FormatStyle 与 CLDR ​

13.2.1 三个词的工程边界 ​

缩写全称工作内容失败模式
i18ninternationalization让代码具备支持任意语言与区域的能力，不含具体翻译硬编码字符串、手拼日期、假设 . 是小数点
l10nlocalization具体语言/区域的资源落地：翻译、日期货币格式、图片文案译者拿到无上下文的 key、翻译回流后 UI 溢出
a11yaccessibility让残障用户可感知、可操作、可理解只有图片加了 alt、表单错误只有红色没有文字

三者共同点：都是架构与流程属性，无法靠最后一轮冲刺补上。i18n 缺失意味着每种新语言都要改代码；a11y 缺失意味着每个页面都要回炉。企业级做法是把它们放进 13.3 的流水线与 13.7 的追溯矩阵。

13.2.2 String Catalog：.xcstrings 工作流 ​

Xcode 15 起，String Catalog（.xcstrings）是新建工程的默认本地化格式，逐步取代 .strings / .stringsdict：

能力说明
自动提取构建期从 Text("...")、String(localized:) 等提取字符串，新增/删除 key 自动同步
状态标记每条译文有 new / translated / stale（源文案变了但译文未跟进）/ reviewed
构建期校验缺失 key、占位符不匹配在编译阶段暴露，而不是等用户看到 key not found
复数与变体复数、设备宽度等变化内建支持，.stringsdict 退役
JSON 格式可 diff、可评审、可被脚本批量处理（13.3.3 的 CI 检查就建立在这上面）

代码侧的正确姿势是 String(localized:)——key 即默认文案，同时给译者留上下文：

13.2.3 FormatStyle + 显式 Locale：把「格式正确」从运气变成代码 ​

⚠️ 坑点：Locale.current 在 CI 机器、同事的模拟器、用户的真机上是三个不同的值。任何依赖「隐式 Locale」的格式化，正确性都是碰运气。企业级规则是：格式化必须显式传 Locale，且 Locale 的来源是明确的产品决策（货币跟结算区域、号码格式跟账号归属地），「跟随设备」只是其中一个显式选择。

swift
// File: Sources/LocalizationA11y/LocaleFormatting.swift —— 显式 Locale 的格式化骨架

import Foundation

enum LocaleFormatting {

    static func number(_ value: Double, localeID: String) -> String {
        // ✅ FormatStyle 链式 API：格式意图（.number）与区域（.locale）都显式声明
        value.formatted(.number.locale(Locale(identifier: localeID)))
    }

    static func currency(_ value: Double, code: String, localeID: String) -> String {
        // 货币代码与展示区域是两个独立决策：EUR 也要区分给德国用户还是爱尔兰用户看
        value.formatted(.currency(code: code).locale(Locale(identifier: localeID)))
    }

    static func date(_ date: Date, localeID: String) -> String {
        let locale = Locale(identifier: localeID)
        // ⚠️ 区域不仅换文字，还可能换历法（th 默认佛历）：
        // FormatStyle 的 calendar 是属性而非链式修饰符，用 init 注入，否则默认公历
        var style = Date.FormatStyle(locale: locale, calendar: locale.calendar)
        style = style.year().month(.wide).day()
        return style.format(date)
    }

    static func percent(_ value: Double, localeID: String) -> String {
        value.formatted(.percent.locale(Locale(identifier: localeID)))
    }
}

13.2.4 CLDR 复数：复数是语言规则，不是 if n == 1 ​

❌ 反例："You have \(n) item\(n > 1 ? "s" : "")" —— 这行代码只对英语「碰巧」成立。CLDR（Unicode 通用区域数据库）为每种语言定义了复数类别规则：

语言整数复数类别例（「商品」）
中文 / 日文仅 other1 个商品 / 2 个商品 / 100 个商品——量词不变形
英语one / other1 item / 2 items
俄语one / few / many / other21 товар / 22 товара / 25 товаров / 11 товаров
阿拉伯语zero / one / two / few / many / other0 / 1 / 2 各有专门形式，3~10 与 11~99 又不同

俄语的规则本质是「看个位数 + 排除 11~14」：i % 10 == 1 且 i % 100 != 11 才是 one。这正是「字符串拼接」必然翻车的地方——s 后缀法在俄语要展开成四种词形，在阿拉伯语六种。

swift
// File: Sources/LocalizationA11y/CLDRPluralRules.swift —— 复数类别的纯函数实现（节选）

enum CLDRPluralCategory: String, Sendable {
    case zero, one, two, few, many, other
}

enum CLDRPluralRules {
    /// 与 CLDR Plural Rules（整数）一致；同一输入必得同一类别，可表驱动穷举测试
    static func category(for n: Int, language: PluralLanguage) -> CLDRPluralCategory {
        switch language {
        case .en:  return n == 1 ? .one : .other
        case .zh:  return .other                       // 中文永远 other：量词承载「数」
        case .ru:
            let m10 = n % 10, m100 = n % 100
            if m10 == 1 && m100 != 11 { return .one }
            if (2...4).contains(m10) && !(12...14).contains(m100) { return .few }
            if m10 == 0 || (5...9).contains(m10) || (11...14).contains(m100) { return .many }
            return .other
        case .ar:
            if n == 0 { return .zero }
            if n == 1 { return .one }
            if n == 2 { return .two }
            if (3...10).contains(n % 100) { return .few }
            if (11...99).contains(n % 100) { return .many }
            return .other
        }
    }
}

13.2.5 RTL：镜像不是翻转 ​

阿拉伯语、希伯来语、波斯语、乌尔都语是从右向左（RTL）书写的。RTL 适配的实质是语义方向翻转：

  • ❌ 禁用 left/right 对齐与坐标运算，✅ 一律用 leading/trailing（SwiftUI）或语义约束（UIKit 自动布局 leadingAnchor/trailingAnchor）——系统在 RTL 下自动把 leading 映射到右侧；
  • 导航栏返回箭头、滑动返回、列表缩进等系统组件自动镜像；自定义图标与动效需要显式声明是否镜像：进度条、返回箭头要镜像，「播放/暂停」「时钟」「品牌 Logo」不能镜像；
  • 数字与英文片段在 RTL 文本中仍按 LTR 渲染（Unicode bidi 算法），复制/校验逻辑要意识到「显示顺序 ≠ 存储顺序」。
swift
// File: Sources/LocalizationA11y/RTLSupport.swift —— 方向判定与方向感知图标（节选）

import Foundation

enum RTLSupport {
    /// 系统判定：Locale.characterDirection 按语言码返回书写方向
    static func shouldMirrorLayout(languageCode: String) -> Bool {
        Locale.characterDirection(forLanguageCode: languageCode) == .rightToLeft
    }

    /// 「前进」箭头在 RTL 下必须镜像——这行代码在评审中替代了口头约定
    static func forwardChevron(for languageCode: String) -> String {
        shouldMirrorLayout(languageCode: languageCode) ? "‹" : "›"
    }
}

13.3 本地化工程流：把「翻译」纳入 CI ​

13.3.1 key 命名与注释纪律 ​

本地化事故的源头大多在取词阶段。团队规范（进 9.6 评审清单）：

规则原因
key 三段式：模块.页面.用途译者有上下文；CI 可按模块统计覆盖率
String(localized:) 必带 comment注释是译者唯一的信息来源：谁在什么场景看到它、点击后发生什么
禁止运行时字符串拼接拼接产出的句子在别的语序下不成立（见 13.2.4）；整句取词 + 占位符
占位符有名字%@ 满天飞时译者无法调整语序；用 String(localized: "\(name) 你好") 的插值形式生成具名占位符
装饰性数字/符号不进文案资源文案资源只承载语言内容，格式交给 FormatStyle（13.2.3）

13.3.2 伪本地化：最便宜的风险探测器 ​

伪本地化（pseudolocalization）= 不真的翻译，而是把源字符串机械变换后「假装」是一门新语言，用来在没有译者参与的情况下暴露翻译风险：

风险伪本地化如何暴露
漏翻（硬编码字符串）走过本地化管道的字符串带重音标记，裸 ASCII 的就是漏网之鱼
截断 / 溢出伪文本比原文长约 40%，固定宽度的按钮和标签立刻撑破
拼接破坏被拆成两段的句子经变换后语序错乱、占位符丢失，一眼可见
占位符漂移变换必须原样保留 %@，丢占位符即运行时崩溃被当场抓住
swift
// File: Sources/LocalizationA11y/PseudoLocalizer.swift —— 伪本地化纯逻辑版（节选）

struct PseudoLocalizer {

    /// Latin → 重音形映射；非 Latin（CJK/RTL）原样保留
    static let accentMap: [Character: String] = [
        "a": "á", "e": "é", "i": "í", "o": "ó", "u": "ú", "y": "ý",
        "A": "Á", "E": "É", "I": "Í", "O": "Ó", "U": "Ú", "Y": "Ý",
    ]

    static func pseudo(_ source: String, wrapMarkers: Bool = true) -> String {
        var out = ""
        for ch in source {
            let mapped = accentMap[ch] ?? String(ch)
            out += mapped
            if isVowelLike(mapped) { out += mapped }   // 元音重复 ≈ +30~40% 长度，模拟德语膨胀
        }
        // 哨兵括号：任何被裁掉的头部/尾部都会切掉标记，截图审查一眼可见
        return wrapMarkers ? "[!! \(out) !!]" : out
    }

    /// 裸 ASCII + 含字母 → 大概率是没走本地化管道的硬编码英文
    static func isLikelyUntranslated(_ source: String) -> Bool {
        source.contains(where: { $0.isLetter }) && source.allSatisfy { $0.isASCII }
    }
}

13.4.1 L1 系统层：尊重用户的系统设置 ​

系统设置是无障碍的「用户偏好总开关」，App 的义务是全部响应而不是只做几个好看的开关：

设置SwiftUI 响应UIKit 响应
Dynamic Type（字体缩放）.font(.body) 等文本样式自动缩放；自定义字体 .custom(_, size:, relativeTo:)；间距 @ScaledMetricUIFontMetrics + adjustsFontForContentSizeCategory = true
Reduce Motion（减弱动态效果）@Environment(\.accessibilityReduceMotion) 关闭转场/视差UIAccessibility.isReduceMotionEnabled + 通知监听
Increase Contrast@Environment(\.colorSchemeContrast) 切换高对比配色同语义的 trait / 配色分支
Bold Text / Button Shapes文本样式自动响应；.buttonStyle(.bordered) 自动出边框UIAccessibility.isBoldTextEnabled 等

✅ 推荐：设计稿默认只出 1x 字号，但排期必须包含 XXL（最大三档）快照——这是 L1 层唯一的验收方式；@ScaledMetric 管间距而非只管字号，否则大字号下文字挤压重叠。

13.4.2 L2 语义层：给每个元素正确的「身份」 ​

VoiceOver 用户看到的界面 = 每个可达元素的四要素 + 遍历顺序：

要素回答的问题反例
label这是什么（名词）图片按钮 label 是文件名 btn_pay@2x
value当前值是什么滑杆不说当前温度；余额被逐位读成「一二三四点五六」
hint操作会怎样（仅在前三者不足时）每个按钮都带 hint，播报冗长到不可用
traits它是什么角色、什么状态自绘按钮没有 .isButton，用户不知道可以点
swift
// File: Sources/LocalizationA11y/AccessibilityDescriptions.swift —— 四要素生成器（节选）

/// 账户卡片 → 无障碍描述：这是本章示例 target 中「可单测」的语义层
struct AccountCardModel: Sendable {
    var bankName: String
    var maskedNumber: String      // "尾号 8888"
    var balance: Double
}

enum AccountCardA11y {
    static func describe(_ model: AccountCardModel) -> AccessibilityElement {
        AccessibilityElement(
            label: "\(model.bankName)（\(model.maskedNumber)）",          // 名词：这是哪张卡
            value: "余额 " + model.balance.formatted(                      // 值：格式化货币，
                .currency(code: "CNY").locale(Locale(identifier: "zh_CN"))), // 绝不让 VoiceOver 逐位读数字
            hint: "双击查看账单明细",                                       // 仅在 label/value 不足时补充
            traits: [.button]
        )
    }
}

13.4.3 L3 交互层：焦点、顺序与操作可达 ​

  • 焦点顺序 = 阅读顺序 ≈ 视觉顺序：布局改版后最容易出现「焦点先读到右下角的价格、再读到标题」的错乱；分组的容器用 .accessibilityElement(children: .combine) 合并成一条播报；
  • 每个手势操作都要有按钮等价物：滑动删除、下拉刷新、长按菜单必须同时存在于 VoiceOver 自定义操作（.accessibilityAction / accessibilityCustomActions）中——VoiceOver 手势不是用户手势的镜像；
  • 状态变化要主动播报（UIKit）：加载完成、列表刷新用 UIAccessibility.post(notification: .announcement, argument: "已加载 3 条结果")，否则屏幕阅读器用户对「屏幕变了」毫无感知；SwiftUI 数据驱动会自动重算语义树，但焦点不会自动移动到新内容；
  • 复杂图表提供替代视图或摘要（「本月支出较上月下降 12%」），语音输入路径覆盖所有表单。

13.4.4 L4 认知层：文案与错误恢复 ​

认知无障碍服务的是所有用户，也是 WCAG 最常被忽略的部分：

  • 错误信息说清「发生了什么 + 怎么办」，禁止裸错误码（呼应 1.8 的错误分层：用户文案与日志文案分离）；
  • 表单校验就地标注在字段旁（不是只红个边框），VoiceOver 聚焦字段即播报错误（SC 3.3.1/3.3.3）；
  • 谨慎使用时限：验证码倒计时可延长或重发；「5 秒后自动跳转」必须可暂停；
  • 关键操作的确认文案用完整句子，避免「确认？」式的二义性。

13.5 SwiftUI / UIKit 双框架适配对照 ​

双框架并存是企业存量（4 章）的常态，无障碍 API 必须两套都会写：

需求SwiftUIUIKit
语义 label.accessibilityLabel("结账")accessibilityLabel = "结账"
语义 value.accessibilityValue("3 件")accessibilityValue = "3 件"
语义 hint.accessibilityHint("保存并返回列表")accessibilityHint = "保存并返回列表"

13.7 EAA 与 WCAG 2.2：合规追溯矩阵 ​

欧洲无障碍法案（European Accessibility Act，指令 (EU) 2019/882）已于 2025 年 6 月 28 日进入适用期：面向欧盟消费者的电子商务、银行服务、交通票务、电子书、通信服务等必须满足无障碍要求，App 作为服务触点被直接覆盖（成员国以本国立法落地，如德国 BFSG）。符合性判定的事实基准是 EN 301 549 引用的 WCAG——工程上建议直接以 WCAG 2.2 AA（2022 年 10 月发布）为目标，把 EAA 与内部验收统一到一张追溯矩阵上，方法与 10.6.1 的法规映射完全同构：

WCAG SC要求iOS 技术控制验证方式（→ 证据）
1.1.1 非文本内容所有非文本有替代装饰图 hidden；内容图 .accessibilityLabel审计器 + VoiceOver 走查记录
1.4.3 对比度（文本）≥ 4.5:1（大字 3:1）ContrastAuditor 对设计令牌单测swift test 报告（本章示例）
1.4.4 文本缩放支持至 200% 无功能损失Dynamic Type 全量接入XXL 快照 + 截图

2.4.7 焦点可见焦点位置可见系统焦点框；自定义样式不移除VoiceOver / 键盘走查

⚠️ 坑点：EAA 的义务主体是「服务」而不是「App 安装包」——客服渠道、账单、网站同受约束；合规是持续状态而非发版检查点，每季度复核矩阵（新功能 → 新增矩阵行），并把矩阵与无障碍声明（accessibility statement）一起作为审计证据留档。豁免（微型企业、2030-06-28 前的遗留服务合约）见指令原文，工程规划按「全量达标」执行。

企业级场景分析 ​

场景一：全球零售 App 的多语言改造（从 1 种语言到 9 种） ​

背景：第 10 章案例二的零售 App 出海欧盟与中东。存量现状：字符串硬编码在 View 里、金额日期手拼、Simulator 里切德语后按钮全部截断、阿语用户反馈「按钮文字反了」。

改造四步（两个季度，与业务迭代并行）：

  1. 存量迁移：脚本扫描 String(format:)、手拼日期与裸 Text("中文")，迁移到 String Catalog；key 三段式 + comment 全量补齐（13.3.1）；
  2. 格式层重构：金额、日期、百分比全部收敛到 FormatStyle + 显式 Locale（13.2.3），货币跟结算区域而不是跟设备语言——这一步单独上线，因为它是正确性修复不是展示优化；
  3. 伪本地化冒烟：CI 加双倍长度伪语言 + 关键 20 个页面快照，一次性修掉 40+ 处固定宽度截断；Accented 伪语言暴露 17 处硬编码字符串；
  4. RTL 专项：阿语与希语构建跑 RTL 伪语言走查，修复 9 处 left/right 布局与 3 处不该镜像的图标（播放键、时钟）。

结果：第 5~9 种语言接入变成纯翻译工作（译文 PR 走 CI 门禁即合入），零代码改动；伪本地化门禁上线后拦截的截断/漏翻回归约每迭代 5 起。关键经验：先修格式正确性（1.234.567,89），再做翻译——顺序反了会在错误的地基上返工两遍。

场景二：银行 App 的 EAA 合规冲刺（6 周） ​

背景：面向欧盟零售用户的手机银行，2025 年适用期临近。审计基线：主转账流程 VoiceOver 完成率 0%（验证码控件不可达）、品牌金色按钮对比度 2.8:1、表单错误只有红框没有文字。

小结与自测 ​

要点回顾：

  1. i18n 是代码能力、l10n 是资源落地、a11y 是工程质量；三者都是架构与流程属性，冲刺救不了；
  2. String Catalog 让 key/译文/状态/复数变体可构建期校验；FormatStyle + 显式 Locale 把格式正确性从设备运气变成代码事实；
  3. 复数是 CLDR 语言规则：zh 只有 other、en 两类、ru 四类、ar 六类；字符串拼接是一等反例；
  4. 伪本地化 + CI 门禁（死 key / 缺翻译 / 占位符 / 长度冒烟）让翻译回归在 PR 阶段被拦截；
  5. 无障碍四层模型：系统层尊重设置、语义层四要素、交互层焦点与可达、认知层文案与恢复；自动化审计守机械问题，手工 VoiceOver 守语义与体验；
  6. EAA 2025-06-28 起是欧盟 B2C 服务的法定义务；用 SC → 技术控制 → 验证方式 → 证据的追溯矩阵把合规做成可审计的持续状态。

自测题（先自答再回看正文）：

1. 为什么格式化代码要显式传 Locale，而不是统一依赖 Locale.current？

因为 Locale.current 在 CI、同事模拟器与用户真机上是三个不同的值，隐式依赖等于把正确性交给环境。格式应跟随「内容面向的区域」这一产品决策（货币跟结算区域、号码跟账号归属地），「跟随设备」只是其中一个需要显式声明的选择。显式传 Locale 还让格式化逻辑可以在单测中确定性验证（本章测试全部依赖这一点）。

2. 俄语的 21、22、25 为什么是三种不同词形？中文为什么永远是 other？

CLDR 规则按「个位数 + 排除 11~14」判定：21（i%10=1 且 i%100≠11）是 one，22 落入 2~4 是 few，25 落入 5~9 是 many。中文的「数」由量词承载、名词不变形，所以整个整数域只有 other。这说明复数是语言规则而非算术，if n == 1 式拼接只对英语碰巧成立——正确做法是交给 String Catalog 复数变体或 CLDR 规则引擎。

3. 伪本地化能在没有译者的情况下提前发现哪几类问题？

四类：漏翻（裸 ASCII 字符串没被重音标记覆盖，即硬编码）、截断（+40% 膨胀撑破固定宽度）、拼接破坏（被拆分的句子变换后语序错乱）、占位符丢失（变换必须原样保留 %@，丢失即当场暴露）。配合快照还能暴露 RTL 假镜像。它是最便宜的探测器，因为它不需要任何翻译资源，一个 Debug 构建就能全量跑。

4. VoiceOver 四要素各回答什么问题？hint 为什么慎用？

label 回答「这是什么」，value 回答「当前值是什么」，traits 回答「什么角色/状态」（按钮、已选中等），hint 回答「操作后会发生什么」。hint 只在前三者信息不足时补充——每个元素都挂 hint 会让播报冗长到不可用，等于把使用手册塞进每个按钮。金额等数值必须格式化进 value，否则被逐位朗读。

5. EAA/WCAG 追溯矩阵一行需要哪几列？为什么自动化审计不能替代手工 VoiceOver？

列：成功标准（SC）→ 要求 → iOS 技术控制 → 验证方式 → 证据链接。自动化审计（审计器/performAccessibilityAudit）只能判定机械属性（缺 label、对比度、触控目标），无法判定语义正确性——一个 label 值为 "button" 的按钮能通过全部自动检查，但对用户毫无意义；焦点顺序是否贴合阅读顺序、真实流程能否完成，只有真机走查能回答。所以门禁组合是单测 + 审计 + 手工清单三层。
