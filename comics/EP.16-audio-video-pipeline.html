第 16 话 · 开播即卡：七跳链路与弱网治理 ​

服务端全绿，用户却一直黑屏。问题不在「服务」，在「链路」。 本话漫画：EP.16-audio-video-pipeline.svg

这一话的冲突 ​

直播上线首日，机房大盘漂亮得像样板间：CPU 40%、带宽余量 60%、日志没有任何 error。 但客服群里刷屏：开播 5 秒还在转圈，弹幕从「卡了」升级成「主播跑路」。

Swifty 的第一反应也是查服务端——直到 Runtime 长老把问题掰成两半： 用户感知的是端到端链路，而你监控的只是其中一跳。 这一话要建立一张七跳地图，并且让每一跳都打上同口径的埋点。

登场角色 ​

  • Swifty：负责客户端播放器的年轻工程师，习惯从服务端日志找答案。
  • Runtime 长老：把「链路」拆成可观测节点的人，坚持先同口径、再优化。
  • 产品同学：只关心「开播几秒能看到画面」，对指标名不感兴趣。
  • 值班运维：手持全绿大盘，却解释不了黑屏。

分格解读 ​

格 1 · 痛点现场：开播 5 秒黑屏 ​

  • 左侧手机预览窗一直转圈，右侧大盘三块全绿；
  • 在线人数 1200 → 300，说明不是「没人看」，是「看不了」；
  • 弹幕与客服双重报警，逼着团队承认：监控口径漏了客户端链路。

格 2 · 机制登场：弱网三件套先保连续 ​

  • 码率阶梯（ABR）：4M → 2.5M → 1.8M → 1.2M，按缓冲水位与吞吐升降档；
  • FEC + NACK：关键帧冗余约 20%，普通帧 NACK 最多 2 次，重传超 200ms 直接放弃；
  • 抖动缓冲：depth = P95 抖动 × 2 + 30ms，最低不低于 60ms；
  • 升档要同时满足四个条件，降档分「无条件」与「安全」两档，避免来回抖动。

格 3 · 七跳链路：四个大节点 + 三个小节点 ​

  • 大节点：采集 → 编码 → 传输 → 播放；
  • 小节点：前处理 → 封装 → 分发；
  • 每一跳都要能回答两件事：耗时多少、丢了什么；
  • 传送门式统一命名：capture / encode / send / play，埋点字段同名同义；
  • 协议选型：RTMP 上行 2~10s、SRT 200ms~2s 抗弱网、WebRTC 100~400ms 适合互动。

Runtime 长老划重点 ​

先把七跳各打一个同口径的 signpost，再谈优化；否则「卡」永远只能靠猜。

自测一题 ​

问：服务端 99.9% 可用、播放成功率 98%，为什么用户仍可能大面积黑屏？

答：可用性只描述「服务活着」，不代表「画面到了」。首帧耗时、分发 TTFB、弱网重连、 抖动缓冲水位都发生在服务端之外；缺了客户端七跳埋点，就无法把「黑屏」定位到具体一跳。

去实验室 ​

  • 深读：第 16 章 · 音视频与实时链路
  • 动手：examples/MediaPipeline —— 码率阶梯、抖动缓冲、重连与音频会话的纯逻辑实现；
  • 观察：把丢包率从 0% 调到 8%，看缓冲水位与降档时机如何变化。

下一话预告 ​

三盏绿灯、一次回滚——当分母和样本都对不上时，指标越漂亮越危险。
