## 登场角色

- **斯威芙蒂**：改了价格计算函数，手动点了下单页觉得没问题，结果线上购物车金额全错，退款工单 300+。
- **Runtime 长老**：教她搭测试金字塔，让 CI 在合并前就拦住坏代码。

## 剧情梗概

手动回归覆盖不全，公共函数一改，所有调用方都可能受影响。正确的解法是建立三层测试金字塔：底层大量快速的单元测试（70%）、中层集成测试（20%）、顶层少量端到端 UI 测试（10%）。每个单元测试遵循 Given-When-Then 三段式，CI 跑全量测试加覆盖率门禁，坏代码在 PR 阶段就被拦住。

## 分格解读

### 格1 · 痛点现场

改了一个被多处调用的公共函数，手动只测了其中一个页面，其他调用方的边界条件全漏。线上爆发后才发现，损失已经造成。手动测试的根本问题是：**覆盖范围依赖人的记忆力和耐心**，代码量一大必然漏。

### 格2 · 机制登场

测试金字塔（Mike Cohn 提出）：

- **单元测试（70%）**：XCTest，测单个函数/类，mock 外部依赖，毫秒级执行。这是底座，量要大、速度要快。
- **集成测试（20%）**：测多模块协作，比如网络层 + 解析层 + 存储层的串联，需要真实数据库或测试服务器。
- **UI 测试（10%）**：XCUITest，端到端模拟用户操作，慢但最接近真实。只覆盖核心链路（登录、下单、支付）。

比例倒过来（大量 UI 测试）会导致：跑一次半小时、随便改个 UI 就红一片、维护成本爆炸。

### 格3 · 落地收束

- **Given-When-Then 三段式**：Given 准备数据和 mock，When 执行被测操作，Then 断言结果。每个测试只验证一个行为。
- **CI 门禁**：PR 触发 `xcodebuild test`，全量测试必须通过；代码覆盖率低于阈值（如核心模块 80%）则禁止合并；SwiftLint 检查代码风格。
- **Mock 依赖**：网络请求用 `URLProtocol` mock 或依赖注入协议，不要让单元测试依赖真实网络。

## Runtime 长老划重点

1. 测试金字塔：单元 70% / 集成 20% / UI 10%，比例倒了又慢又脆。
2. Given-When-Then 三段式，每个测试只验证一个行为。
3. CI 跑全量测试 + 覆盖率门禁，坏代码在合并前就被拦住。

## 自测一题

**问**：为什么不推荐写大量 UI 测试来替代单元测试？

**答**：UI 测试有三个硬伤：①慢——启动 App + 模拟操作，一个用例几秒到几十秒，全量跑要半小时；②脆——UI 布局微调（改个控件 ID、挪个位置）就可能导致测试失败，但业务逻辑其实没坏；③难定位——UI 测试失败时堆栈指向 UI 操作，很难直接定位到是哪段业务逻辑出错。单元测试快、稳、定位准，所以金字塔底座必须是单元测试。UI 测试只用来守护最核心的端到端链路。
