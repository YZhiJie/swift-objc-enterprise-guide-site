# 漫画 · 第 15 话 线上运营闭环：可观测性与灰度

## 登场角色

- **斯威芙蒂**：崩溃率升高但不知道哪崩，灰度 50% 不知道该不该全量，新功能出问题没法秒级回滚。
- **Runtime 长老**：教她用可观测性三支柱看清线上、用 Feature Flag 控制发布、用发布门禁自动兜底。

## 剧情梗概

上线不是终点，是运营的起点。没有可观测性等于盲飞——崩溃、卡顿、成功率全靠用户反馈才知道。正确的运营闭环是：①MetricKit + 三支柱（日志/指标/链路）看清线上；②Feature Flag 控制功能开关，出问题秒级 Kill Switch；③A/B 实验用一致性哈希分桶，发布门禁在核心指标超阈值时自动暂停灰度+回滚。

## 分格解读

### 格1 · 痛点现场

- **盲飞**：崩溃率升高，但只知道「崩了」，不知道哪个页面、哪个版本、哪个 iOS 版本崩；
- **拍脑袋灰度**：灰度到 50%，没有数据支撑判断「该全量还是该回滚」；
- **无法回滚**：新功能有 bug，只能紧急发版，等审核通过时用户已经流失。

### 格2 · 机制登场

- **可观测性三支柱**：日志（Log，查具体问题）、指标（Metrics，看趋势和告警）、链路（Tracing，追调用路径）。iOS 上用 MetricKit 免 SDK 采集崩溃、卡顿、功耗、磁盘 IO 等系统级指标，系统自动聚合回调。
- **Feature Flag**：把功能是否开启做成远程开关，代码分支判断 flag 值。出问题时后台关闭 flag，用户端秒级生效，不需要发版。必须有 Kill Switch（一键关停）。
- **A/B 实验**：用一致性哈希（如 `hash(userID) % 100 < bucketSize`）把用户分到对照组和实验组，保证同一用户始终在同一组，避免实验结果被用户流动污染。
- **发布门禁**：灰度发布时持续监控核心指标（崩溃率 < 0.5%、核心转化率不下降、ANR 率不升高），超阈值自动暂停灰度并回滚。

### 格3 · 落地收束

1. **埋点 Schema 校验**：所有埋点事件经过 Schema 校验，PII（个人身份信息）自动脱敏，字段不合规直接拦截，避免脏数据和合规风险；
2. **Flag 评估瀑布**：远程配置 → 本地缓存 → 编译期默认值，三级兜底确保 flag 永远有值，网络异常时不白屏；
3. **发布门禁决策表**：定义每个灰度阶段的通过/回滚阈值，自动化执行，不靠人盯。

## Runtime 长老划重点

1. 可观测性三支柱：日志查问题、指标看趋势、链路追调用，MetricKit 免 SDK。
2. Feature Flag 必须有 Kill Switch，出问题秒级关闭，不依赖发版。
3. 发布门禁：核心指标超阈值自动暂停灰度+回滚，不靠人盯。

## 自测一题

**问**：为什么 Feature Flag 不能只存在远程，必须有本地缓存和默认值？

**答**：因为远程配置依赖网络。如果 App 启动时网络不可用（地铁、电梯），远程 flag 拉不到，如果只有远程值，flag 就会是 nil 导致崩溃或功能不可用。三级瀑布的设计是：①远程配置（最新值，有网络时用）②本地缓存（上次拉取的值，无网络时用）③编译期默认值（兜底，确保永远有值）。这样无论什么网络状况，flag 都能给出确定结果，App 不会因为配置问题白屏。
